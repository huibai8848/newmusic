## 1. 模块目标

在基础音乐房之上，解决**多人同步播放的核心难题**（时钟漂移、网络延迟），并增加**互动玩法**（投票、礼物、排行榜）。

**衡量指标**：

| 指标 | 目标 |
|---|---|
| 房间内播放同步偏差 | ≤ 300ms（P95）/ ≤ 800ms（P99） |
| 同步校准频率 | ≤ 每 30 秒 1 次 |
| 投票点歌参与率 | ≥ 30%（房间内活跃用户） |
| 房间消息延迟 | ≤ 200ms（P95） |
| 弱网连接保持率 | ≥ 95%（4G 弱信号下） |
| 房间崩溃率 | ≤ 0.5% |

## 4. 播放同步与进度校准

### FR-22-001 服务端权威播放状态 【P0】

| 项 | 内容 |
|---|---|
| **功能目标** | 房间内所有人听到同一位置，误差 ≤ 300ms |
| **使用角色** | 系统内部（服务端权威） |

**核心模型**：

```java
/**
 * 房间播放状态（服务端权威）
 * 版本号单调递增，客户端依此判断是否需要重新同步
 */
public class RoomPlayState {
    private Long roomId;
    private Long songId;
    private Long playStateVersion;      // 单调递增，每次状态变化 +1
    private Integer playStatus;         // 1 播放中 / 2 暂停 / 3 缓冲中 / 4 结束
    private Integer startPositionMs;    // 播放开始时的起始位置（毫秒）
    private Long stateUpdateTimeMs;     // 状态更新时的服务端时间戳
    private Integer playbackRate;       // 倍速（100 = 1.0x，房间内固定 100）
    private Integer volume;             // 房间音量（0-100，房主控制，客户端本地调节覆盖）
    private Long updatedBy;             // 最后操作人
}
```

**客户端播放位置计算**：

```typescript
/**
 * 客户端根据服务端状态计算"现在应该在的位置"
 * 这是房间同步的核心算法
 */
function calculateExpectedPosition(state: RoomPlayState, serverTimeOffsetMs: number): number {
  if (state.playStatus === PAUSED || state.playStatus === ENDED) {
    return state.startPositionMs;
  }
  // 当前服务端时间（用本地时间 + 时钟偏移修正）
  const nowServerMs = Date.now() + serverTimeOffsetMs;
  // 已经过去的时长
  const elapsedMs = (nowServerMs - state.stateUpdateTimeMs) * (state.playbackRate / 100);
  // 期望位置
  const expected = state.startPositionMs + elapsedMs;
  // 不超过总时长
  return Math.max(0, Math.min(expected, state.durationMs));
}

/**
 * 时钟偏移估算（多次往返取最小 RTT 的样本，避免受网络抖动影响）
 */
class ClockSync {
  private offsetMs = 0;
  private samples: { offset: number; rtt: number }[] = [];

  onServerTimeResponse(t1: number, serverTime: number, t4: number) {
    const rtt = t4 - t1;
    // NTP 算法：(服务器时间 - 往返中点) - 本地时间
    const offset = serverTime - (t1 + t4) / 2;
    this.samples.push({ offset, rtt });
    if (this.samples.length > 5) {
      // 保留 RTT 最小的 5 个样本，取其中位数
      this.samples.sort((a, b) => a.rtt - b.rtt);
      this.samples = this.samples.slice(0, 5);
      const offsets = this.samples.map(s => s.offset).sort((a, b) => a - b);
      this.offsetMs = offsets[Math.floor(offsets.length / 2)];
    }
  }

  get offset(): number { return this.offsetMs; }
}
```

**业务规则**：

- `BR-22-001`：**服务端是唯一权威**，客户端**不允许**独立控制播放（只能请求）。
- `BR-22-002`：`playStateVersion` **单调递增**，客户端收到**更小**版本的消息**必须丢弃**（防乱序）。
- `BR-22-003`：**时钟同步**：客户端连接后**立即**做 3 次 NTP 风格的时间同步（间隔 500ms），之后每 **5 分钟**校准一次。
- `BR-22-004`：**时钟偏移**取**最小 RTT 样本的中位数**（避免网络抖动影响）。
- `BR-22-005`：房间内**播放倍速固定 1.0x**（不允许变速，否则同步混乱）。
- `BR-22-006`：**音量可本地调节**（不强制同步，用户可自行调整），但**静音状态同步**（房主静音则全员静音）。
- `BR-22-007`：状态变更（播放/暂停/切歌/跳转）**必须**通过 WebSocket 广播（BROADCASTING 模式，见 [13 章](./13-模块04-WebSocket.md)）。
- `BR-22-008`：状态变更**必须**持久化到 Redis（`ml:room:play:{roomId}`），新加入成员**立即**获取当前状态。
- `BR-22-009**：状态持久化**必须有 TTL**（房间结束后自动过期，如 24 小时）。
- `BR-22-010`：**操作请求必须带幂等键**（`clientMsgId`），防止重复提交导致重复切歌。
- `BR-22-011`：**权限校验**：只有房主/管理员可控制播放（点歌除外）。

**异常情况**：

| 编号 | 场景 | 处理 |
|---|---|---|
| `EX-22-001-1` | 客户端收到旧版本状态 | 丢弃，不更新 |
| `EX-22-001-2` | 服务端状态不存在（房间刚创建） | 客户端等待，显示"加载中" |
| `EX-22-001-3` | 消息乱序 | 版本号判断丢弃 |
| `EX-22-001-4` | 重复操作请求 | 幂等键去重 |
| `EX-22-001-5` | 服务端时间同步失败（全部超时） | 使用本地时间（降低同步精度）并标记 `syncDegraded: true` |
| `EX-22-001-6` | Redis 状态丢失 | 服务端重建（以当前播放位置为准） |

**验收标准**：

- `AC-22-001-1`：房间内所有成员播放位置偏差 ≤ 300ms（P95）
- `AC-22-001-2`：版本号乱序消息被丢弃
- `AC-22-001-3`：时钟同步在 5 分钟内完成
- `AC-22-001-4`：新成员加入立即获取当前状态
- `AC-22-001-5`：非房主/管理员无法控制播放
- `AC-22-001-6`：重复操作请求被幂等去重

### FR-22-002 进度校准机制 【P0】

| 项 | 内容 |
|---|---|
| **功能目标** | 持续校正漂移，保证长期同步 |
| **使用角色** | 系统内部 |

**双层校准策略**：

| 层级 | 触发 | 偏差阈值 | 处理 |
|---|---|---|---|
| **软校准** | 每 10 秒检查一次 | 偏差 > 500ms 且 ≤ 2000ms | **微调 `playbackRate`**（如 1.02x 加速追赶）持续 5 秒后恢复 1.0x |
| **硬校准** | 每 30 秒检查一次；或软校准后仍超阈值 | 偏差 > 2000ms | **直接跳转** `currentTime` 到期望位置 |

**软校准实现（避免可感知的跳跃）**：

```typescript
class SyncCalibrator {
  private readonly SOFT_THRESHOLD_MS = 500;
  private readonly HARD_THRESHOLD_MS = 2000;
  private readonly CHECK_INTERVAL_MS = 10_000;
  private readonly MAX_RATE_ADJUST = 0.05;    // 最大 ±5% 速度调整

  private calibrating = false;

  check() {
    if (this.calibrating) return;
    const expected = calculateExpectedPosition(this.state, this.clock.offset);
    const actual = this.audio.currentTime * 1000;
    const drift = actual - expected;   // 正数=快了，负数=慢了

    if (Math.abs(drift) > this.HARD_THRESHOLD_MS) {
      // 硬校准：直接跳转
      this.logger.warn('Hard sync: drift={}ms, seeking', drift);
      this.metrics.roomSyncHardTotal.inc();
      this.audio.currentTime = expected / 1000;
      return;
    }

    if (Math.abs(drift) > this.SOFT_THRESHOLD_MS) {
      // 软校准：微调播放速度追赶/放慢
      // 目标：在 5 秒内消除偏差
      const adjust = clamp(-drift / 5000, -this.MAX_RATE_ADJUST, this.MAX_RATE_ADJUST);
      this.applyTemporaryRate(1.0 + adjust, 5000);
      this.metrics.roomSyncSoftTotal.inc();
      this.logger.debug('Soft sync: drift={}ms, rate adjust={}', drift, adjust);
    }
  }

  /** 临时调整播放速度，durationMs 后恢复 */
  private applyTemporaryRate(rate: number, durationMs: number) {
    this.calibrating = true;
    this.audio.playbackRate = rate;
    setTimeout(() => {
      this.audio.playbackRate = 1.0;
      this.calibrating = false;
    }, durationMs);
  }
}
```

**软校准的听觉影响**：

```
偏差 1000ms（客户端慢了 1 秒）
   ↓
需要 5 秒内追赶 1 秒 → 需要额外速度 20% → 超过 MAX_RATE_ADJUST(5%)
   ↓
实际只能按 5% 追赶 → 5 秒追赶 250ms → 需要 20 秒才能追上 1 秒
   ↓
结论：偏差 500-2000ms 时，软校准需要较长时间。
优化：根据偏差大小**动态调整追赶时长**，或**提高 MAX_RATE_ADJUST 到 8%**（8% 速度变化在有音乐的背景下不易察觉）。
```

> **【假设 A-29】** `MAX_RATE_ADJUST` 设为 **8%**。理由：8% 的速度变化（1.08x）在有背景音时几乎不可察觉，但能显著加快追赶速度。需 A/B 测试验证感知度。

**业务规则**：

- `BR-22-012`：**检查频率**：每 10 秒检查一次（不用 `timeupdate`，因为其频率不足且不稳定）。
- `BR-22-013`：**软校准阈值 500ms**（超过则用户可能感知到不同步）。
- `BR-22-014`：**硬校准阈值 2000ms**（直接跳转，接受一次可感知的跳跃）。
- `BR-22-015`：**软校准最大变速 8%**，持续 5 秒。
- `BR-22-016`：**校准期间不叠加**（`calibrating` 标志防止重复校准）。
- `BR-22-017`：**用户拖动进度条**（若允许）后**重置校准基线**。
- `BR-22-018`：**缓冲状态**：播放中若发生缓冲（`waiting`），暂停校准，`canplay` 后重新校准。
- `BR-22-019`：**校准埋点**必须记录（偏差值、校准类型、房间 ID、网络类型）。
- `BR-22-020`：**软校准频繁触发**（1 分钟内 > 6 次）说明网络持续抖动，上报监控。
- `BR-22-021`：**页面不可见**（切后台）时**暂停校准**（`visibilitychange`），恢复可见时**立即做一次硬校准**。

**异常情况**：

| 编号 | 场景 | 处理 |
|---|---|---|
| `EX-22-002-1` | 音频未加载完成 | 跳过校准 |
| `EX-22-002-2` | 校准中切歌 | 取消校准，重置状态 |
| `EX-22-002-3` | 持续漂移（每次校准后仍漂移） | 检查时钟同步，重新做时间同步 |
| `EX-22-002-4` | 软校准导致音质异常（变速明显） | 降低 MAX_RATE_ADJUST 或直接硬校准 |
| `EX-22-002-5` | 硬校准过于频繁 | 提高阈值或检查网络 |
| `EX-22-002-6` | 页面切后台再回来 | 立即硬校准 |

**验收标准**：

- `AC-22-002-1`：偏差 500-2000ms 时软校准生效且不易察觉
- `AC-22-002-2`：偏差 > 2000ms 时硬校准
- `AC-22-002-3`：校准不叠加
- `AC-22-002-4`：切后台后恢复立即校准
- `AC-22-002-5`：校准埋点完整
- `AC-22-002-6`：长期播放（30 分钟）偏差保持在 300ms 内

> **说明**：本 FR 描述**升级后**的点歌与队列（基础版本见 [14 章](./14-模块05-音乐房.md)，此处补充投票与优先级）。

**队列结构**：

```java
public class RoomQueueItem {
    private Long id;
    private Long roomId;
    private Long songId;
    private Long requestedBy;          // 点歌人
    private Integer priority;          // 优先级（房主置顶 = 100，普通 = 0）
```

**排序规则**：

```
orderIndex = priority * 10000 + voteCount * 100 + (1000 - 插入顺序)
按 orderIndex DESC 排序（越大越靠前）
```

**业务规则**：

- `BR-22-023`：**队列上限 50 首**（超出拒绝）。
- `BR-22-024`：**房主置顶**的歌曲优先级最高（`priority = 100`）。
- `BR-22-025`：**重复点歌**（同一首歌已在队列）**合并**（投票数累加，不重复入队）。
- `BR-22-026`：**点歌后**在房间内**公屏提示**"XXX 点了《YYY》"。
- `BR-22-027`：**房主/管理员可删除**队列中的歌曲（需提示原因）。
- `BR-22-028`：**点歌人可撤销**自己的点歌（播放前）。
- `BR-22-029`：**队列变动**通过 WebSocket 广播（增量更新，不全量推送）。
- `BR-22-030`：**队列持久化**到 `t_room_queue`，房间结束后清理（或保留用于回顾）。
- `BR-22-031`：**点歌限流**：1 分钟最多 5 次。
- `BR-22-032`：**不可点播**下架/无版权歌曲。

### FR-22-004 投票切歌与投票跳过 【P1】

| 项 | 内容 |
|---|---|
| **功能目标** | 让房间成员集体决定跳过当前歌曲 |
| **使用角色** | 房间成员 |

**投票流程**：

```
任一成员发起"投票跳过当前歌曲"
   ↓
WebSocket 广播投票开始（含倒计时 60 秒）
   ↓
成员点击"同意跳过" → 记录投票
   ↓
判定（满足任一即通过）：
  - 同意票数 ≥ 当前在线人数 × 60%
  - 同意票数 ≥ 5 且 ≥ 在线人数 × 50%
  - 房主/管理员直接投票（一票通过）
   ↓
通过 → 跳过当前歌曲，播下一首，广播结果
未通过（60 秒超时） → 广播"投票未通过"，当前歌继续
   ↓
同一首歌**只能发起一次投票**（防骚扰）
```

**Redis 数据结构**：

```
ml:room:vote:{roomId}:{songId}   Hash {
  initiatorId: 123,
  startTime: 1730000000000,
  endTime:   1730000060000,
  status:    1,               // 1 进行中 / 2 通过 / 3 未通过
  voters:    "<Set 的虚拟表示>"   // 实际用 Set
}
ml:room:vote:voters:{roomId}:{songId}   Set<userId>
```

> **优化**：`voters` 用独立 Set 存储（避免 Hash 内序列化大对象），Hash 只存元数据。

**业务规则**：

- `BR-22-033`：**投票时长 60 秒**（可配置）。
- `BR-22-034`：**通过条件**（任一满足）：
  - 同意票 ≥ 在线人数 **60%**
  - 同意票 ≥ **5** 且 ≥ 在线人数 **50%**
  - 房主/管理员投票（**一票通过**）
- `BR-22-035`：**同一首歌只能发起一次**投票。
- `BR-22-036`：**每人一票**（Set 去重）。
- `BR-22-037`：**在线人数**以投票开始时的快照为准（避免中途进出影响）。
- `BR-22-038**：**投票发起冷却**：同一房间 5 分钟内最多发起 3 次投票（防骚扰）。
- `BR-22-039`：**不可投票**跳过第一首歌的前 30 秒（刚开播就跳过体验差）。
- `BR-22-040`：**投票结果实时广播**（每次投票更新票数）。
- `BR-22-041`：**投票通过**后立即切歌，且被跳过的歌**不播放下一首**（标记为"被跳过"）。
- `BR-22-042`：**房主可随时**跳过（不投票），但**必须**在公屏说明（自动提示"房主跳过了当前歌曲"）。
- `BR-22-043`：**投票数据**持久化到 `t_room_vote`（用于分析）。
- `BR-22-044`：**投票频率监控**：房间频繁投票说明歌曲质量差，可反馈给推荐系统。

**异常情况**：

| 编号 | 场景 | 处理 |
|---|---|---|
| `EX-22-004-1` | 同歌重复发起 | `80015`，提示"已发起过投票" |
| `EX-22-004-2` | 投票冷却中 | `80016`，提示剩余冷却时间 |

## 5. 互动玩法

### FR-22-005 房间排行榜 【P1】

| 项 | 内容 |
|---|---|
| **功能目标** | 展示房间内的贡献与活跃度 |
| **使用角色** | 房间成员（查看） |

**排行维度**：

| 榜单 | 统计口径 | 刷新频率 |
|---|---|---|
| **贡献榜** | 送礼价值总和 | 实时（ZSet） |
| **活跃榜** | 消息数 × 1 + 点歌数 × 5 + 投票数 × 2 | 实时（ZSet） |
| **点歌榜** | 点歌次数（有效播放的） | 每次点歌后 |
| **收听时长榜** | 房间内累计收听时长 | 每分钟更新 |

**Redis 结构**：

```
ml:room:rank:gift:{roomId}       ZSet   score = 累计礼物价值，member = userId
ml:room:rank:active:{roomId}     ZSet   score = 活跃分
ml:room:rank:request:{roomId}    ZSet   score = 点歌次数
ml:room:rank:listen:{roomId}     ZSet   score = 收听时长（秒）
```

**业务规则**：

- `BR-22-045`：排行榜**Top 10** 展示。
- `BR-22-046`：**实时更新**（ZSet `ZINCRBY`），房间页每 30 秒刷新展示。
- `BR-22-047`：**活跃分**计算：消息 × 1 + 点歌 × 5 + 投票 × 2 + 送礼 × 10。
- `BR-22-048`：**收听时长**每分钟上报一次（客户端累计，定时上报）。
  - **防作弊**：服务端校验时间间隔（上报间隔异常则不计）。
- `BR-22-049`：**房间结束**后排行榜**保留 24 小时**（可通过房间历史查看）。
- `BR-22-050`：**日榜/周榜**（P2）：跨房间聚合，本期不做。
- `BR-22-051`：**榜单变化**在公屏播报 Top 3 变化（如"XXX 成为贡献榜第 1"），但**限制频率**（1 分钟最多 1 条）。
- `BR-22-052`：**隐私**：用户可在设置中选择**不上榜**（匿名参与）。
- `BR-22-053`：**异常数据**过滤（如单次礼物价值异常高，需人工核查）。

**异常情况**：

| 编号 | 场景 | 处理 |
|---|---|---|
| `EX-22-005-1` | Redis 数据丢失 | 从 MySQL 重建（房间结束时会落库） |
| `EX-22-005-2` | 用户刷活跃分 | 频率限制 + 异常检测 |
| `EX-22-005-3` | 收听时长上报异常 | 服务端校验间隔，异常则忽略该次 |
| `EX-22-005-4` | 榜单为空 | 展示"暂无数据" |

**验收标准**：

- `AC-22-005-1`：四个榜单正确统计
- `AC-22-005-2`：实时更新且 30 秒内可见
- `AC-22-005-3`：活跃分计算正确
- `AC-22-005-4`：收听时长防作弊有效
- `AC-22-005-5`：房间结束后榜单保留 24 小时
- `AC-22-005-6`：用户可选择不上榜

## 6. 弱网与稳定性

### FR-22-008 弱网优化 【P1】

| 项 | 内容 |
|---|---|
| **功能目标** | 弱网下保持房间可用 |
| **使用角色** | 房间成员 |

**策略**：

| 场景 | 策略 |
|---|---|
| 网络抖动（RTT > 500ms） | 降低心跳频率（30s → 45s），减少消息广播频率 |
| 断线 | 指数退避重连（1s, 2s, 4s, 8s, 16s, 30s 封顶） |
| 重连成功 | 拉取当前播放状态 + 增量消息补偿（`lastMsgId`） |
| 长时间断线（> 2 分钟） | 提示"连接已断开"，提供手动重连 |
| 音频卡顿 | 缓冲期间显示"同步中..."，跳过校准 |
| 音频加载失败 | 降级为标准音质重试 |
| 消息发送失败 | 本地队列 + 重试（最多 3 次） |

**业务规则**：

- `BR-22-076`：**心跳自适应**：RTT > 500ms 时心跳间隔从 30s 调整为 45s（减少网络负担）。
- `BR-22-077`：**重连退避**：1s, 2s, 4s, 8s, 16s, 30s（封顶），加 ±20% 抖动。
- `BR-22-078`：**重连后补偿**：携带 `lastMsgId`，服务端返回此 ID 之后的消息（最多 100 条）。
- `BR-22-079`：**超过 100 条未收**：直接返回当前状态快照（不全量补消息，避免流量暴增）。
- `BR-22-080`：**音频卡顿时**暂停同步校准（缓冲期间位置本来就滞后）。
- `BR-22-081`：**消息本地队列**：发送失败的消息存本地，重连后重发（带 `clientMsgId` 幂等）。
- `BR-22-082`：**弱网下降低非核心消息频率**：如榜单刷新、系统提示。
- `BR-22-083`：**弱网提示**：连续 3 次重连失败，提示用户"网络不稳定"。
- `BR-22-084`：**音频降级**：弱网下自动切换到标准音质（见 [21 章](./21-模块12-播放升级.md)）。
- `BR-22-085`：**离线恢复**：网络恢复后**立即**做时钟同步 + 硬校准。
- `BR-22-086`：**弱网埋点**必须记录（网络类型、重连次数、同步偏差、卡顿次数）。

**异常情况**：

| 编号 | 场景 | 处理 |
|---|---|---|
| `EX-22-008-1` | 重连后消息缺失 | 增量补偿（`lastMsgId`） |
| `EX-22-008-2` | 补偿消息过百 | 返回状态快照 |
| `EX-22-008-3` | 长时间断线（> 5 分钟） | 提示"连接已关闭"，需手动重新进入房间 |
| `EX-22-008-4` | 消息重发导致重复 | `clientMsgId` 幂等 |
| `EX-22-008-5` | 弱网下音频完全无法加载 | 提示"网络异常，请检查网络" |
| `EX-22-008-6` | 房主断线 | 房主交接逻辑触发（见 [14 章](./14-模块05-音乐房.md)） |

**验收标准**：

- `AC-22-008-1`：弱网下心跳自适应
- `AC-22-008-2`：断线重连成功且消息补偿
- `AC-22-008-3`：长时间断线有明确提示
- `AC-22-008-4`：消息不重复（幂等）
- `AC-22-008-5`：弱网下音频降级
- `AC-22-008-6`：网络恢复后快速同步
- `AC-22-008-7`：弱网埋点完整

## 10. WebSocket 消息类型（房间升级）

| `type` | 方向 | 载荷 | 说明 |
|---|---|---|---|
| `ROOM_PLAY_STATE` | S→C | `{ roomId, songId, playStatus, startPositionMs, stateUpdateTimeMs, playStateVersion, ... }` | 播放状态（权威） |
| `ROOM_SYNC_ACK` | S→C | `{ clientTime, serverTime }` | 时间同步响应 |
| `ROOM_QUEUE_UPDATE` | S→C | `{ action, item }` | 队列增量更新 |
| `ROOM_VOTE_START` | S→C | `{ voteId, songId, endTime, onlineCount, initiator }` | 投票开始 |
| `ROOM_VOTE_UPDATE` | S→C | `{ voteId, agreeCount, status }` | 投票更新 |
| `ROOM_VOTE_RESULT` | S→C | `{ voteId, passed, agreeCount }` | 投票结果 |
| `ROOM_GIFT` | S→C | `{ senderId, receiverId, giftCode, quantity, animation }` | 礼物 |
| `ROOM_RANK_UPDATE` | S→C | `{ type, top3 }` | 榜单更新（低频） |
| `ROOM_LIKE_UPDATE` | S→C | `{ songId, count }` | 点赞数更新（节流 2s） |
| `ROOM_DANMAKU` | S→C | `{ userId, nickname, content }` | 弹幕 |
| `ROOM_MSG_COMPENSATE` | S→C | `{ messages: [...] }` | 重连消息补偿 |

**客户端时间同步**：

```typescript
// 请求
ws.send(JSON.stringify({ type: 'ROOM_SYNC_REQ', data: { clientTime: Date.now() } }));

// 响应
// { type: 'ROOM_SYNC_ACK', data: { clientTime: 1730000000000, serverTime: 1730000000050 } }
// 客户端计算：offset = serverTime - (clientTime + rtt/2)
```

## 11. 性能与容量

| 项 | 预估 | 说明 |
|---|---|---|
| 单房间最大成员 | 500 | WebSocket 连接数 |
| 单房间消息 QPS | 50（峰值） | 500 人 × 0.1 条/秒 |
| 房间数（并发） | 1000 | 总 WebSocket 连接 5 万 |
| 播放状态广播 | 每次状态变更 × 成员数 | BROADCASTING 模式，各节点推自己连接的成员 |
| 同步校准消息 | 每 10 秒 × 成员数 | **不做服务端推送**（客户端本地计算，节省带宽） |
| 排行榜更新 | 每次互动 × 1 | ZSet 操作，极快 |
| 礼物动画 | 全屏动画 1 分钟 1 次 | 限制频率 |

**关键设计**：**同步校准在客户端本地完成**（每 10 秒检查一次本地偏差），**服务端不推送校准消息**——否则 500 人 × 每 10 秒 = 50 msg/s 纯校准流量，浪费。

## 12. 降级策略

| 依赖 | 故障 | 降级 |
|---|---|---|
| Redis（播放状态） | 不可用 | 服务端内存存状态（单节点有效，多节点不一致） + 告警 |
| RocketMQ（广播） | 不可用 | 降级为单节点广播（其他节点成员不同步） + 提示 |
| 时钟同步 | 失败 | 使用本地时间，标记 `syncDegraded` |
| 投票服务 | 不可用 | 隐藏投票入口 |
| 礼物服务 | 不可用 | 隐藏礼物入口 |
| 排行榜 | 不可用 | 隐藏榜单 |
| WebSocket | 断开 | 轮询播放状态（每 5 秒） |
| CDN | 音频加载失败 | 降质重试 + 备用 CDN |
