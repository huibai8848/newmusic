## 1. 模块目标

建立**"埋点 → 采集 → 计算 → 展示 → 决策"**的完整数据闭环，让产品与运营决策**基于数据而非拍脑袋**。

**核心目标**：

| 目标 | 说明 |
|---|---|
| **统一埋点** | 一套埋点规范覆盖全端，禁止各自为战 |
| **统一口径** | 所有指标有唯一定义，避免"同名不同义" |
| **实时可见** | 核心指标分钟级延迟，异常即时发现 |
| **可下钻** | 从总览下钻到维度、到个体 |
| **可归因** | 每个变化能追溯到具体功能/实验/渠道 |
| **有闭环** | 指标异常 → 告警 → 排查 → 行动 → 验证 |

**衡量指标（数据平台自身）**：

| 指标 | 目标 |
|---|---|
| 埋点覆盖率（关键行为） | 100% |
| 埋点上报成功率 | ≥ 99.5% |
| 埋点数据延迟（实时链路） | ≤ 1 分钟 |
| 离线 T+1 报表产出时间 | 次日 07:00 前 |
| 指标口径文档覆盖率 | 100% |
| 数据质量问题（每日） | ≤ 3 个 |
| 报表加载 P95 | ≤ 3s |
| 数据与业务库对账偏差 | ≤ 0.5% |

## 4. 埋点体系

### FR-26-001 埋点规范 【P0】

| 项 | 内容 |
|---|---|
| **功能目标** | 定义统一的埋点模型、命名、上报方式，保证数据可用 |
| **使用角色** | 开发（实施）、数据（管理） |

**埋点模型（事件 + 属性）**：

```
一个埋点 = 事件（Event）+ 公共属性（Common Properties）+ 业务属性（Properties）+ 用户属性（User Properties）

事件名规范：{domain}_{object}_{action}
  例：player_song_play、post_like_click、room_enter_success

属性名规范：snake_case
  例：song_id, play_duration, from_source, position
```

**公共属性（所有事件自动携带）**：

| 属性 | 说明 | 示例 |
|---|---|---|
| `event_id` | 事件唯一 ID（客户端生成，用于去重） | `uuid` |
| `event_time` | 客户端时间戳（毫秒） | `1760000000000` |
| `server_time` | 服务端接收时间戳 | `1760000000123` |
| `user_id` | 用户 ID（未登录为 null） | `123456` |
| `device_id` | 设备 ID | `d_abc123` |
| `session_id` | 会话 ID（30 分钟无活动则新会话） | `s_xyz789` |
| `platform` | 平台 | `web` |
| `app_version` | 前端版本 | `1.2.0` |
| `os` | 操作系统 | `Windows 11` |
| `browser` | 浏览器 | `Chrome 120` |
| `screen` | 屏幕分辨率 | `1920x1080` |
| `network` | 网络类型 | `4g` / `wifi` |
| `ip` | IP（服务端填充） | — |
| `region` | 地区（IP 解析） | `浙江` |
| `page_id` | 页面标识 | `home` |
| `page_url` | 页面 URL | `/home` |
| `referrer` | 来源页 | — |
| `trace_id` | 链路追踪 ID（关联后端日志） | — |
| `ab_tests` | 参与的实验与分组 | `{"rerank_v2":"treatment_a"}` |
| `is_new_user` | 是否新用户（注册 < 7 天） | `false` |

**业务属性（按事件定义）**：

```json
{
  "event": "player_song_play",
  "common": { "...公共属性..." },
  "properties": {
    "song_id": "1001",
    "song_name": "晴天",
    "artist_id": "2001",
    "playlist_id": null,
    "from_source": "recommend_home",
    "position": 3,
    "quality": "high",
    "is_cache": false,
    "recommend_trace_id": "r_abc123"
  }
}
```

**埋点分类（按重要性）**：

| 类别 | 说明 | 举例 |
|---|---|---|
| **核心埋点（P0）** | 业务指标必需，必须 100% 覆盖 | 播放、点赞、搜索、注册、下单（本无） |
| **重要埋点（P1）** | 分析必需，关键路径覆盖 | 曝光、点击、页面停留 |
| **辅助埋点（P2）** | 用于细粒度分析 | 按钮 hover、滚动深度 |
| **性能埋点** | 技术指标 | 页面加载、接口耗时、错误 |

**埋点上报方式**：

| 方式 | 说明 | 适用 |
|---|---|---|
| **批量上报** | 客户端缓存事件，每 5 秒或满 20 条上报 | **默认**（省流量、减压力） |
| **立即上报** | 关键事件立即上报 | 播放、支付（本无支付） |
| **页面卸载上报** | `visibilitychange` + `sendBeacon` | 页面停留时长 |
| **服务端埋点** | 后端直接记录（无前端参与） | 接口耗时、任务执行 |

**上报端点**：`POST /api/v1/track/events`（支持 `sendBeacon`）+ `POST /api/v1/track/batch`

**业务规则**：

- `BR-26-001`：**所有埋点必须有文档**（事件名、触发时机、属性、示例），无文档的埋点不予采集。
- `BR-26-002`：**事件名必须遵循规范**（`{domain}_{object}_{action}`），且**全局唯一**。
- `BR-26-003`：**埋点必须带公共属性**（由 SDK 自动注入，业务方不手动传）。
- `BR-26-004`：**埋点 ID 必须去重**（`event_id` 幂等，服务端 5 分钟内去重）。
- `BR-26-005`：**埋点不得包含敏感信息**（密码、手机号明文、身份证、token），手机号必须脱敏。
- `BR-26-006`：**埋点上报不阻塞主流程**（异步、失败不影响业务）。
- `BR-26-007`：**埋点失败必须重试**（本地缓存，最多 3 次，超过丢弃）。
- `BR-26-008`：**埋点采样**：高流量事件按比例采样（如 hover 100% 上报会爆炸），**核心事件不采样**。
- `BR-26-009`：**埋点版本管理**：埋点定义变更时保留历史版本（便于回溯），属性**只增不减**（改语义须新建属性）。
- `BR-26-010`：**客户端时间不可信**：分析时使用 `server_time`，`event_time` 仅用于客户端行为顺序。
- `BR-26-011`：**埋点数据必须可追溯**：每条埋点有 `trace_id`，可与后端日志关联。
- `BR-26-012`：**禁止"埋点上线后补文档"**（先文档后埋点）。
- `BR-26-013`：**埋点测试必须覆盖**：前端单测 + 联调验证 + 线上抽样验证。
- `BR-26-014`：**埋点去重**：同一用户同一次行为不得重复上报（如 React 严格模式导致的双次执行）—— SDK 层做 500ms 内的同事件去重。

**异常情况**：

| 编号 | 场景 | 处理 |
|---|---|---|
| `EX-26-001-1` | 上报接口不可用 | 本地缓存（最多 100 条），恢复后重传 |
| `EX-26-001-2` | 本地缓存满 | 丢弃最旧的非核心事件 |
| `EX-26-001-3` | 埋点属性缺失 | 上报仍发送（缺失字段为 null），数据侧告警 |
| `EX-26-001-4` | 埋点风暴（异常高频） | SDK 限流（单用户 100 事件/分钟） |
| `EX-26-001-5` | 广告拦截器 | 降级为服务端埋点（部分事件） |
| `EX-26-001-6` | 用户禁用 Cookie/存储 | 使用内存会话（数据仅当次有效） |
| `EX-26-001-7` | 埋点数据格式错误 | 进"脏数据"主题，人工排查 |

**验收标准**：

- `AC-26-001-1`：所有关键行为有埋点且文档完整
- `AC-26-001-2`：埋点上报成功率 ≥ 99.5%
- `AC-26-001-3`：埋点不阻塞业务（异步）
- `AC-26-001-4`：埋点去重生效
- `AC-26-001-5`：埋点不含敏感信息
- `AC-26-001-6`：埋点失败重试与本地缓存
- `AC-26-001-7`：埋点带公共属性与 trace_id
- `AC-26-001-8`：埋点可与服务端日志关联

### FR-26-002 埋点采集链路 【P0】

| 项 | 内容 |
|---|---|
| **功能目标** | 高吞吐、低延迟、不丢数据的埋点采集 |
| **使用角色** | 系统内部 |

**链路架构**：

```
[前端 SDK]
   ↓ HTTP 批量上报（5s / 20 条）
[Track Gateway（Spring Boot）]
   - 鉴权（可选，匿名也接收）
   - 限流
   - 格式校验
   - 幂等去重（Redis，event_id）
   - 补全服务端属性（IP、地区、server_time、trace_id）
   ↓ 写入 MQ
[Kafka / RocketMQ]
   Topic: ml_track_event
   Partitions: 12（按 user_id hash 分区，保证同用户有序）
   ↓ 两条消费链路
   ├─→ [实时链路] Flink / 消费者 → 实时指标（Redis / ClickHouse 实时表）
   └─→ [离线链路] Kafka → ODS（HDFS/S3）→ Spark 批处理 → DWD/DWS/ADS
```

> **【假设 A-36】** 实时计算引擎选型：**Flink 1.17**（业界主流，JDK 8 兼容）或**自研 Java 消费程序**（简单场景）。本项目**实时指标简单**（计数、去重 UV），**建议先用 Java 消费者 + Redis 实现**（降低运维复杂度），Flink 留作二期演进。若已具备 Flink 团队，直接上 Flink。

**为什么用 Kafka 而不是 RocketMQ**：

| 维度 | Kafka | RocketMQ |
|---|---|---|
| 吞吐 | **极高**（百万/秒） | 高（十万/秒） |
| 生态 | **与 Flink/Spark 无缝** | 需适配器 |
| 回溯 | **原生支持（offset 重置）** | 支持 |
| 数据保留 | **长（按时间/大小）** | 支持 |
| 适用 | **数据管道** | 业务消息 |

> **结论**：**埋点用 Kafka**（数据管道场景），**业务消息用 RocketMQ**（如房间广播、通知）。两者并存，各司其职。

**Trace Gateway 关键实现**：

```java
@RestController
@RequestMapping("/api/v1/track")
public class TrackController {

    private final KafkaTemplate<String, String> kafkaTemplate;
    private final RedisTemplate<String, String> redis;

    @PostMapping("/batch")
    public Result<Void> batch(@RequestBody TrackBatchRequest req,
                              HttpServletRequest httpReq) {
        // 1. 限流（单 deviceId 1000 事件/分钟）
        if (!rateLimiter.tryAcquire(req.getDeviceId(), req.getEvents().size())) {
            return Result.success();  // 静默丢弃，不报错（埋点不应影响客户端）
        }

        List<TrackEvent> valid = new ArrayList<>();
        for (TrackEvent e : req.getEvents()) {
            // 2. 幂等去重（5 分钟窗口）
            Boolean first = redis.opsForValue()
                .setIfAbsent("ml:track:dedup:" + e.getEventId(), "1", Duration.ofMinutes(5));
            if (Boolean.FALSE.equals(first)) continue;

            // 3. 补全服务端属性
            e.setServerTime(System.currentTimeMillis());
            e.setIp(IpUtil.getRealIp(httpReq));
            e.setRegion(ipRegionService.lookup(e.getIp()));
            e.setTraceId(MDC.get("traceId"));

            // 4. 基础校验（事件名格式）
            if (!EventNameValidator.isValid(e.getEvent())) {
                kafkaTemplate.send("ml_track_dirty", JSON.toJSONString(e));
                continue;
            }
            valid.add(e);
        }

        // 5. 批量发 Kafka（key = userId 保证同用户有序）
        for (TrackEvent e : valid) {
            kafkaTemplate.send("ml_track_event", String.valueOf(e.getUserIdSafe()),
                JSON.toJSONString(e));
        }
        return Result.success();
    }
}
```

**业务规则**：

- `BR-26-015`：**采集网关不阻断客户端**（任何异常都返回 success，埋点失败不能影响业务体验）。
- `BR-26-016`：**埋点写入 MQ 必须异步**（不等待 Kafka ack 返回客户端）。
- `BR-26-017`：**分区键 = userId**（保证同一用户事件有序）；游客用 deviceId。
- `BR-26-018`：**幂等去重 5 分钟**（Redis `SETNX`）。
- `BR-26-019`：**脏数据隔离**（格式错误进 `ml_track_dirty` 主题，不污染主链路）。
- `BR-26-020`：**Kafka 必须配置**：`acks=1`（埋点可容忍极小丢失，性能优先）、`retries=3`、`compression.type=lz4`。
- `BR-26-021`：**数据保留**：Kafka 埋点 topic 保留 **7 天**（足够离线消费 + 回溯）。
- `BR-26-022`：**两次消费**：实时链路与离线链路**独立消费组**（互不影响，可分别重置 offset）。
- `BR-26-023`：**埋点数据必须落 ODS**（长期保留，用于回溯与重算），ODS 按天分区，保留 **2 年**。
- `BR-26-024`：**降级**：Kafka 不可用时，网关**写本地磁盘缓冲**（滚动文件，最多 10GB），恢复后补发。
- `BR-26-025`：**网关必须水平扩展**（无状态）。
- `BR-26-026`：**采集链路必须监控**：上报 QPS、Kafka 积压、消费延迟、脏数据量。

**异常情况**：

| 编号 | 场景 | 处理 |
|---|---|---|
| `EX-26-002-1` | Kafka 不可用 | 本地磁盘缓冲 + 告警，恢复后补发 |
| `EX-26-002-2` | Kafka 积压 | 扩容消费者 + 告警 |
| `EX-26-002-3` | 消费延迟 > 5 分钟 | 告警 |
| `EX-26-002-4` | 脏数据激增 | 告警（可能是埋点 bug） |
| `EX-26-002-5` | 单设备埋点风暴 | 网关限流丢弃 |
| `EX-26-002-6` | ODS 写入失败 | 重试 + 告警，Kafka 保留期内可重放 |
| `EX-26-002-7` | 磁盘缓冲满 | 丢弃最旧数据，告警 |

**验收标准**：

- `AC-26-002-1`：埋点经网关写入 Kafka
- `AC-26-002-2`：埋点不阻塞客户端
- `AC-26-002-3`：幂等去重生效
- `AC-26-002-4`：脏数据隔离
- `AC-26-002-5`：实时与离线独立消费
- `AC-26-002-6`：ODS 数据保留 2 年
- `AC-26-002-7`：Kafka 故障时磁盘缓冲
- `AC-26-002-8`：采集链路监控完整
- `AC-26-002-9`：埋点端到端延迟 ≤ 1 分钟

## 5. 指标体系

### FR-26-003 核心指标体系 【P0】

| 项 | 内容 |
|---|---|
| **功能目标** | 定义唯一口径的、分层的指标体系 |
| **使用角色** | 全部数据使用方 |

**指标分层（AARRR + 业务专项）**：

```
【北极星指标】DAU-Play（日有效播放用户数）
  定义：当日有效播放（播放 ≥ 30s 或完成度 ≥ 60%）≥ 3 首的用户数

【一级指标】
  1. 用户规模：DAU / MAU / 新增用户 / 活跃用户
  2. 内容消费：播放次数 / 播放时长 / 人均播放 / 有效播放率
  3. 留存：次留 / 7 留 / 30 留
  4. 收入：（本期无付费）
  5. 内容生态：曲库规模 / 新增歌曲 / 内容生产
  6. 社交互动：互动次数 / 互动用户数

【二级指标】（下钻与解释）
  按渠道、设备、地区、新老用户、场景等维度拆分

【三级指标】（业务专项）
  推荐、搜索、房间、社交、AI 各自的专项指标
```

**指标定义（关键指标口径）**：

| 指标 | 口径定义 | 去重规则 | 数据源 |
|---|---|---|---|
| **DAU** | 当日有任意有效埋点的登录用户数 | 按 userId | 埋点 |
| **DAU-Play（北极星）** | 当日有效播放 ≥ 3 首的用户数 | 按 userId | 播放埋点 |
| **有效播放** | 单次播放：时长 ≥ 30s **或** 完成度 ≥ 60% | — | 播放埋点 |
| **新增用户** | 首次注册（`user_id` 首次出现） | 按 userId | 用户表 |
| **次日留存** | D 日新增用户中，D+1 日有有效播放的比例 | 按 userId | 埋点 |
| **人均播放次数** | 总播放次数 / DAU | — | 播放埋点 |
| **人均播放时长** | 总播放时长 / DAU（分钟） | — | 播放埋点 |
| **播放完成率** | 完成播放（完成度 ≥ 90%）次数 / 总播放次数 | — | 播放埋点 |
| **曲库有效播放率** | 当日被有效播放过的歌曲数 / 曲库总数 | — | 播放埋点 + 曲库 |
| **推荐 CTR** | 推荐曝光后点击的比例 | 曝光按 (userId, songId, 位置) 去重 | 推荐埋点 |
| **搜索成功率** | 有结果点击的搜索次数 / 总搜索次数 | — | 搜索埋点 |
| **房间活跃用户** | 当日进入过任意音乐房的用户数 | 按 userId | 房间埋点 |
| **互动用户数** | 当日有点赞/评论/关注/发动态的用户 | 按 userId | 社交埋点 |
| **内容生产量** | 当日动态发布数 + 评论数 + 歌单创建数 | — | 业务库 |
| **AI 成本** | 当日 AI 调用成本（元） | — | AI 日志 |
| **服务器成本** | 当日云资源成本（元） | — | 云监控 |

**指标卡片（Metric Card）规范**：

```
指标名：DAU-Play（日有效播放用户数）
指标 ID：metric_dau_play
口径：当日有效播放（≥30s 或完成度≥60%）≥3 首的用户数
计算：COUNT(DISTINCT user_id) FROM dws_play_daily WHERE valid_play_cnt >= 3
维度：日期、渠道、设备、新老用户、地区
更新频率：T+1（次日 06:00）
数据源：dws_play_daily
```

### FR-26-006 漏斗分析 【P1】

**核心漏斗**：

| 漏斗 | 步骤 |
|---|---|
| **新用户激活漏斗** | 打开首页 → 播放第一首歌 → 播放 ≥ 3 首（有效） → 次日回访 |
| **注册漏斗** | 访问 → 点击注册 → 填写信息 → 完成注册 → 首次播放 |
| **搜索漏斗** | 点击搜索 → 输入 → 提交 → 有结果 → 点击结果 → 播放 |
| **房间漏斗** | 看到房间入口 → 进入房间 → 停留 > 1 分钟 → 互动（点歌/弹幕/礼物）→ 再次进入 |
| **社交漏斗** | 浏览动态 → 点赞/评论 → 关注 → 发布动态 |
| **AI 搜索漏斗** | 输入自然语言 → AI 解析成功 → 有结果 → 播放 |
| **歌单漏斗** | 浏览歌单 → 播放 → 收藏歌单 → 自己创建歌单 |

**漏斗计算（支持任意步骤组合）**：

```sql
-- 新用户激活漏斗（ClickHouse）
SELECT
  step,
  COUNT(DISTINCT user_id) AS users,
  COUNT(DISTINCT user_id) / first_step_users AS conversion_rate,
  COUNT(DISTINCT user_id) / lag_users AS step_rate
FROM (
  SELECT 1 AS step, user_id FROM events WHERE event = 'page_view' AND page_id = 'home' AND dt = '2026-10-12' AND is_new_user = 1
  UNION ALL
  SELECT 2, user_id FROM events WHERE event = 'player_song_play' AND dt = '2026-10-12' AND is_new_user = 1
  UNION ALL
  SELECT 3, user_id FROM dws_play_daily WHERE valid_play_cnt >= 3 AND dt = '2026-10-12' AND is_new_user = 1
  UNION ALL
  SELECT 4, user_id FROM events WHERE event = 'page_view' AND dt = '2026-10-13' AND user_id IN (SELECT user_id FROM new_users_20261012)
) GROUP BY step ORDER BY step;
```

**漏斗归因窗口**：

| 漏斗 | 归因窗口 |
|---|---|
| 新用户激活 | 首日起 7 天 |
| 注册漏斗 | 同一会话（30 分钟） |
| 搜索漏斗 | 同一会话 |
| 房间漏斗 | 首日起 7 天 |
| 社交漏斗 | 首日起 30 天 |

**业务规则**：

- `BR-26-059`：**漏斗步骤必须有序且时间递增**（步骤 N 的事件必须晚于步骤 N-1）。
- `BR-26-060`：**归因窗口明确**（超出窗口不计入）。
- `BR-26-061`：**漏斗支持任意步骤组合**（自助配置）。
- `BR-26-062`：**漏斗支持分维度**（渠道、设备、新老用户、地区）。
- `BR-26-063`：**漏斗展示每步转化率与整体转化率**。
- `BR-26-064`：**流失分析**：展示每步流失人数与流失率，流失最大的步骤高亮。
- `BR-26-065`：**漏斗结果必须可下钻**到用户明细（有权限者）。
- `BR-26-066`：**漏斗计算使用 ClickHouse**（大表 JOIN 性能）。

**验收标准**：

**分层架构**：

```
ODS（原始数据层）

  - 埋点：ods_track_event_di（Kafka → Hive/OSS）
  - 业务库：ods_user_di, ods_song_di, ods_order_di（每日全量/增量同步）

  - dwd_user_action_di（用户行为明细）
  - dwd_room_detail_di（房间明细）
  - 按天分区，保留 2 年

   ↓

DWS（汇总数据层）
  - 按主题汇总，轻度聚合
  - dws_user_daily（用户日汇总：播放数、时长、互动数）

ADS（应用数据层）
  - 直接服务报表与看板
  - ads_daily_metrics（日指标总览）
  - ads_funnel_activation（激活漏斗）
  - ads_retention_daily（留存表）
  - ads_recommend_metrics（推荐指标）
  - 按天分区，保留 1 年
```

**分区与存储**：

| 层 | 分区 | 存储格式 | 保留 |
|---|---|---|---|
| ODS | `dt=yyyy-MM-dd` | Parquet | 2 年 |

```
  05:00  ADS 加工

  - 任务失败自动重试 3 次（间隔 5 分钟）
```

### FR-26-011 数据质量与对账 【P1】

| 项 | 内容 |
|---|---|
| **功能目标** | 保证数据准确可信，及时发现数据问题 |
| **使用角色** | 数据开发、产品 |

**质量校验维度**：

| 维度 | 校验项 | 示例 |
|---|---|---|
| **完整性** | 行数不为 0，分区存在 | `ods_track_event` 当日行数 > 0 |
| **唯一性** | 主键唯一 | `event_id` 无重复 |
| **有效性** | 值域、格式、枚举 | `play_duration >= 0`、`platform IN ('web')` |
| **一致性** | 跨表一致 | DAU（埋点）vs 活跃用户（业务库）偏差 < 5% |
| **及时性** | 数据产出时间 | T+1 报表 07:00 前产出 |
| **准确性** | 与业务对账 | 播放次数（数仓）vs 播放日志（Redis 计数） |
| **波动性** | 环比波动 | 指标环比波动 > 30% 告警 |

**对账清单**：

| 对账项 | 数仓侧 | 业务侧 | 允许偏差 |
|---|---|---|---|
| 新增用户 | `ads_daily_metrics.new_user_cnt` | `t_user` 当日注册数 | 0（应完全一致） |
| 播放次数 | `dws_song_daily.total_play` | Redis 播放计数 | ≤ 1% |
| 歌曲收藏数 | `dws_song_daily.collect_cnt` | `t_like` 收藏数 | ≤ 1% |
| 动态数 | `dws_user_daily.post_cnt` | `t_user_post` 当日数 | 0 |
| AI 成本 | `ads_ai_cost` | `t_ai_call_log` 汇总 | 0 |
| 房间时长 | `dws_room_daily.duration` | 房间埋点汇总 | ≤ 2% |

**数据质量监控**：

```yaml
data_quality_rules:
  - table: dwd_play_detail_di
    partition: dt
    rules:
      - type: row_count
        expr: "row_count > 0"
        severity: critical
      - type: null_rate
        column: user_id
        expr: "< 0.01"
        severity: critical
      - type: value_range
        column: play_duration
        expr: ">= 0 AND <= 86400"
        severity: warning
      - type: duplicate
        column: [event_id]
        expr: "= 0"
        severity: critical
      - type: anomaly
        column: row_count
        expr: "abs(row_count - avg_7d) / avg_7d < 0.3"
        severity: warning
```

**业务规则**：

- `BR-26-101`：**必须有质量规则**（每张核心表至少 3 条规则）。
- `BR-26-102`：**质量失败必须阻断下游**（critical 级别），不能输出错误数据。
- `BR-26-103`：**必须每日对账**（数仓 vs 业务库）。
- `BR-26-104`：**对账偏差超阈值必须告警 + 排查**（不允许"忽略"）。
- `BR-26-105`：**异常波动自动检测**（环比 > 30% 告警）。
- `BR-26-106`：**数据问题必须有处理记录**（问题、原因、修复、影响范围）。
- `BR-26-107`：**埋点变更必须通知数据团队**（避免口径断裂）。
- `BR-26-108`：**数据质量日报**（每日质量得分 + 问题列表）。
- `BR-26-109`：**看板与报表必须标注数据健康状态**（有质量问题时提示"数据可能不准确"）。

**异常情况**：

| 编号 | 场景 | 处理 |
|---|---|---|
| `EX-26-011-1` | 质量校验失败（critical） | 阻断下游 + 告警 + 人工介入 |
| `EX-26-011-2` | 对账偏差超标 | 告警 + 排查 + 修正 |
| `EX-26-011-3` | 指标异常波动 | 告警 + 人工确认（业务变化 or 数据问题） |
| `EX-26-011-4` | 上游任务失败 | 下游阻断，重跑上游后自动恢复 |
| `EX-26-011-5` | 埋点口径变更未通知 | 数据质量告警（突降/突升） |

**验收标准**：

- `AC-26-011-1`：核心表有质量规则

```sql
    properties      String,          -- JSON（业务属性）

ENGINE = MergeTree()
PARTITION BY dt
ORDER BY (event, server_time, user_id)
TTL dt + INTERVAL 180 DAY
SETTINGS index_granularity = 8192;
```

**物化视图（实时聚合）**：

```sql
-- 实时播放量（分钟级）
CREATE MATERIALIZED VIEW ml.mv_play_realtime
ENGINE = SummingMergeTree()
PARTITION BY toYYYYMMDD(minute)
ORDER BY (minute, song_id)
AS SELECT
    toStartOfMinute(server_time) AS minute,
    song_id,
    count() AS play_cnt,
    sum(if(is_valid_play = 1, 1, 0)) AS valid_play_cnt
FROM ml.ck_play_detail
GROUP BY minute, song_id;
```

**业务规则**：

- `BR-26-110`：**ClickHouse 表必须用 MergeTree 家族引擎**（MergeTree / SummingMergeTree / ReplacingMergeTree）。
- `BR-26-111`：**必须设 TTL**（明细 180-365 天，汇总表可更长）。
- `BR-26-112`：**排序键必须匹配主要查询模式**（如按 dt + song_id 查歌曲日报）。
- `BR-26-113`：**低基数字段用 LowCardinality**（节省空间，提升性能）。
- `BR-26-114`：**避免高基数的 JOIN**（ClickHouse JOIN 性能差），推荐用宽表。
- `BR-26-115`：**必须用分区裁剪**（查询必须带 `dt` 条件）。
- `BR-26-116`：**实时物化视图用于实时指标**，避免全表扫描。
- `BR-26-117`：**批量写入**（每批 ≥ 1000 行），避免小批量写入造成 too many parts。

## 12. 降级策略

| 依赖 | 故障 | 降级 |
|---|---|---|
| 埋点上报接口 | 不可用 | 客户端本地缓存，恢复后重传 |
| Kafka | 不可用 | 网关磁盘缓冲，恢复后补发 |
| 实时计算 | 延迟 | 看板显示延迟提示，用离线数据兜底 |
| Redis（实时指标） | 不可用 | 看板用 ClickHouse 实时表（延迟略高） |
| ClickHouse | 不可用 | 看板与报表降级到预计算快照（T-1 数据） |
| 数仓任务 | 失败 | 报表展示 T-2 数据 + 明确提示；重跑后更新 |
| 画像服务 | 不可用 | 推荐用离线兜底特征（见 [24 章](./24-模块15-推荐升级.md)） |
| 报表分发 | 失败 | 重试 3 次 + 站内可查 |
| 数据质量校验 | 失败 | 阻断下游，展示上次有效数据并标注 |
