## 1. 角色模型总览

本平台存在**两套角色体系**，必须严格区分：

| 体系 | 作用域 | 存储 | 角色 |
|---|---|---|---|
| **全局角色（Global Role）** | 全平台 | `t_user_role` + `t_role` | 游客、普通用户、平台管理员、超级管理员、运营人员 |
| **房间角色（Room Role）** | 单个音乐房内 | `t_room_member.room_role` | 房主、房管、普通成员、黑名单 |

> **关键规则**：房间角色**不继承**全局角色；全局角色的管理权限**不可**在房间内生效（平台管理员进入房间默认是普通成员，除非房主授予房管）。反之，房主在房间内的权限不外溢到平台其他房间。

### 1.1 角色定义

| 编号 | 角色 | 标识 | 说明 | 典型行为 |
|---|---|---|---|---|
| R-01 | **游客** | `GUEST` | 未登录访客，仅有匿名会话标识（`guestId`） | 浏览、搜索、30s 试听、看公开歌单/房间 |
| R-02 | **普通用户** | `USER` | 已注册登录用户 | 全量听歌、评论、收藏、歌单、进房、社交、AI 能力 |
| R-03 | **音乐房房主** | `ROOM_OWNER` | 房间创建者（房间内角色） | 控播、踢人、禁言、排麦管理、设房管、转让、解散 |
| R-04 | **音乐房管理员** | `ROOM_ADMIN` | 房主指派的房间管理员（房间内角色） | 禁言、踢人、排麦管理、公告（不可解散/转让） |
| R-05 | **平台管理员** | `ADMIN` | 后台运营管理岗 | 用户/内容/审核/举报/推荐配置/看板 |
| R-06 | **超级管理员** | `SUPER_ADMIN` | 系统最高权限 | 权限分配、系统配置、敏感操作审批、AB 配置 |
| R-07 | **运营人员** | `OPERATOR` | 内容与活动运营岗 | 推荐位、运营报表、用户画像、活动歌单、内容审核 |

### 1.2 角色继承与互斥

```
SUPER_ADMIN ──包含──> ADMIN ──包含──> OPERATOR（部分能力）
     │
     └── 独占：权限分配、系统配置、敏感操作审批、AB 实验配置

USER ──(在房间内)──> ROOM_OWNER / ROOM_ADMIN / MEMBER / BLACKLIST（四选一）
```

**互斥约束（BR-02-001 ~ BR-02-005）**：

- `BR-02-001`：一个用户在**同一房间**内只能有一个房间角色。
- `BR-02-002`：房主**不可**被踢出、不可被禁言、不可被降级（须先转让）。
- `BR-02-003`：房管不可设置/撤销其他房管，不可转让房主，不可解散房间。
- `BR-02-004`：被拉入黑名单的用户不可再加入该房间（除非移除黑名单）。
- `BR-02-005`：平台管理员/超管的全局权限**不自动**作用于房间；但超管可通过后台"强制解散房间"（记敏感操作日志 + 二次审批）。

## 2. RBAC 数据模型

### 2.1 模型结构

```
t_user ──(1:N)── t_user_role ──(N:1)── t_role ──(1:N)── t_role_permission ──(N:1)── t_permission
   │
   └──(1:N)── t_room_member ──(room_role)── 房间内角色
```

### 2.2 表结构摘要

| 表 | 关键字段 | 说明 |
|---|---|---|
| `t_user` | `id, username, phone, email, password, nickname, avatar, status, user_type` | `user_type`：1=普通用户 2=运营 3=管理员 4=超管 |
| `t_role` | `id, role_code, role_name, description, status` | 角色字典，**固定不可删除**，仅可修改权限 |
| `t_permission` | `id, perm_code, perm_name, perm_type(MENU/BUTTON/API), parent_id, path` | 权限点，树形 |
| `t_user_role` | `id, user_id, role_id, create_time` | 用户-角色关联 |
| `t_role_permission` | `id, role_id, perm_id` | 角色-权限关联 |
| `t_room_member` | `id, room_id, user_id, room_role(0成员/1房管/2房主/9黑名单), mic_status, join_time` | 房间成员与角色 |

### 2.3 内置角色初始化数据

| role_code | role_name | 说明 |
|---|---|---|
| `ROLE_USER` | 普通用户 | 注册后默认授予 |
| `ROLE_OPERATOR` | 运营人员 | 后台配置 |
| `ROLE_ADMIN` | 平台管理员 | 后台配置 |
| `ROLE_SUPER_ADMIN` | 超级管理员 | 仅初始化脚本创建，不可自助授予 |

### 2.4 权限点编码规范

```
{模块}:{资源}:{动作}
```

示例：`music:song:create`、`music:song:audit`、`social:comment:delete`、`system:config:update`、`room:room:forceClose`

- 通配：`music:song:*` 表示该资源全部动作；`*:*:*` 仅超管拥有。
- 前端按钮级控制：接口返回的权限码集合驱动菜单/按钮显隐（**仅作展示控制，服务端必须二次校验**）。

## 5. 关键权限规则（业务规则 BR）

### 5.1 全局规则

| 编号 | 规则 |
|---|---|
| `BR-02-010` | 所有写操作必须校验登录态；未登录返回 `40101`。 |
| `BR-02-011` | 所有后台接口必须校验权限码；无权限返回 `40301`。 |
| `BR-02-012` | 封禁用户的**所有** access token 立即失效（Redis 黑名单 + 用户状态校验）。 |
| `BR-02-013` | 敏感操作（强制解散房间、删除用户、修改系统配置、授予超管）需**二次确认 + 审批工单**。 |
| `BR-02-014` | 权限变更后，用户权限缓存（Redis）须在 60s 内失效（主动删除 + 兜底 TTL）。 |
| `BR-02-015` | 运营人员不可执行删除类操作（除评论/动态的软删除，保留可恢复）。 |

### 5.2 房间内规则

| 编号 | 规则 |
|---|---|
| `BR-02-020` | 房主不可被禁言/踢出/降级（先转让）。 |
| `BR-02-021` | 房管可被房主禁言/撤销；房管之间的禁言操作**互斥**（房管 A 不能禁言房管 B）。 |
| `BR-02-022` | 单个房间房管数量上限 10 人。 |
| `BR-02-023` | 黑名单上限 200 人/房。 |
| `BR-02-024` | 禁言时长可选：5 分钟 / 30 分钟 / 1 小时 / 24 小时 / 永久（永久仅房主可设）。 |
| `BR-02-025` | 房间解散后，成员关系、麦位、队列全部清理，房间标记 `status=3(已解散)`，30 天后物理归档。 |

## 6. 鉴权流程

### 6.1 登录鉴权时序

```
Client                       Gateway/Filter            AuthService              Redis/MySQL
  │                               │                        │                        │
  ├─ POST /api/v1/auth/login ────>│                        │                        │
  │   {account, password}         ├─ 校验账号密码 ────────>│                        │
  │                               │                        ├─ 查询用户 ────────────>│
  │                               │                        ├─ BCrypt 校验          │
  │                               │                        ├─ 生成 AccessToken(2h) │
  │                               │                        ├─ 生成 RefreshToken(7d)│
  │                               │                        ├─ 写会话缓存 ──────────>│ ml:auth:session:{userId}
  │<── {accessToken, refreshToken, userInfo, perms} ───────┤                        │
  │                                                        │                        │
  ├─ GET /api/v1/music/songs ────>│                        │                        │
  │   Authorization: Bearer xxx   ├─ JWT 解析校验 ────────>│                        │
  │                               ├─ 检查黑名单 ──────────────────────────────────>│ ml:auth:blacklist:{jti}
  │                               ├─ 加载权限 ────────────────────────────────────>│ ml:auth:perms:{userId}
  │<── 200 OK ────────────────────┤                        │                        │
```

### 6.2 Token 策略

| 项 | 值 | 说明 |
|---|---|---|
| 签名算法 | **RS256**（非对称） | 私钥签发、公钥验签，便于多服务验证 |
| AccessToken 有效期 | 2 小时 | 携带 `userId, jti, roles, exp, iat` |
| RefreshToken 有效期 | 7 天 | 存 Redis，**一次性使用**（用完即换新，防重放） |
| Token 刷新 | access 剩余 < 30min 时前端自动刷新 | 静默刷新，失败则跳登录 |
| 登出 | access 入黑名单（TTL=剩余有效期）、refresh 删除 | 黑名单 key：`ml:auth:blacklist:{jti}` |
| 多端登录 | 允许，最多 5 个活跃 refresh token | 超出则踢掉最早的 |
| 封禁 | 用户状态变更 → 删除全部会话 + 用户级黑名单 | 写 `ml:auth:userban:{userId}` TTL=7d |

### 6.3 权限加载与缓存

```
用户请求 → JWT 解析得到 userId
        → 查 Redis ml:auth:perms:{userId}
          ├─ 命中 → 直接使用
          └─ 未命中 → 查库（user→role→perm）→ 写 Redis（TTL 30min）→ 使用
        → @PreAuthorize("hasAuthority('music:song:create')") 校验
```

**性能设计**：权限集合以 `Set<String>` 存 Redis，单用户权限点数量预计 < 200，单次读取 < 1ms。

## 7. 用户状态机

### 7.1 账号状态

```
                    ┌──────────────┐
   注册 ──────────> │   NORMAL     │ <──── 解封
                    │  (状态=1)    │
                    └──────┬───────┘
                           │ 违规/举报成立
                           ▼
                    ┌──────────────┐
                    │   BANNED     │ 封禁时长：7d/30d/永久
                    │  (状态=2)    │ 永久封禁需超管审批(BR-02-013)
                    └──────┬───────┘
                           │ 到期自动解封（定时任务）
                           ▼
                    ┌──────────────┐
                    │   NORMAL     │
                    └──────────────┘

    用户申请注销 ──> ┌──────────────┐  7天冷静期 ──> ┌──────────────┐
                    │  DELETING    │                │   DELETED    │
                    │  (状态=3)    │ <── 撤回 ────── │  (状态=4)    │
                    └──────────────┘                └──────────────┘
                                                    （数据脱敏保留）
```

| 状态值 | 名称 | 可登录 | 可见性 | 说明 |
|---|---|---|---|---|
| 0 | 待验证 | ❌ | — | 注册未验证手机/邮箱 |
| 1 | 正常 | ✅ | 全部 | — |
| 2 | 封禁 | ❌ | 主页不可见 | 记录封禁原因、时长、操作人 |
| 3 | 注销中 | ✅（可撤回） | 内容隐藏 | 7 天冷静期 |
| 4 | 已注销 | ❌ | 不可见 | 手机号/邮箱脱敏，内容保留但作者显示"已注销用户" |

### 7.2 房间成员状态

| 状态 | 说明 | 可否发言 | 可否上麦 |
|---|---|---|---|
| 在房（在线） | 已连接 WebSocket 且在房 | ✅ | ✅（未禁言时） |
| 离开（离线） | 已退出或断连超时 | ❌ | ❌ |
| 禁言中 | 在房但被禁言 | ❌ | ❌ |
| 黑名单 | 被拉黑，禁止入房 | ❌ | ❌ |

## 8. 验收标准（权限相关）

| 编号 | 验收标准 | 优先级 |
|---|---|---|
| `AC-02-001` | 未登录用户调用任意写接口，返回 `40101` 且不产生副作用 | P0 |
| `AC-02-002` | 普通用户调用后台接口，返回 `40301` | P0 |
| `AC-02-003` | 房主被房管禁言时返回 `40302`（无权限操作房主） | P0 |
| `AC-02-004` | 封禁用户 1 秒内所有接口返回 `40102`（账号已封禁） | P0 |
| `AC-02-005` | 超管修改用户角色后，该用户 60s 内权限生效 | P0 |
| `AC-02-006` | 强制解散房间无审批工单时返回 `40303` | P1 |
| `AC-02-007` | 黑名单用户尝试入房返回 `40304` | P1 |
| `AC-02-008` | 同账号第 6 次登录时，最早的会话被踢下线 | P2 |
