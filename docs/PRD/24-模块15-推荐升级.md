### FR-24-001 统一召回接口 【P0】

| 项 | 内容 |
|---|---|
| **功能目标** | 所有召回源统一接口、统一输出格式、统一错误处理，支持并行与可插拔 |
| **使用角色** | 系统内部 |

**接口定义**：

```java
public interface RecallSource {

    /** 召回源名称（唯一，用于配置与埋点） */
    String name();

    /** 是否需要用户上下文（无用户时可跳过） */
    default boolean requiresUser() { return true; }

    /** 是否启用（读配置） */
    default boolean enabled(RecallContext ctx) { return true; }

    /** 召回 */
    RecallResult recall(RecallContext ctx);

    /** 超时时间（毫秒），超时则跳过该源 */
    default int timeoutMs() { return 100; }

    /** 该源的优先级（用于结果融合时排序，越大越优先） */
    default int priority() { return 0; }
}

@Data
public class RecallContext {
    private Long userId;              // 可能为 null（游客）
    private String scene;             // HOME_FEED / DAILY / RADIO / SIMILAR / PLAYLIST
    private Long seedSongId;          // 种子歌曲（相似推荐）
    private Long seedPlaylistId;      // 种子歌单
    private Integer limit;            // 各源召回数量
    private String experimentBucket;  // 实验分组
    private Map<String, Object> features; // 实时上下文（时段、设备、网络）
    private Set<Long> excludeIds;     // 需排除的歌曲（已播、不喜欢）
    private Set<Long> excludeArtists; // 需排除的歌手
    private long deadlineMs;          // 全局截止时间（从入口计算）
}

@Data
public class RecallResult {
    private String source;            // 召回源名
    private List<RecallItem> items;
    private long costMs;
    private boolean success;
    private String errorMsg;
}

@Data
public class RecallItem {
    private Long songId;
    private Double score;             // 该源内的原始分数（各源量纲不同，融合时归一化）
    private Map<String, Object> extra; // 附加信息（如向量相似度、来源标签）
}
```

**召回执行流程**：

```
RecommendEngine.recommend(ctx)
   ↓
[1] 解析场景配置：该场景启用哪些召回源、各源数量、权重
   ↓
[2] 排除集准备：已播放（24h）、不喜欢、屏蔽歌手、下架
   ↓
[3] 并行调用所有启用源
     - 线程池（每个源独立线程，超时中断）
     - 单个源超时/失败 → 跳过，不影响其他
     - 全局 deadline 保护（如 150ms）
   ↓
[4] 收集结果，记录各源耗时与数量（埋点）
   ↓
[5] 归一化：各源分数归一化到 [0,1]（min-max 或 rank-based）
   ↓
[6] 融合（见 FR-24-002）
   ↓
[7] 输出候选集（如 500 首）
```

**并行执行实现要点**：

```java
// 使用 CompletableFuture + 独立线程池，超时隔离
private List<RecallResult> executeParallel(RecallContext ctx, List<RecallSource> sources) {
    List<CompletableFuture<RecallResult>> futures = sources.stream()
        .map(source -> CompletableFuture
            .supplyAsync(() -> safeRecall(source, ctx), recallExecutor)
            .orTimeout(source.timeoutMs(), TimeUnit.MILLISECONDS)
            .exceptionally(ex -> RecallResult.failed(source.name(), ex))
        )
        .collect(Collectors.toList());

    // 全局 deadline 等待
    long remaining = ctx.getDeadlineMs() - System.currentTimeMillis();
    try {
        CompletableFuture.allOf(futures.toArray(new CompletableFuture[0]))
            .get(Math.max(remaining, 0), TimeUnit.MILLISECONDS);
    } catch (TimeoutException | InterruptedException e) {
        log.warn("Recall global deadline exceeded");
    }
    return futures.stream()
        .filter(f -> f.isDone() && !f.isCompletedExceptionally())
        .map(CompletableFuture::join)
        .collect(Collectors.toList());
}
```

> **关键**：`recallExecutor` 必须**独立线程池**（核心 32 / 最大 64 / 队列 0 / `CallerRunsPolicy` 或直接拒绝），**不与业务线程池共用**，避免推荐雪崩拖垮全站。

**业务规则**：

- `BR-24-001`：**所有召回源必须**实现 `RecallSource` 接口，**禁止**在引擎中硬编码召回逻辑。
- `BR-24-002`：**单源超时必须被隔离**，超时源的线程必须被中断或放弃（不阻塞主流程）。
- `BR-24-003`：**全局 deadline**：整个召回阶段 ≤ 150ms，超时则用已完成的源继续。
- `BR-24-004`：**至少 1 个源成功**才继续；全部失败则降级到热门榜。
- `BR-24-005`：**召回源启用/权重可配置**（`t_rec_config`，热更新，见 [05 章 配置规范](./05-通用设计规范.md)）。
- `BR-24-006`：**排除集必须全局应用**（在融合前，不在各源内重复做）。
  - **例外**：`editor`（运营源）**不受排除集限制**（运营可强推），但仍在最终阶段过滤下架歌曲。
- `BR-24-007`：**召回量**：各源召回量之和应 ≥ 目标的 3-5 倍（如最终要 100 首，召回 300-500 首）。
- `BR-24-008`：**各源耗时必须埋点**（用于发现慢源）。
- `BR-24-009`：**游客**（无 userId）时，跳过 `requiresUser = true` 的源。
- `BR-24-010`：**冷启动用户**时，`cf_*` 源返回空（无行为数据），靠 `hot`/`tag_match`/`new_song`/`long_tail` 兜底。
- `BR-24-011`：**召回源必须有兜底**：任一源返回空不能导致整体失败。
- `BR-24-012`：**幂等**：同一请求并发执行无副作用（召回只读）。
- `BR-24-013`：**线程池隔离**：召回线程池、排序线程池、特征线程池**分别独立**。
- `BR-24-014`：**禁止在召回阶段做 N+1 查询**（如逐首查歌曲详情），召回只返回 ID + 分数，详情在最终阶段批量查。

**异常情况**：

| 编号 | 场景 | 处理 |
|---|---|---|
| `EX-24-001-1` | 单源超时 | 跳过，记录埋点，告警（连续超时） |
| `EX-24-001-2` | 全部源失败 | 降级到热门榜（Redis 缓存） |
| `EX-24-001-3` | 全局 deadline 超时 | 用已完成结果继续 |
| `EX-24-001-4` | 线程池打满 | 拒绝新任务（`AbortPolicy`），该源视为失败 |
| `EX-24-001-5` | 候选集为空 | 降级到热门榜 |
| `EX-24-001-6` | 配置读取失败 | 使用**内置默认配置**（硬编码兜底） |
| `EX-24-001-7` | 向量库不可用 | `vector*` 源失败，其他源继续 |
| `EX-24-001-8` | 候选集过小（< 20） | 用热门榜补齐 |

**验收标准**：

- `AC-24-001-1`：15 个召回源可独立启用/禁用
- `AC-24-001-2`：单源超时不影响其他源
- `AC-24-001-3`：全局 deadline 生效
- `AC-24-001-4`：全部失败时降级到热门榜
- `AC-24-001-5`：排除集全局生效
- `AC-24-001-6`：各源耗时埋点完整
- `AC-24-001-7`：游客与冷启动用户有结果
- `AC-24-001-8`：线程池隔离，无跨业务影响
- `AC-24-001-9`：召回阶段 P99 ≤ 150ms

### FR-24-002 多路召回融合 【P0】

| 项 | 内容 |
|---|---|
| **功能目标** | 将各源结果融合为统一候选集，兼顾准确性与多样性 |
| **使用角色** | 系统内部 |

**融合算法：加权排名融合（Weighted Rank Fusion, WRF）**

```
对于歌曲 i：
  fused_score(i) = Σ_src [ w_src × norm_score_src(i) × decay_src(i) ]

其中：
  w_src        = 该源的权重（配置可调）
  norm_score   = 归一化分数
  decay_src(i) = 位置衰减（排名越靠后衰减越大）
```

**归一化方式（可配置）**：

| 方式 | 公式 | 适用 |
|---|---|---|
| `MIN_MAX` | `(s - min) / (max - min)` | 分数分布均匀 |
| `RANK` | `1 - rank / N` | **推荐**：跨源可比性好，对异常值鲁棒 |
| `Z_SCORE` | `(s - μ) / σ` | 分数近似正态 |
| `SOFTMAX` | `e^s / Σe^s` | 需要概率interpretation |

**默认采用 `RANK` 归一化**，因为各源分数**量纲完全不同**（热度是播放次数，向量是余弦相似度 0-1，ItemCF 是共现次数），rank 归一化天然消除量纲差异。

**权重配置示例（`t_rec_config`）**：

```json
{
  "scene": "HOME_FEED",
  "fusion": {
    "normalize": "RANK",
    "sources": [
      {"name": "cf_user",        "weight": 1.2, "limit": 300, "decay": 0.98},
      {"name": "vector",         "weight": 1.0, "limit": 300, "decay": 0.98},
      {"name": "cf_item",        "weight": 0.9, "limit": 300, "decay": 0.98},
      {"name": "tag_match",      "weight": 0.8, "limit": 300, "decay": 0.95},
      {"name": "hot",            "weight": 0.6, "limit": 500, "decay": 0.90},
      {"name": "friend_listen",  "weight": 0.8, "limit": 200, "decay": 0.95},
      {"name": "follow_artist",  "weight": 0.9, "limit": 200, "decay": 0.95},
      {"name": "new_song",       "weight": 0.7, "limit": 200, "decay": 0.95},
      {"name": "long_tail",      "weight": 0.4, "limit": 200, "decay": 0.90},
      {"name": "editor",         "weight": 2.0, "limit": 50,  "decay": 1.00}

```

**去重与合并**：

```
同一首歌被多个源召回：
  - 分数累加（体现"多源共识"，这是重要信号）
  - 记录来源列表（用于解释"为什么推荐给你"）
  - 示例：
    歌曲 A：[cf_user=0.95, vector=0.88, tag_match=0.7]
    fused = 1.2×0.95 + 1.0×0.88 + 0.8×0.7 = 1.14 + 0.88 + 0.56 = 2.58
```

**多样性控制（融合阶段）**：

| 策略 | 说明 |
|---|---|
| **歌手打散** | 同歌手在 Top N 中最多 M 首（默认 M=2） |
| **专辑打散** | 同专辑最多 1 首 |
| **类别打散** | 同语言/同风格最多 40% |
| **MMR（Maximal Marginal Relevance）** | 在相关性与多样性间平衡 |

**MMR 实现（可选，用于精排后的重排）**：

```java
/**
 * MMR: 每次选择边际收益最大的候选
 * MMR(i) = λ × rel(i) - (1-λ) × max_{j∈Selected} sim(i, j)
 */
public List<Long> mmrSelect(List<Candidate> candidates, int k, double lambda) {
    List<Candidate> selected = new ArrayList<>();
    List<Candidate> pool = new ArrayList<>(candidates);

    while (selected.size() < k && !pool.isEmpty()) {
        Candidate best = null;
        double bestScore = Double.NEGATIVE_INFINITY;

        for (Candidate c : pool) {
            double maxSim = 0.0;
            for (Candidate s : selected) {
                maxSim = Math.max(maxSim, similarity(c, s)); // 向量余弦相似度
            }
            double mmr = lambda * c.getScore() - (1 - lambda) * maxSim;
            if (mmr > bestScore) {
                bestScore = mmr;
                best = c;
            }
        }
        selected.add(best);
        pool.remove(best);
    }
    return selected.stream().map(Candidate::getSongId).collect(Collectors.toList());
}
```

**`λ` 取值建议**：`0.7`（偏相关性）；探索场景（如"发现新歌"）用 `0.5`。

**业务规则**：

- `BR-24-015`：**默认 RANK 归一化**（消除量纲差异）。
- `BR-24-016`：**多源共识加分**：同一首歌被多源召回，分数累加（这是强信号）。
- `BR-24-017`：**权重可配置且热更新**。
- `BR-24-018`：**来源必须记录**（`RecallItem.extra.source`），用于推荐理由生成与效果归因。
- `BR-24-019`：**多样性约束在融合后立即执行**（歌手/专辑打散），避免多样性不足进入排序。
- `BR-24-020`：**运营源权重最高**（`editor` 权重 2.0），保证运营意图。
- `BR-24-021`：**融合必须确定性**：相同输入相同输出（分数相同时按 songId 排序，保证可复现）。
- `BR-24-022`：**融合阶段不做数据库查询**（纯内存计算）。
- `BR-24-023`：**候选集上限**：融合后保留 Top 500（超出丢弃）。
- `BR-24-024`：**长尾保护**：融合后强制保留 ≥ 10% 的长尾歌曲（`long_tail` 源）进入排序，避免马太效应。

**异常情况**：

| 编号 | 场景 | 处理 |
|---|---|---|
| `EX-24-002-1` | 配置缺失 | 使用内置默认权重 |
| `EX-24-002-2` | 全部源返回空 | 降级热门榜 |
| `EX-24-002-3` | 权重全为 0 | 视为等权重 |
| `EX-24-002-4` | 多样性约束导致候选不足 | 放宽约束（歌手上限 2→3→不限） |
| `EX-24-002-5` | 融合后 < 20 首 | 热门榜补齐 |

**验收标准**：

- `AC-24-002-1`：多源融合结果正确（单测验证加权公式）
- `AC-24-002-2`：多源共识加分生效
- `AC-24-002-3`：权重热更新生效
- `AC-24-002-4`：多样性约束生效（同歌手 ≤ 2 首）
- `AC-24-002-5`：长尾占比 ≥ 10%
- `AC-24-002-6`：相同输入结果确定性
- `AC-24-002-7`：来源信息完整记录
- `AC-24-002-8`：融合阶段 P99 ≤ 20ms

## 5. 排序框架

### FR-24-003 三段式排序 【P0】

| 项 | 内容 |
|---|---|
| **功能目标** | 粗排快速收敛 → 精排模型打分 → 重排业务约束 |
| **使用角色** | 系统内部 |

**整体流程**：

```
候选集 500 首（融合后）
   ↓
【粗排 Coarse Ranking】
   目标：500 → 150，延迟 ≤ 30ms
   方式：轻量模型 / 规则（多目标线性加权）
   特征：~20 个关键特征（不含重型特征）
   ↓
【精排 Fine Ranking】
   目标：150 → 150（打分不裁剪），延迟 ≤ 80ms
   方式：GBDT / DNN 模型（或本期的线性模型，见选型）
   特征：~80 个特征（含实时特征）
   ↓
【重排 Re-ranking】
   目标：打散、去重、业务规则、探索
   延迟 ≤ 30ms
   ↓
最终 30-50 首 → 返回
```

**为什么三段式**：

| 阶段 | 目的 | 为什么不能省 |
|---|---|---|
| 粗排 | 用廉价计算快速过滤明显不相关的 | 精排模型昂贵（80 特征），500 首全量精排延迟不可接受（> 300ms） |
| 精排 | 用丰富特征精准打分 | 粗排特征少，准确性不足 |
| 重排 | 业务约束（多样性、去重、探索、运营） | 模型只优化点击率，不保证业务目标 |

**粗排模型（本期：线性加权）**：

```java
// 粗排分数 = Σ(w_i × norm(feature_i))
public double coarseScore(Candidate c, UserFeatures u) {
    return 0.30 * c.getRecallScore()          // 召回分数（已融合）
         + 0.15 * c.getHotScore()             // 热度（时间衰减）
         + 0.15 * c.getUserTagMatch()         // 用户标签匹配度
         + 0.10 * c.getArtistAffinity()       // 歌手偏好
         + 0.10 * c.getFreshness()            // 新鲜度
         + 0.08 * c.getCompletionRatePrior()  // 历史完成率先验
         + 0.07 * c.getSkipRatePrior();       // 跳过率先验（负向，实际用 1-x）
}
```

> **【假设 A-32】** 本期（V1.2）**不引入 DNN/深度模型**，精排采用**逻辑回归（LR）+ GBDT（LightGBM）**。原因：JDK 8 技术栈下 Java 侧模型推理方案有限（需引入 PMML 或通过 Python 服务），且**训练数据量不足以支撑深度模型**（需要千万级样本）。方案：
> - **方案 A（推荐）**：LightGBM 离线训练 → 导出 PMML → Java 侧用 **PMML4S/JPM4L** 加载推理。
> - **方案 B**：Python 模型服务（Flask/FastAPI）+ gRPC，Java 侧远程调用（延迟 +10-20ms）。
> - **方案 C（本期兜底）**：纯规则 + 人工调参的线性模型（无训练）。
>
> 本期实施 **方案 A**，若 PMML 加载有 JDK 8 兼容问题则退回方案 C。

**精排输出（多目标）**：

```json
{
  "songId": "1001",
  "pctr": 0.15,        // 点击率预测
  "pcvr": 0.62,        // 播放完成率预测（"转化"）
  "plike": 0.08,       // 点赞率预测
  "pskip": 0.12,       // 跳过率预测
  "finalScore": 0.87   // 融合分数
}
```

**多目标融合公式**：

```
finalScore = pctr^a × pcvr^b × (1-pskip)^c × (1+plike)^d × hotBoost

默认：a=0.5, b=0.3, c=0.15, d=0.05
（指数用于调整各目标的相对重要性，且保证量纲归一化）
```

> **为什么不简单加权**：`pctr` 范围 0-1，`pcvr` 范围 0-1，简单加权 `0.5×pctr + 0.3×pcvr` 会偏向数值大的目标；**乘法融合**（几何加权）是业界标准做法，且天然表达"多个目标都要好"。

- `BR-24-031`：**模型热加载**：模型更新不重启服务（定时检查文件变更 + 原子替换）。
- `BR-24-032`：**多目标权重可配置**（`a/b/c/d` 在 `t_rec_config`）。

### FR-24-004 重排策略 【P1】

| 项 | 内容 |
|---|---|
| **功能目标** | 在模型分数基础上施加业务约束与探索 |
| **使用角色** | 系统内部 |

**重排算子链（按顺序执行）**：

| 顺序 | 算子 | 说明 |
|---|---|---|
| 1 | **过滤** | 移除下架、无版权、当前不可播放 |
| 2 | **去重** | 移除重复歌曲、同曲不同版本 |
| 3 | **运营置顶** | 运营指定歌曲插到指定位置（见 [17 章](./17-模块08-AI推荐.md) 位置 1/8/15） |
| 4 | **歌手打散** | 同歌手 Top N 内 ≤ 2 首，用滑动窗口 |
| 5 | **专辑打散** | 同专辑 ≤ 1 首 |
| 6 | **风格/语言打散** | 同风格 ≤ 40% |
| 7 | **新人加权** | 新歌/新歌手给予曝光加成 |
| 8 | **长尾插入** | 每 10 首插入 ≥ 1 首长尾 |
| 9 | **探索插入（bandit/ε-greedy）** | 10% 位置留给探索（见 FR-24-007） |
| 10 | **多样性重排（MMR）** | 可选，强多样性场景启用 |
| 11 | **最终裁剪** | 取 Top N |

**歌手打散实现（滑动窗口）**：

```java
/**
 * 滑动窗口打散：保证任意连续 windowSize 首中，同一歌手不超过 maxCount 首
 */
public List<Candidate> diversifyByArtist(List<Candidate> ranked, int windowSize, int maxCount) {
    List<Candidate> result = new ArrayList<>();
    Map<Long, Integer> windowCount = new HashMap<>();
    Deque<Candidate> window = new ArrayDeque<>();
    List<Candidate> pending = new ArrayList<>(ranked);

    while (!pending.isEmpty()) {
        Candidate picked = null;
        for (Candidate c : pending) {
            Integer cnt = windowCount.getOrDefault(c.getArtistId(), 0);
            if (cnt < maxCount) {
                picked = c;
                break;
            }
        }
        if (picked == null) {
            // 无法满足约束，取分最高的（放宽约束）
            picked = pending.get(0);
        }

        pending.remove(picked);
        result.add(picked);

        window.addLast(picked);
        windowCount.merge(picked.getArtistId(), 1, Integer::sum);

        if (window.size() > windowSize) {
            Candidate out = window.pollFirst();
            windowCount.merge(out.getArtistId(), -1, Integer::sum);
        }
    }
    return result;
}
```

> **注意**：窗口大小应设为"用户可见的第一屏长度"（如 6-8 首），而不是整个列表。用户只会注意到首屏的重复。

**业务规则**：

- `BR-24-036`：**算子链顺序固定**（过滤 → 去重 → 置顶 → 打散 → 加权 → 探索 → 裁剪），**顺序影响结果，不得调换**。
- `BR-24-037`：**运营置顶优先级最高**（打完分后插入指定位置，覆盖原位置歌曲，被挤出的歌曲向后顺延）。
- `BR-24-038`：**置顶歌曲不参与打散约束**（运营意图优先）。
- `BR-24-039`：**打散窗口 = 首屏长度**（8 首），不是全列表。
- `BR-24-040`：**约束无法满足时放宽**（而不是返回空），放宽顺序：歌手 2→3→不限。
- `BR-24-041`：**长尾插入**：每 10 首至少 1 首长尾（曝光次数 < 1000 的歌曲）。
- `BR-24-042`：**探索插入**：10% 位置给探索内容（见 FR-24-007）。
- `BR-24-043`：**重排算子可配置**（增删与参数）。
- `BR-24-044`：**重排必须记录每一步的变化**（埋点：哪个算子改变了哪个位置），便于排查"为什么排成这样"。
- `BR-24-045`：**重排不得引入未召回歌曲**（除运营置顶，运营歌曲可不在召回集内）。

**特征一致性保障（线上线下一致）**：

| 措施 | 说明 |
|---|---|
| **同一份特征代码** | 离线（Spark 批处理）与在线（Java 服务）使用**同一份特征定义**（配置驱动），避免口径不一致 |
| **特征版本号** | 每份特征有版本号（`feat_version`），线上线下一并记录 |
| **一致性校验任务** | 每日抽样 1000 用户，对比离线特征与在线特征的值，偏差 > 5% 告警 |
| **特征回填（Backfill）** | 新特征上线时，回填历史数据供训练 |

> **特征一致性是推荐系统最经典的坑**：训练时用离线特征（T+1，全量准确），推理时用在线特征（实时，可能不准），两者分布不一致会导致**模型上线效果远低于离线评估**。本项目的对策是：**同一份特征计算代码 + 每日一致性校验**。

**业务规则**：

- `BR-24-046`：**必须批量获取特征**（Pipeline），禁止逐条调用。
- `BR-24-047`：**特征获取整体超时 ≤ 20ms**，超时则用离线特征或默认值。
- `BR-24-048`：**特征缺失必须用默认值**（每个特征定义默认值），不得报错。
- `BR-24-049`：**特征版本必须记录**，且线上线下一并校验。
- `BR-24-050`：**特征必须有 TTL**（Redis 中的特征 hash 设置过期，防止脏数据长期存在）。
  - 用户画像 TTL 25 小时（T+1 更新，留 1 小时缓冲）。
  - 歌曲统计 TTL 10 分钟（5 分钟更新，留 2 倍缓冲）。
- `BR-24-051`：**特征必须可回填**（用于新特征上线与模型重训）。
- `BR-24-052`：**实时特征更新异步**（用户播放后通过 MQ 异步更新 Redis，不阻塞播放）。
- `BR-24-053`：**特征服务不参与业务事务**（读多写少，纯缓存）。
- `BR-24-054`：**特征命名规范**：`{entity}_{scope}_{metric}`，如 `song_1h_play_cnt`、`user_top_genre_1`。
- `BR-24-055`：**特征上线流程**：开发 → 回填 → 离线评估 → 一致性校验 → 灰度 → 全量。

### FR-24-007 探索机制（Bandit）【P1】

| 项 | 内容 |
|---|---|
| **功能目标** | 在利用（exploitation）与探索（exploration）间平衡，避免信息茧房 |
| **使用角色** | 系统内部 |

**方案对比**：

| 方案 | 说明 | 复杂度 | 本项目 |
|---|---|---|---|
| **ε-greedy** | 以 ε 概率随机选，1-ε 概率选最优 | 低 | **本期采用** |
| **Thompson Sampling** | 按后验概率采样 | 中 | P2 演进 |
| **UCB** | 置信上界，自动平衡 | 中 | P2 演进 |
| **LinUCB** | 上下文 bandit | 高 | 远期 |

**ε-greedy 实现**：

```java
public class ExploreOperator implements RerankOperator {

    private static final double EPSILON = 0.10;  // 10% 探索
    private static final int EXPLORE_SLOTS = 3;  // 每 30 首留 3 个探索位

    @Override
    public List<Candidate> apply(List<Candidate> ranked, RerankContext ctx) {
        int total = ranked.size();
        int slots = Math.max(1, (int) (total * EPSILON));

        // 1. 从探索池中选（长尾 + 新歌 + 未曝光）
        List<Candidate> explorePool = explorePoolService.getPool(ctx.getUserId());
        List<Candidate> exploreItems = weightedRandomPick(
            explorePool, slots, ctx.getUserHash());  // 按用户 hash 保证稳定

        // 2. 插入到非头部位置（避免影响首屏体验）
        //    位置：8, 16, 24 ... （跳过首屏）
        List<Candidate> result = new ArrayList<>(ranked);
        for (int i = 0; i < exploreItems.size(); i++) {
            int pos = 8 + i * 8;
            if (pos < result.size()) {
                result.set(pos, exploreItems.get(i));  // 替换而非插入（保持长度）
            }
        }
        return result;
    }

    private List<Candidate> weightedRandomPick(List<Candidate> pool, int k, long seed) {
        Random random = new Random(seed);  // 种子含 userId，同一用户结果稳定
        double totalWeight = pool.stream().mapToDouble(Candidate::getExploreWeight).sum();
        List<Candidate> picked = new ArrayList<>();
        for (int i = 0; i < k && !pool.isEmpty(); i++) {
            double r = random.nextDouble() * totalWeight;
            double cum = 0;
            for (Iterator<Candidate> it = pool.iterator(); it.hasNext(); ) {
                Candidate c = it.next();
                cum += c.getExploreWeight();
                if (cum >= r) {
                    picked.add(c);
                    totalWeight -= c.getExploreWeight();
                    it.remove();
                    break;
                }
            }
        }
        return picked;
    }
}
```

**探索池构成与权重**：

| 来源 | 权重 | 说明 |
|---|---|---|
| 新歌（7 天内） | 1.0 | 给新内容机会 |
| 长尾（曝光 < 1000） | 0.8 | 打破马太效应 |
| 用户未听过的风格（但相近） | 0.6 | 拓宽兴趣 |
| 高潜力（小曝光但高完成率） | 1.2 | 优质内容优先 |

**业务规则**：

- `BR-24-065`：**探索占比 10%**（可配置 5%-15%）。
- `BR-24-066`：**探索位不在首屏**（从第 8 位开始），保证首屏体验。
- `BR-24-067`：**探索结果按用户 hash 稳定**（同一用户同一天看到同一批探索内容），便于效果归因。
- `BR-24-068`：**探索内容必须相关**（不能纯随机）—— 从"相近风格"中选，不是全库随机。

### FR-24-008 实验分流 【P0】

| 项 | 内容 |
|---|---|
| **功能目标** | 支持算法/策略的在线对照实验，科学评估效果 |
| **使用角色** | 算法工程师、运营（创建实验）、管理员（审批） |

**分流模型**：

```
实验定义：
  实验 ID: 202610_rerank_v2
  层级（Layer）: 推荐策略层
  流量: 20%（总流量的 20% 参与该实验）
  分组:
    - control（对照组，50%）: 现有策略
    - treatment_a（实验组 A，25%）: 新的重排算子
    - treatment_b（实验组 B，25%）: 新的融合权重

分流算法（关键，必须确定性）：
  hash = murmur3(experimentId + "|" + userId + "|" + layerSalt)
  bucket = abs(hash) % 10000    // 0-9999
  if bucket >= trafficPercent * 100 → 不参与实验（走默认）
  else → 按分组比例映射到具体组
```

**分层实验（Layer）设计**：

| 层 | Layer Salt | 说明 |
|---|---|---|
| 召回层 | `recall_layer_v1` | 召回源相关实验 |
| 排序层 | `rank_layer_v1` | 排序模型相关实验 |
| 重排层 | `rerank_layer_v1` | 重排策略相关实验 |
| UI 层 | `ui_layer_v1` | 前端展示（推荐理由、卡片样式） |

> **为什么要分层**：同一用户可以**同时参与多个层的实验**（如召回层实验 A + UI 层实验 B），层之间用**不同的 salt** 保证分流独立（正交）。如果所有实验用同一 salt，会互相干扰。

**互斥组（Mutual Exclusion Group）**：

```json
{
  "mutexGroup": "ranking_strategy",
  "experiments": ["rerank_v2", "rerank_v3"],
  "rule": "同一用户只能进入其中一个实验"
}
```

> 用于**同层同类实验**必须互斥的场景（如两个不同的重排方案不能同时作用于同一用户）。

**分流实现**：

```java
@Component
public class ExperimentService {

    public ExperimentGroup assign(String experimentId, Long userId) {
        Experiment exp = experimentCache.get(experimentId);
        if (exp == null || !exp.isRunning()) {
            return ExperimentGroup.defaultGroup();
        }

        // 1. 检查是否被白名单强制指定
        ExperimentGroup forced = whitelistService.check(experimentId, userId);
        if (forced != null) return forced;

        // 2. 检查互斥组
        if (exp.getMutexGroup() != null) {
            ExperimentGroup existing = getMutexAssignment(exp.getMutexGroup(), userId);
            if (existing != null) {
                return existing.getExperimentId().equals(experimentId)
                    ? existing : ExperimentGroup.notInExperiment();
            }
        }

        // 3. Hash 分流
        long hash = Hashing.murmur3_32().hashString(
            experimentId + "|" + userId + "|" + exp.getLayerSalt(), StandardCharsets.UTF_8
        ).asInt();
        int bucket = Math.abs(hash) % 10000;

        if (bucket >= exp.getTrafficPercent() * 100) {
            return ExperimentGroup.notInExperiment();
        }

        // 4. 按分组比例映射
        int cumulative = 0;
        for (ExperimentGroup group : exp.getGroups()) {
            cumulative += group.getRatioPercent() * 100;
            if (bucket < cumulative) {
                return group;
            }
        }
        return ExperimentGroup.notInExperiment();
    }
}
```

**业务规则**：

- `BR-24-073`：**分流必须确定性**：同一 `userId + experimentId` 永远分到同一组（用 hash，不用随机数）。
- `BR-24-074`：**分流时机**：用户维度（不是请求维度），保证同一用户在整个实验期体验一致。
  - **例外**：游客用 `deviceId` 代替 `userId`。
- `BR-24-075`：**分层正交**：不同层用**不同 salt**，保证实验独立。

```java
/**
 * 两组比例指标的显著性检验（Z 检验）
 * 用于 CTR、完成率等比例指标
 */
public SignificanceResult zTest(long clicksA, long exposureA, long clicksB, long exposureB) {
    double pA = (double) clicksA / exposureA;
    double pB = (double) clicksB / exposureB;
    double pPool = (double) (clicksA + clicksB) / (exposureA + exposureB);

    double se = Math.sqrt(pPool * (1 - pPool) * (1.0 / exposureA + 1.0 / exposureB));
    if (se == 0) return SignificanceResult.notSignificant();

    double z = (pB - pA) / se;
    double pValue = 2 * (1 - normalCdf(Math.abs(z)));  // 双尾

    return SignificanceResult.builder()
        .lift((pB - pA) / pA)          // 相对提升
        .zScore(z)
        .pValue(pValue)
        .significant(pValue < 0.05)
        .confidenceLevel(1 - pValue)
        .build();
}
```

```
│ 人均有效播放│ 8.12     │ 9.45     │ 8.20     │ A: +16.4% *** │
│ 不喜欢率    │ 1.85%    │ 1.72%    │ 1.90%    │ A: -7.0%      │
│ 跳过率      │ 22.10%   │ 20.30%   │ 22.40%   │ A: -8.1% **   │
│ 长尾占比    │ 5.20%    │ 14.80%   │ 5.30%    │ A: +184% ***  │
└─────────────┴──────────┴──────────┴──────────┴──────────┘

结论：treatment_a 在 CTR、完成率、人均播放上均显著优于对照组（p < 0.01），建议全量。
显著性标记：* p<0.05, ** p<0.01, *** p<0.001
```

**业务规则**：

- `BR-24-085`：**主指标唯一**（每实验定义 1 个主指标，避免"挑指标"）。
- `BR-24-086`：**必须给出置信区间**，不只看点估计。
- `BR-24-087`：**样本量不足时不给结论**（显示"样本不足，继续观察"）。
- `BR-24-088`：**多重比较校正**：多个实验组对比时使用 Bonferroni 校正（`α' = α / n`）。
- `BR-24-089`：**实验最短运行周期 7 天**（覆盖工作日与周末），避免星期效应。
- `BR-24-090`：**AA 测试**：实验创建后先跑 AA（两组同策略）验证分流均匀（差异应不显著）。
- `BR-24-091`：**辛普森悖论防范**：指标必须支持**分维度下钻**（按新老用户、设备、时段），避免总体指标掩盖分群差异。
- `BR-24-092`：**指标口径唯一**：实验指标与数据平台指标**使用同一套口径**（同一份 SQL/同一份计算代码）。
- `BR-24-093`：**结果自动推送**：实验达显著或到期时，自动通知创建者。
- `BR-24-094`：**实验结论必须归档**（成功/失败都归档，失败经验同样有价值）。
- `BR-24-095`：**禁止边看边改**：实验运行中不得修改分组比例或策略（会导致样本污染）。

**异常情况**：

| 编号 | 场景 | 处理 |
|---|---|---|
| `EX-24-009-1` | 样本量不足 | 显示"样本不足"，不给结论 |
| `EX-24-009-2` | 分组流量严重不均 | 告警（分流 bug） |
| `EX-24-009-3` | AA 测试显示显著差异 | 阻断实验，排查分流问题 |
| `EX-24-009-4` | 指标数据延迟 | 显示"数据更新至 XX 时间" |
| `EX-24-009-5` | 实验期间线上故障 | 标注故障时段，支持剔除该时段数据 |

**验收标准**：

- `AC-24-009-1`：指标自动计算
- `AC-24-009-2`：显著性检验正确（单测验证）
- `AC-24-009-3`：样本不足不给结论
- `AC-24-009-4`：AA 测试可执行

## 9. 效果评估

### FR-24-010 离线评估 【P1】

| 项 | 内容 |
|---|---|
| **功能目标** | 上线前用历史数据评估新策略，避免直接上线的风险 |
| **使用角色** | 算法工程师 |

**评估方法**：

| 方法 | 说明 | 指标 |
|---|---|---|
| **时序切分（Time-based Split）** | 用前 6 天数据训练，第 7 天评估 | 所有指标 |
| **留一法（Leave-One-Out）** | 用用户历史 N-1 次播放预测第 N 次 | Hit Rate, NDCG |
| **离线重放（Replay）** | 用线上真实请求日志重放，对比新旧策略输出 | 列表差异率, 指标预估 |

**离线指标**：

| 指标 | 公式 | 说明 |
|---|---|---|
| **Hit Rate@K** | 推荐的 Top K 中命中用户实际播放的比例 | 召回能力 |
| **NDCG@K** | 归一化折损累计增益 | 排序质量 |
| **MAP@K** | 平均精度均值 | 排序质量 |
| **AUC** | 模型区分度 | 模型质量 |
| **LogLoss** | 交叉熵 | 模型校准度 |
| **覆盖率** | 有曝光的歌曲数 / 总歌曲数 | 生态健康 |
| **新颖性** | 推荐歌曲的平均热度倒数 | 探索能力 |

**评估报告**：

```
离线评估报告：rerank_v2
评估日期：2026-10-11
训练集：2026-10-04 ~ 2026-10-09（6 天）
测试集：2026-10-10（1 天）
样本量：1,250,000 次推荐请求

┌──────────────┬──────────┬──────────┬──────────┐

├──────────────┼──────────┼──────────┼──────────┤
│ AUC          │ 0.7234   │ 0.7412   │ +2.46%   │
│ LogLoss      │ 0.4521   │ 0.4468   │ -1.17%   │
│ HitRate@10   │ 0.3120   │ 0.3350   │ +7.37%   │
│ NDCG@10      │ 0.4512   │ 0.4730   │ +4.83%   │
│ HitRate@30   │ 0.5420   │ 0.5560   │ +2.58%   │
│ 覆盖率       │ 0.1820   │ 0.2140   │ +17.6%   │

└──────────────┴──────────┴──────────┴──────────┘

```

**业务规则**：

- `BR-24-096`：**必须离线评估通过**才能创建在线实验（离线指标不得显著下降）。
- `BR-24-097`：**时序切分必须严格**：测试集时间**晚于**训练集（不能随机切分，会造成未来信息泄露）。
- `BR-24-098`：**负样本采样**：训练时对未曝光歌曲采样（未曝光 ≠ 不感兴趣，不能全作为负样本）。
- `BR-24-099`：**评估必须可复现**（固定随机种子 + 固定数据集版本）。
- `BR-24-100`：**覆盖率和多样性必须一起评估**（不能只看点击率，否则推荐会收敛到少数热门）。
- `BR-24-101`：**离线评估与在线结果的相关性**需持续跟踪（若相关性低，说明评估有问题）。
- `BR-24-102`：**评估结果归档**（谁、何时、什么数据、什么结论）。

**验收标准**：

- `AC-24-010-1`：离线评估流程可执行
- `AC-24-010-2`：时序切分严格
- `AC-24-010-3`：AUC/NDCG/HitRate 等指标可计算
- `AC-24-010-4`：评估可复现
- `AC-24-010-5`：覆盖率和多样性一并评估
- `AC-24-010-6`：报告自动生成
- `AC-24-010-7`：结果归档

| 精排 | ≤ 80ms | 高（模型推理） | 中 |
| 重排 | ≤ 30ms | 中 | 低 |
| 详情批量查询 | ≤ 20ms | 低 | 低 |
| **合计** | **≤ 200ms（P99）** | — | ≤ 200MB/请求峰值 |

**并发能力**：

| 指标 | 值 |
|---|---|
| 单实例推荐 QPS | ~500（8C16G） |
| 推荐实例数（10 万 DAU） | 4（2 主 2 备，峰值弹性到 8） |
| 召回线程池 | 核心 32，最大 64，队列 0 |
| 特征线程池 | 核心 16，最大 32 |
| 排序线程池 | 核心 16，最大 32 |

**缓存策略**：

| 场景 | 缓存 | TTL | 命中率目标 |
|---|---|---|---|
| 游客首页推荐 | Redis（按设备 hash 分桶） | 5min | ≥ 70% |
| 新用户首页 | Redis（全局热门） | 5min | ≥ 90% |
| 活跃用户首页 | 不缓存（个性化） | — | — |
| 每日推荐 | Redis | 24h | ≥ 95% |
| 相似歌曲 | Redis | 7d | ≥ 90% |

**存储容量**：

| 数据 | 规模 | 存储 |
|---|---|---|
| 用户画像特征 | 100 万 × 2KB | Redis ~2GB |
| 歌曲统计特征 | 100 万 × 1KB | Redis ~1GB |
| 推荐日志 | 200 万/天 × 2KB | ClickHouse ~4GB/天，保留 7 天 ~28GB |
| 指标日报 | 365 × 10 场景 × N 组 | MySQL ~10MB/年 |
| 实验配置 | 少量 | MySQL |
| 曝光记录 | 100 万用户 × 100 首 | Redis ~10GB（需评估，可缩短 TTL） |

## 14. 降级策略

| 依赖 | 故障 | 降级 |
|---|---|---|
| 特征服务 | Redis 不可用 | 全特征用默认值，退化为召回分数排序 |
| 向量库 | Milvus 不可用 | 跳过 `vector*` 源 |
| 协同过滤存储 | 不可用 | 跳过 `cf_*` 源 |
| 精排模型 | 加载/推理失败 | 降级到线性规则 |
| 召回源 | 单源失败 | 跳过（其他源继续） |
| 召回全部失败 | — | 降级热门榜（Redis 缓存） |
| 整体超时 | > 200ms | 返回已达成的候选（可能少于 30 首） |
| 实验服务 | 不可用 | 全部用户走默认策略 |
| 推荐服务 | 完全不可用 | 前端降级展示"热门歌曲"静态列表 |
| LLM（推荐理由） | 不可用 | 不展示理由 |

**降级优先级（从轻到重）**：

```
1. 关闭推荐理由生成
2. 关闭探索位
3. 跳过向量召回
4. 跳过协同过滤召回
5. 跳过精排（用召回分数）
6. 只保留热度召回
7. 返回 Redis 缓存的热门榜
8. 前端静态兜底
```
