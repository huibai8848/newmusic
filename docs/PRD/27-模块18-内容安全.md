## 1. 模块目标

音乐内容平台是**强监管场景**，内容安全是**合规红线**，不是"锦上添花"。

**核心目标**：

| 目标 | 说明 |
|---|---|
| **违规内容零漏出** | 高危内容（涉政、涉黄、暴恐）**必须**在上线前拦截 |
| **快速处置** | 举报到处置 ≤ 24 小时（紧急 ≤ 2 小时） |
| **可追溯** | 每次审核/处置有记录，可回溯 |
| **可申诉** | 用户对处置有申诉通道 |
| **合规** | 满足《网络安全法》《网络信息内容生态治理规定》《未成年人保护法》等 |

**衡量指标**：

| 指标 | 目标 |
|---|---|
| 高危内容漏出率 | **0**（红线） |
| 机审召回率（文本） | ≥ 99% |
| 机审准确率（文本） | ≥ 95% |
| 图片违规检出率 | ≥ 98% |
| 举报处理时效（P95） | ≤ 2 小时（紧急）/ ≤ 24 小时（一般） |
| 误判申诉处理时效 | ≤ 24 小时 |
| 审核人力成本 | ≤ 5 人/10 万 DAU |
| 审核覆盖率 | 100%（所有 UGC） |

## 4. 内容安全架构

```
UGC 内容产生（评论/动态/歌单名/房间名/昵称/简介/私信/弹幕/歌词校准）
      ↓
【第一道防线：前置校验/DFA】（同步，< 10ms）
   - 敏感词（DFA 树）
   - 长度/格式校验
   - 频率限制
   - 高危词直接拒绝（返回错误）
      ↓
【第二道防线：机审】（同步/异步）
   - 文本：DFA + 分类模型 + 第三方审核 API
   - 图片：图像审核 API（涉黄/暴恐/OCR 文字）
   - 决策：通过 / 拒绝 / 转人工
      ↓
【第三道防线：人工审核】（异步，队列）
   - 机审不确定的内容
   - 用户举报的内容
   - 随机抽检
      ↓
【第四道防线：事后巡检】（定时）
   - AI 全量扫描存量内容
   - 关键词回溯
   - 用户举报聚类
      ↓
【处置】（违规内容）
   - 内容：删除/隐藏/仅自己可见
   - 用户：警告/限制/禁言/封禁
   - 记录：审核日志 + 通知用户 + 支持申诉
```

**四道防线设计原则**：

| 防线 | 特点 | 目标 |
|---|---|---|
| 前置校验 | **同步、极快、成本低** | 拦截明显违规（高危词、格式错误），减少下游压力 |
| 机审 | **准实时、覆盖率 100%** | 找出大部分违规，分流 |
| 人工审核 | **准确、成本高** | 处理机审不确定与用户举报 |
| 事后巡检 | **兜底、覆盖存量** | 发现规则更新前的漏网之鱼 |

## 5. 敏感词过滤（DFA）

### FR-27-001 敏感词库与 DFA 过滤 【P0】

| 项 | 内容 |
|---|---|
| **功能目标** | 毫秒级检测文本中的敏感词，拦截违规内容 |
| **使用角色** | 系统内部（词库由管理员维护） |

**DFA（Deterministic Finite Automaton）算法**：

```
使用 Trie 树（字典树）+ 失败指针（AC 自动机）实现多模式匹配。
复杂度：O(n)（n 为文本长度），与词库大小无关。

为什么用 DFA 而不是正则/contains：
  - 词库有 10 万+ 词，正则逐词匹配是 O(m×n)，不可接受
  - DFA 一次扫描即可匹配所有词，O(n)
  - 支持重叠词、最长匹配、多模式同时匹配
```

**Trie 节点实现**：

```java
public class SensitiveWordFilter {

    /** Trie 节点 */
    private static class TrieNode {
        private final Map<Character, TrieNode> children = new HashMap<>(4);
        private boolean isEnd = false;      // 是否为词尾
        private String word;                 // 完整词（用于返回）
        private int level;                   // 敏感级别（1 疑似 / 2 高危 / 3 禁止）
    }

    private TrieNode root = new TrieNode();

    /** 构建词库（支持热更新，双 buffer 切换） */
    public void build(Collection<SensitiveWord> words) {
        TrieNode newRoot = new TrieNode();
        for (SensitiveWord w : words) {
            TrieNode node = newRoot;
            // 归一化：全角转半角、简繁统一、去空格、转小写
            char[] chars = normalize(w.getWord()).toCharArray();
            for (char c : chars) {
                node = node.children.computeIfAbsent(c, k -> new TrieNode());
            }
            node.isEnd = true;
            node.word = w.getWord();
            node.level = w.getLevel();
        }
        this.root = newRoot;  // 原子替换（volatile）
    }

    /** 检测文本中的敏感词 */
    public List<MatchResult> match(String text) {
        List<MatchResult> results = new ArrayList<>();
        char[] chars = normalize(text).toCharArray();

        for (int i = 0; i < chars.length; i++) {
            TrieNode node = root;
            for (int j = i; j < chars.length; j++) {
                node = node.children.get(chars[j]);
                if (node == null) break;
                if (node.isEnd) {
                    results.add(new MatchResult(node.word, i, j - i + 1, node.level));
                    // 最长匹配：继续匹配，不 break
                }
            }
        }
        return results;
    }

    /**
     * 归一化：这是最关键的一步，防止绕过
     */
    private String normalize(String text) {
        if (text == null) return "";
        String s = text;
        s = ChineseConverter.toSimplified(s);        // 繁体转简体
        s = FullHalfWidthConverter.toHalfWidth(s);   // 全角转半角
        s = s.toLowerCase();                          // 转小写
        s = s.replaceAll("\\s+", "");                 // 去所有空白（防"敏 感 词"绕过）
        s = s.replaceAll("[\\p{Punct}\\p{IsPunctuation}]", ""); // 去标点（防"敏-感-词"绕过）
        s = NumericWordConverter.convert(s);          // 数字谐音转字母（如 "1"→"一"？见下）
        s = PinyinConverter.toPinyin(s);              // 【可选】拼音化（防拼音绕过）
        return s;
    }
}
```

**绕过手段与对策**：

| 绕过手段 | 示例 | 对策 |
|---|---|---|
| 空格分隔 | `敏 感 词` | 去所有空白 |
| 标点分隔 | `敏-感-词`、`敏*感*词` | 去标点 |
| 全角字符 | `敏感词`（全角） | 全角转半角 |
| 繁体字 | `敏感詞` | 繁转简 |
| 大小写 | `SensItive` | 转小写 |
| 拼音 | `minganci` | 拼音化后匹配 |
| 谐音字 | `敏感磁` | 词库包含谐音变体 |
| 同音数字 | `520`（我爱你） | 数字谐音词典 |
| 插入特殊字符 | `敏​感词`（零宽字符） | 去除不可见字符 |
| 拆字 | `敏` + `感` + `词`（不同消息） | 跨消息检测（限制） |
| 图片文字 | 敏感内容做成图片 | OCR 识别（见 FR-27-003） |
| 火星文 | `勄感詞` | 词库包含变体 + 人工审核 |

**业务规则**：

- `BR-27-001`：**所有 UGC 文本必须过 DFA**（评论、动态、昵称、简介、歌单名/简介、房间名/公告、弹幕、私信、歌词校准提交、举报理由）。
- `BR-27-002`：**敏感词分三级**：

| 级别 | 名称 | 处置 |
|---|---|---|
| **L1** | 疑似 | 内容**正常发布**，但**转人工审核**（不阻塞用户） |
| **L2** | 高危 | 内容**发布但仅自己可见**，转人工审核 |
| **L3** | 禁止 | 内容**拒绝发布**，返回明确错误，记录风险用户 |

- `BR-27-003`：**L3 词不得出现在词库管理界面**（防泄露），仅 SUPER_ADMIN 可见。
- `BR-27-004`：**词库必须热更新**（不重启服务），采用**双 buffer 切换**（构建新树后原子替换引用）。
- `BR-27-005`：**归一化必须全面**（见上表），且**归一化后匹配的位置必须能映射回原文**（用于高亮）。
- `BR-27-006`：**词库来源**：
  - 基础词库（官方合规词库，定期更新）
  - 业务词库（运营维护，如竞品名、广告词）
  - 用户举报补充（从举报中提取）
  - 白名单（误判词，如"草莓"含"草"相关词时排除）
- `BR-27-007`：**白名单优先**：白名单命中的词**不判定为敏感**（如"人民大会堂"含"人民"）。
- `BR-27-008`：**禁止在日志中输出敏感词原文**（脱敏为 `敏**词` 或哈希）。
- `BR-27-009`：**词库变更有审计**（谁、何时、增删了什么词）。
- `BR-27-010`：**词库版本管理**：每次变更有版本号，审核记录引用版本号（便于回溯"当时为什么放行"）。
- `BR-27-011`：**多音字/变体**：词库需包含常见变体（如"微 信"、"威信"、"V信"）。
- `BR-27-012`：**正则支持**：部分规则需要正则（如手机号 `1[3-9]\d{9}`），DFA 与正则**混合使用**。
- `BR-27-013`：**误判可申诉**：用户可对误判申诉，申诉成功则加入白名单。
- `BR-27-014`：**词库更新频率**：官方词库每周同步，业务词库随时可加。
- `BR-27-015`：**必须支持"命中统计"**：每个词被命中次数统计（用于评估词质量，清理无效词）。

**机审能力矩阵**：

| 内容类型 | 检测项 | 方式 |
|---|---|---|

**机审架构**：

```java
public interface ContentAuditService {

    AuditResult audit(AuditRequest request);
}

@Data
@Builder
public class AuditRequest {
    private String contentType;   // TEXT / IMAGE / NICKNAME / PLAYLIST_NAME / ROOM_NAME / DANMAKU / COMMENT / POST / PRIVATE_MSG
    private Long contentId;       // 内容 ID
    private String text;           // 文本内容
    private List<String> images;   // 图片 URL
    private Long userId;
    private String scene;          // 场景
}

@Data
public class AuditResult {
    private AuditDecision decision;   // PASS / REJECT / REVIEW（转人工）
    private String reason;             // 原因
    private List<String> hitWords;     // 命中的敏感词（脱敏）
    private int riskLevel;             // 0-100 风险分
    private String auditSource;        // DFA / MODEL / THIRD_PARTY / OCR
    private long costMs;
    private String detail;             // 详细（JSON）
}

public enum AuditDecision {
    PASS,      // 通过
    REJECT,    // 拒绝
    REVIEW     // 转人工
}
```

**机审流程**：

```
内容提交
   ↓
[1] DFA 敏感词检测（< 1ms）
     - L3 命中 → REJECT（直接拒绝，不再往下）
     - L2 命中 → REVIEW（转人工，同时标记）
     - L1 命中 → REVIEW
     - 无命中 → 继续
   ↓
[2] 正则规则检测（< 1ms）
     - 手机号/QQ/微信/URL → REJECT 或 REVIEW
   ↓
[3] 分类模型（本地，< 10ms）
     - 轻量模型（如 FastText/ONNX）判断文本倾向
     - 高风险 → REVIEW
   ↓
[4] 第三方审核 API（可选，50-200ms，异步）
     - 更准确的判定（涉政涉黄）
     - 返回风险分与标签
     - 高风险 → REJECT
     - 中风险 → REVIEW
     - 低风险 → PASS
   ↓
[5] OCR（图片类必做）
     - 提取图片文字 → 再走 DFA
   ↓
[6] 综合决策
     - 任一环节 REJECT → REJECT
     - 任一环节 REVIEW → REVIEW
     - 全部 PASS → PASS
```

**机审策略（按内容类型）**：

| 内容类型 | 同步/异步 | 策略 |
|---|---|---|
| 评论 | **同步**（阻塞，≤ 50ms） | DFA + 规则 + 轻量模型；第三方异步复核 |
| 动态 | **半同步**（DFA 同步拒绝高危，其余先发后审） | 见 [25 章 BR-25-027](./25-模块16-社交升级.md) |
| 昵称/简介 | **同步**（≤ 100ms） | DFA + 规则 |
| 歌单名/简介 | **同步** | 同上 |
| 房间名/公告 | **同步** | 同上 |
| 弹幕 | **同步**（≤ 20ms） | DFA + 规则（**仅 L3 拒绝，L1/L2 直接过滤不展示**） |
| 私信 | **异步**（不阻塞发送） | 发送后异步审核，违规则撤回 + 通知 |
| 图片 | **异步**（先展示占位/模糊） | 上传后异步机审，不通过则隐藏 |

> **弹幕特殊处理**：弹幕是高频实时场景，不能因为审核延迟影响体验。策略：**DFA 命中 L1/L2 直接不展示（静默丢弃）**，L3 拒绝并提示。同时异步抽样送第三方审核。

**业务规则**：

- `BR-27-026`：**所有 UGC 必须机审**（无例外）。
- `BR-27-027`：**同步审核有超时保护**（≤ 50ms），超时则**保守处理**：
  - 高危场景（昵称、评论首条）→ 转人工（REVIEW）
  - 低危场景（弹幕）→ 丢弃
- `BR-27-028`：**机审决策必须记录**（`t_audit_record`：内容、决策、来源、耗时、命中项）。
- `BR-27-029`：**第三方审核 API 必须有降级**（不可用时只用 DFA + 规则，标注"审核不完整"）。
- `BR-27-030`：**机审成本控制**（第三方 API 按量计费）：
  - 纯文本先用 DFA/规则过滤，**只有无命中才送第三方**（大部分内容 DFA 可判定）。
  - 高置信内容跳过第三方（如已知安全的模板内容）。
  - 抽样送检（如 10% 的正常内容送第三方，用于发现漏网）。
- `BR-27-031`：**风险分机制**：机审输出 0-100 风险分，≥ 70 拒绝，40-70 转人工，< 40 通过。
- `BR-27-032`：**图片审核必须包含 OCR**（图片中的文字是常见绕过手段）。
- `BR-27-033`：**图片审核前必须压缩与转码**（防止超大图片拖慢审核）。
- `BR-27-034`：**审核结果可缓存**（相同图片 MD5 复用结果，节省成本）。
- `BR-27-035`：**机审模型版本必须记录**（模型升级后效果对比）。
- `BR-27-036`：**机审误判必须可申诉**（用户申诉后人工复核，纠正则加入白名单或调整阈值）。
- `BR-27-037`：**新用户/低信用用户加严**（注册 < 7 天，风险分阈值下调 10 分，即更易转人工）。
- `BR-27-038`：**高频违规用户加严**（历史违规 ≥ 3 次，阈值下调 20 分）。
- `BR-27-039`：**机审不得输出敏感词原文**（日志脱敏）。

**异常情况**：

| 编号 | 场景 | 处理 |
|---|---|---|
| `EX-27-003-1` | 机审超时 | 按场景保守处理（转人工 / 丢弃） |
| `EX-27-003-2` | 第三方 API 不可用 | 降级到 DFA + 规则，标注审核不完整，告警 |
| `EX-27-003-3` | OCR 服务不可用 | 图片进人工审核队列 |
| `EX-27-003-4` | 模型加载失败 | 降级到纯 DFA |
| `EX-27-003-5` | 机审成本超预算 | 降低第三方调用比例（只送高风险），告警 |
| `EX-27-003-6` | 图片下载失败 | 转人工审核 |
| `EX-27-003-7` | 审核结果冲突（DFA 通过，第三方拒绝） | **以严厉者为准**（第三方拒绝 → 拒绝） |

**验收标准**：

- `AC-27-003-1`：所有 UGC 内容经机审
- `AC-27-003-2`：DFA + 规则 + 模型 + 第三方多级审核
- `AC-27-003-3`：图片含 OCR 检测
- `AC-27-003-4`：风险分机制生效
- `AC-27-003-5`：同步审核超时有保守处理
- `AC-27-003-6`：机审决策完整记录
- `AC-27-003-7`：第三方不可用有降级
- `AC-27-003-8`：机审成本可控（DFA 优先，抽样送检）
- `AC-27-003-9`：新用户/高频违规用户加严
- `AC-27-003-10`：文本机审 P95 ≤ 50ms（不含第三方）

### FR-27-005 申诉处理 【P1】

| 项 | 内容 |
|---|---|
| **功能目标** | 为被误判用户提供申诉通道 |
| **使用角色** | 用户（申诉）、OPERATOR/ADMIN（处理） |

**申诉流程**：

```
用户收到处置通知（含"申诉"按钮）
   ↓
[1] 用户提交申诉
     - 申诉理由（≤ 500 字）
     - 可选上传证据（图片）

[2] 提交限制

     - 申诉需在处置后 7 天内
     - 每日最多申诉 3 次
```

- `BR-27-058`：**申诉成功**：恢复内容与权限（若封禁则解封），**公开道歉/说明**（可选）。
- `BR-27-059`：**误判统计**：记录误判率，用于优化词库与机审阈值。
- `BR-27-060`：**恶意申诉**：明显无理由的申诉（如涉政内容申诉）不计入审核员 KPI，且可能加重处置。
- `BR-27-061`：**申诉不中断处置**：申诉期间原处置继续生效（除封禁可暂缓执行，视策略）。
- `BR-27-062`：**封禁申诉优先**：账号封禁的申诉优先级最高（影响用户使用）。

**异常情况**：

### FR-27-006 举报处理 【P0】

| 项 | 内容 |
|---|---|
| **功能目标** | 接收、合并、处理用户举报 |
| **使用角色** | 用户（举报）、OPERATOR/ADMIN（处理） |

> **说明**：举报的**提交侧**定义见 [19 章 模块10 社交基础](./19-模块10-社交基础.md)。本章定义**处理侧**。

**举报合并规则**：

```
同一内容被多人举报
   ↓
[1] 首次举报 → 创建举报任务
   ↓
[2] 后续举报（24 小时内同一内容）→ 合并到现有任务
     - 累加举报人数
     - 记录举报理由分布
   ↓
[3] 举报人数达到阈值 → 自动提升优先级
     - ≥ 3 人 → 优先级提升
     - ≥ 10 人 → 最高优先级 + 自动降低内容推荐权重（先限流，后审核）
   ↓
[4] 审核员处理整个任务（对所有举报人统一回复）
```

**举报理由分类**：

| 分类 | 子项 |
|---|---|
| 违法违规 | 涉政、涉黄、暴恐、违禁品、赌博、诈骗 |
| 侵权 | 侵犯版权、侵犯隐私、冒充他人 |
| 不良信息 | 辱骂、人身攻击、谣言、引战 |
| 垃圾广告 | 广告、营销、外链、二维码 |
| 其他 | 不感兴趣、其他（需填写说明） |

**自动处置规则（按举报数）**：

| 举报人数 | 处置 |
|---|---|
| 1-2 | 进审核队列（普通优先级） |
| 3-9 | 优先级提升，审核 SLA 缩短到 6 小时 |
| 10-49 | 最高优先级，内容**自动降权**（不推荐、不展示在热门） |
| ≥ 50 | 内容**自动隐藏**（先隐藏后审核，审核通过则恢复） |

**业务规则**：

- `BR-27-063`：**举报 24 小时内同一内容合并**（去重，防止刷举报）。
- `BR-27-064`：**举报人不可见**（被举报者不知道谁举报，除法律要求）。
- `BR-27-065`：**举报限制**：单用户 10 次/小时，30 次/天（见 [19 章](./19-模块10-社交基础.md)）。
- `BR-27-066`：**恶意举报限制**：举报准确率 < 20% 且举报数 > 20 → 限制举报功能 7 天（见 [19 章](./19-模块10-社交基础.md)）。
- `BR-27-067`：**举报必须处理**（不得直接关闭，除非明确无效）。
- `BR-27-068`：**处理结果通知举报人**（"你的举报已处理"），但不透露具体处置细节（保护被举报者隐私）。
- `BR-27-069`：**高举报数自动降权/隐藏**（防止违规内容在审核前大范围传播）。
- `BR-27-070`：**举报处理 SLA**：紧急（涉政涉黄暴恐）2 小时，一般 24 小时。
- `BR-27-071`：**举报来源**：站内举报按钮 + 客服渠道 + 监管转办（监管转办优先级最高）。
- `BR-27-072`：**监管转办**必须**立即处理**（≤ 2 小时）并**反馈处理结果**至监管平台（如有对接）。
- `BR-27-073`：**举报统计**：按内容类型、理由、处理结果统计，用于发现高危内容类型。
- `BR-27-074`：**误报率高不能停用举报**（宁可多处理，不可漏报）。

**异常情况**：

| 编号 | 场景 | 处理 |
|---|---|---|
| `EX-27-006-1` | 被举报内容已删除 | 归档任务，记录"内容已删除" |
| `EX-27-006-2` | 举报人已注销 | 仍处理，不通知 |
| `EX-27-006-3` | 举报数暴增（可能被恶意刷） | 识别异常来源（同一 IP/设备）→ 剔除刷量 |
| `EX-27-006-4` | 举报任务冲突（同时被多个审核员领取） | 分布式锁保证唯一 |
| `EX-27-006-5` | 监管转办 | 最高优先级 + 专门队列 + 时限提醒 |

**验收标准**：

- `AC-27-006-1`：举报可提交与合并

### FR-27-007 用户违规处置与信用分 【P0】

| 项 | 内容 |
|---|---|
| **功能目标** | 对违规用户分级处置，建立信用体系 |
| **使用角色** | ADMIN、SUPER_ADMIN |

**处置等级**：

| 等级 | 处置 | 时长 | 权限 |
|---|---|---|---|
| L1 | 警告（通知） | — | OPERATOR |
| L2 | 限制发言（评论/动态/弹幕） | 1/3/7/30 天 | OPERATOR |
| L3 | 禁言（全部 UGC） | 1/7/30 天 | ADMIN |
| L4 | 封禁（登录受限） | 1/7/30 天 | ADMIN |
| L5 | 永久封禁 | 永久 | SUPER_ADMIN |

**用户状态与处置的关系**：

```
t_user.status: 0 待激活 / 1 正常 / 2 封禁 / 3 注销中 / 4 已注销

限制发言 = status 仍为 1，但 t_user_restriction 有生效记录
禁言     = status 仍为 1，但 restriction.type = ALL_UGC
封禁     = status = 2（无法登录）
```

**信用分机制**：

```
初始信用分：100

扣分规则：
  L1 警告        -5
  内容删除       -3
  限制发言       -10
  禁言 1 天      -20
  禁言 7 天      -30
  封禁           -50
  涉政/涉黄/暴恐 -100（直接归零）

加分规则：
  连续 30 天无违规  +10（上限 100）
  完成实名认证      +5
  账号正常使用 180 天 +10

信用分影响：
  ≥ 90：正常，享有全部功能
  70-89：正常，但内容审核阈值收紧 5 分
  50-69：内容优先人工审核，推荐权重降低
  30-49：限制部分功能（如不能发动态）
  < 30：仅可浏览，不可发布内容
```

**业务规则**：

- `BR-27-075`：**处置必须记录**（`t_user_restriction`：用户、类型、原因、时长、开始/结束时间、操作人、关联内容、关联举报）。
- `BR-27-076`：**处置必须通知用户**（站内消息 + 邮件/短信，视等级；说明原因与时长）。
  - **例外**：涉政类不透露具体原因（只写"违反社区规范"），防对抗。
- `BR-27-077`：**自动解封**：到期自动解除（XXL-Job 定时任务每分钟扫描）。
- `BR-27-078`：**加严策略**：违规次数越多，同等行为处置越重（第一次警告，第三次直接禁言）。
- `BR-27-079`：**累计违规**：90 天内累计 3 次 L2 以上处置 → 自动升级为 L3。
- `BR-27-080`：**封禁必须可申诉**（见 FR-27-005）。
- `BR-27-081`：**封禁的连带处理**：
  - 其内容全部隐藏（用户不可见）。
  - 其关注/粉丝关系保留（解封后恢复）。
  - 其私信不可发送。
- `BR-27-082`：**永久封禁需 SUPER_ADMIN** + 二次确认 + 记录详细原因。
- `BR-27-083`：**同设备/同 IP 关联账号**：若主账号被永久封禁，关联账号进入观察名单（新注册账号加严审核）。
- `BR-27-084`：**信用分恢复**：信用分随时间自然恢复（每月 +5，上限 100）。
- `BR-27-085`：**申诉成功**必须**恢复信用分**（撤销对应扣分）。
- `BR-27-086`：**处置不得侵犯合法权益**（如用户数据不可删除，只能隐藏）。
- `BR-27-087`：**封禁用户的数据保留**（依法保留，不删除）。

**异常情况**：

| 编号 | 场景 | 处理 |
|---|---|---|
| `EX-27-007-1` | 自动解封任务失败 | 告警，手动解封 |
| `EX-27-007-2` | 用户已注销但被处置 | 跳过（不影响注销流程） |

**验收标准**：

### FR-27-008 版权管理与侵权处理 【P0】

| 项 | 内容 |
|---|---|
| **功能目标** | 管理音乐版权，处理侵权投诉 |
| **使用角色** | OPERATOR（日常）、ADMIN（下架决策） |

> **重要前提**：**本项目假设使用已获得授权的正版曲库**或**公版/自有内容**。若实际未获授权，**不得上线供公开收听**。
> **【假设 A-37】** 曲库来源为**已授权音乐版权方的 API/曲库**（假设已签署协议）。若无授权，系统仅可作为**技术演示**（不含真实音频）或使用**公版音乐**（如古典乐、CC 授权）。

**版权信息管理**：

| 字段 | 说明 |
|---|---|
| 歌曲版权方 | 版权持有方 |
| 授权类型 | 独家/非独家 |
| 授权地域 | 中国大陆/全球 |
| 授权开始/结束时间 | 到期需下架或续约 |
| 授权范围 | 在线播放/下载/商用 |
| 版权凭证 | 合同编号/文件 |
| 版权状态 | 有效/即将到期/已过期 |

**到期预警**：

```
授权到期前 30 天 / 15 天 / 7 天 / 3 天 / 1 天 → 提醒运营
到期当天 → 自动下架（可配置为到期即下架，或到期后 24h 宽限）
```

**侵权投诉（DMCA-like）流程**：

```
权利人提交侵权投诉
   ↓
[1] 提交信息（必须完整）：
     - 权利人身份（个人/机构）
     - 权属证明（著作权登记/授权文件）
     - 侵权内容（歌曲 ID / URL）
     - 联系方式
     - 声明（真实性承诺）
   ↓
[2] 校验完整性（信息不全则退回）
   ↓
[3] 创建投诉任务（优先级最高，SLA ≤ 24 小时，紧急 ≤ 2 小时）
   ↓
[4] 审核员初判：
     - 证明材料充分 → 立即下架（先下架后通知）
     - 材料不足 → 联系补充
     - 明显不成立 → 驳回
   ↓
[5] 下架 → 通知上传者/被投诉方（可提出反通知）
   ↓
[6] 反通知 → 转交权利人 → 双方举证（可延长处理）
   ↓
[7] 记录归档（法律留档，保留 ≥ 3 年）
```

**业务规则**：

- `BR-27-088`：**版权信息必须完整**（每首歌都有版权方与授权范围），缺失则**不上架**。
- `BR-27-089`：**授权到期自动下架**（到期前预警，到期当日或宽限期后下架）。
- `BR-27-090`：**授权地域限制**：超地域访问需拦截（按用户 IP 判断）。
- `BR-27-091`：**侵权投诉必须受理**（不得无视），且在 **24 小时内**完成初判。
- `BR-27-092`：**先下架后核实**（对权属证明充分的投诉），降低法律风险。
- `BR-27-093`：**重复侵权用户**（多次上传侵权内容）→ 限制上传权限。
- `BR-27-094`：**下架必须通知相关方**（上传者、受影响用户如收藏了该歌曲）。
- `BR-27-095`：**下架记录必须保留**（≥ 3 年，法律要求）。
- `BR-27-096`：**歌词版权**：歌词展示需授权（**假设**：与曲库同一授权）。
- `BR-27-097`：**用户上传内容**（如动态中的歌词片段）**限制长度**（≤ 100 字，合理引用）。
- `BR-27-098`：**不得提供下载功能**（除授权允许）。
- `BR-27-099`：**不得提供版权歌曲的二次创作分发**（如用户上传翻唱，需单独授权）。
- `BR-27-100`：**监管要求配合**：接到监管下架通知，**立即下架**（≤ 2 小时）并**反馈**。

**异常情况**：

| 编号 | 场景 | 处理 |
|---|---|---|
| `EX-27-008-1` | 版权信息缺失 | 不上架，提示补全 |
| `EX-27-008-2` | 授权到期 | 自动下架 + 通知 |
| `EX-27-008-3` | 投诉材料不全 | 退回并要求补充 |
| `EX-27-008-4` | 监管通知 | 立即下架 + 反馈 |
| `EX-27-008-5` | 反通知 | 延长处理，双方举证 |
| `EX-27-008-6` | 下架影响用户收藏 | 收藏保留但显示"已下架" |

**验收标准**：

- `AC-27-008-1`：版权信息完整管理
- `AC-27-008-2`：到期预警与自动下架
- `AC-27-008-3`：侵权投诉受理 ≤ 24 小时
- `AC-27-008-4`：先下架后核实
- `AC-27-008-5`：下架通知相关方
- `AC-27-008-6`：下架记录保留 ≥ 3 年
- `AC-27-008-7`：监管通知立即处理
- `AC-27-008-8`：地域限制生效

## 13. 内容安全监控与报表

**实时监控**：

| 指标 | 告警阈值 |
|---|---|
| 审核队列积压 | > 1000 条告警 |
| 举报队列积压 | > 500 条告警 |
| 审核 SLA 超时 | 超时率 > 5% 告警 |
| 高危内容漏出（用户投诉） | > 0 立即告警 |
| 机审拒绝率异常 | 环比变化 > 50% |
| 词库热更新失败 | 立即告警 |
| 第三方审核 API 失败 | 失败率 > 10% 告警 |
| 审核成本超预算 | > 80% 预算告警 |
| 单用户高频违规 | 1 小时内 > 5 次违规告警 |
| 同一内容举报激增 | > 50 人举报立即告警 |

**业务规则**：

- `BR-27-118`：**内容安全数据必须单独看板**，运营与管理员可见。
- `BR-27-119`：**误判率必须监控**（申诉成功率），> 10% 需优化。
- `BR-27-120`：**漏出率必须为 0**（高危内容），一旦发生立即复盘。
- `BR-27-121`：**审核时效必须监控**（SLA 达标率）。
- `BR-27-122`：**审核人力 vs 内容量必须监控**（人力不足需预警）。
- `BR-27-123`：**成本监控**（第三方 API + 人力成本）。
- `BR-27-124`：**安全日报每日推送**（含异常提示）。
- `BR-27-125`：**监管报表**：定期生成合规报表（如需上报）。

## 14. 降级策略

| 依赖 | 故障 | 降级 |
|---|---|---|
| DFA 词库 | 加载失败 | 使用内置最小基础词库（L3 词兜底） |
| 词库热更新 | 失败 | 保留旧词库，告警 |
| 第三方审核 API | 不可用 | 仅用 DFA + 规则 + 本地模型，标注"审核不完整" |
| OCR 服务 | 不可用 | 图片进人工队列 |
| 审核工作台 | 不可用 | 内容按保守策略处理（可疑内容暂不展示） |
| 审核队列（MQ） | 不可用 | 内容先发后审，进 DB 待审表 |
| 图片存储 | 不可用 | 禁止上传，纯文本可用 |
| 申诉服务 | 不可用 | 记录申诉请求，恢复后处理 |
| 信用分服务 | 不可用 | 使用默认分（不阻断） |
| **审核整体不可用** | — | **保守降级**：所有 UGC 仅自己可见，恢复后补审（安全优先） |

> **重要原则**：内容安全**不可"降级为放行"**。审核系统故障时，宁可**限制内容发布**（保守），也不能让未审核内容公开。这与一般业务系统的"降级保可用"原则相反。
