## 1. 模块目标

提供"多人同听一首歌"的实时互动场景，把单机听歌升级为群体共鸣，提升停留时长与留存。

**衡量指标**：

| 指标 | 目标 |
|---|---|
| 房间创建成功率 | ≥ 99.9% |
| 加入房间成功率 | ≥ 99.9% |
| 房间平均停留时长 | ≥ 12 分钟 |
| 房间内互动率（发言/弹幕/点赞） | ≥ 40% |
| 单房间峰值并发 | ≥ 500 |
| 播放进度同步偏差 | ≤ 1.5s |

> **【假设 A-09】** 本期音乐房为"**排麦出歌**"模式（成员排队点歌/上麦展示），**不含实时语音连麦**。若后续需要语音，需接入第三方 RTC（TRTC/Agora），架构影响见第 10 节。

---

## 2. 使用角色

| 角色 | 能力 |
|---|---|
| 游客 | 进入公开房收听、查看成员，**不可**发言/上麦/点歌 |
| 普通用户 | 创建房间、加入/退出、发言、弹幕、排麦、点歌、申请切歌、举报 |
| 房主（ROOM_OWNER） | 全部成员能力 + 控播、踢人、禁言、设房管、公告、转让、解散、模式设置 |
| 房管（ROOM_ADMIN） | 控播、踢人、禁言、排麦管理、发公告（不可解散/转让/设房管） |
| 平台管理员 | 后台查看、关闭房间 |
| 超级管理员 | 强制解散（需审批） |

---

## 3. 前置条件

- 用户已登录（游客只读）。
- WebSocket 连接已建立（见 [13 章](./13-模块04-WebSocket.md)）。
- Redis 可用（房间状态存储）。

## 4. 房间生命周期

### 4.1 状态机

```
                    ┌──────────┐
     创建房间 ──────>│  活跃     │
                    │ status=1 │
                    └────┬─────┘
                         │
        ┌────────────────┼────────────────┬──────────────┐
        │                │                │              │
   房主关闭          房主解散         超时无活跃       超管强制解散
        │                │                │              │
        ▼                ▼                ▼              ▼
  ┌──────────┐    ┌──────────┐     ┌──────────┐   ┌──────────┐
  │ 已关闭    │    │ 已解散    │     │ 已解散    │   │ 已解散    │
  │ status=2 │    │ status=3 │     │ status=3 │   │ status=3 │
  └──────────┘    └──────────┘     └──────────┘   └──────────┘
       │
   房主可重新开启（24h 内）
       │
       ▼
  ┌──────────┐
  │  活跃     │
  └──────────┘
```

| 状态 | 值 | 说明 | 可加入 | 保留时间 |
|---|---|---|---|---|
| 活跃 | 1 | 正常运营 | ✅ | — |
| 已关闭 | 2 | 房主主动关闭（暂时） | ❌ | 24h 内可重开，之后自动转解散 |
| 已解散 | 3 | 永久解散 | ❌ | 数据保留 30 天后归档 |

### 4.2 生命周期规则

- `BR-14-001`：**无活跃超过 7 天**的房间自动解散（定时任务，解散前 1 天站内通知房主）。
- `BR-14-002`：关闭状态超过 24 小时未重开，自动转解散。
- `BR-14-003`：解散时：清理全部 Redis Key（`ml:room:*:{roomId}`）、断开所有 WS 连接、通知所有成员、成员关系标记 `deleted=1`。
- `BR-14-004`：解散后房间号**不可复用**（`room_no` 保留，避免用户困惑）。
- `BR-14-005`：房间数据（消息、礼物）保留 30 天后归档到冷存储。

## 5. 功能需求明细

### FR-14-001 创建房间 【P0】

| 项 | 内容 |
|---|---|
| **功能目标** | 用户创建自己的音乐房并成为房主 |
| **使用角色** | 普通用户（登录） |
| **前置条件** | 已登录；当日创建次数未超限 |

**操作流程**：

1. 用户点击"创建房间" → 弹出表单。
2. 填写：房间名（必填）、封面（可选）、类型（公开/私密/密码）、密码（类型=密码时必填）、公告（可选）、主题标签（可选）、麦位数（4/6/8/12）、人数上限（50/100/200/500）、播放模式（房主控播/自由播放/投票切歌）、点歌是否需审核。
3. 提交 → 服务端校验 → 生成房间号（6 位数字）→ 落库 → 自动加入并成为房主 → 建立 WS 连接 → 跳转房间页。
4. 返回房间号，便于分享。

**业务规则**：

- `BR-14-006`：房间名 1-30 字符，需过敏感词校验。
- `BR-14-007`：房间号 6 位数字，全局唯一，从 100000 起递增分配（Redis `INCR ml:room:no_seq`，冲突则重试）。避免使用连续易猜的（可加随机扰动）。
- `BR-14-008`：密码房密码 4-16 位，用 **BCrypt** 存储，**不可明文保存**。
- `BR-14-009`：创建配额：普通用户每日 3 个房间，总上限 10 个活跃房间。
- `BR-14-010`：新创建的房间初始 `status=1`，`online_count=1`，房主自动上 1 号麦（房主专属位）。
- `BR-14-011`：创建后自动创建 `t_room_mic` 麦位记录（按麦位数初始化）。
- `BR-14-012`：房间封面默认使用房主头像或系统默认图。
- `BR-14-013`：`room_type=2(私密)` 时不出现在房间列表，仅通过房间号/邀请进入。

**异常情况**：

| 编号 | 场景 | 处理 |
|---|---|---|
| `EX-14-001-1` | 房间名含敏感词 | 返回 `50002`，提示修改 |
| `EX-14-001-2` | 超过创建配额 | 返回专属错误码，提示上限 |
| `EX-14-001-3` | 用户已被封禁 | `40102`，不允许创建 |
| `EX-14-001-4` | 房间号分配冲突 | 自动重试（最多 5 次），仍失败返回 `90001` |
| `EX-14-001-5` | 落库成功但 WS 连接失败 | 房间已创建，提示"房间已创建，请刷新重试"；房间 5 分钟后无人在线自动关闭 |
| `EX-14-001-6` | 创建过于频繁 | 限流（3 次/小时） |

**验收标准**：

- `AC-14-001-1`：创建成功后自动成为房主并上 1 号麦
- `AC-14-001-2`：房间号 6 位数字且唯一
- `AC-14-001-3`：密码房的密码在 DB 中为 BCrypt 密文
- `AC-14-001-4`：创建第 4 次（同日）被拒绝
- `AC-14-001-5`：私密房间不出现在房间列表中
- `AC-14-001-6`：创建耗时 ≤ 500ms

### FR-14-002 加入房间 【P0】

| 项 | 内容 |
|---|---|
| **功能目标** | 用户进入房间收听与互动 |
| **使用角色** | 游客（只读）/ 登录用户 |
| **前置条件** | 房间存在且 `status=1` |

**操作流程**：

1. 用户从列表/房间号/邀请链接进入 `/room/{roomNo}`。
2. 前端建立 WS 连接（若未建立）。
3. 发送 `room.join {roomId}`。
4. 服务端校验：房间状态 → 是否满员 → 黑名单 → 密码（如需要）→ 是否被封禁。
5. 校验通过 → 加入在线集合 → 落库 `t_room_member`（首次）或更新 `last_enter_time` → 本地订阅 → 读取权威播放态。
6. 返回 `room.join.ack`（含房间快照：房间信息、当前播放、成员列表、麦位、队列、公告、我的角色与权限）。
7. 广播 `room.member.join` 给其他成员。

**加入校验顺序（短路）**：

```
1. 房间是否存在 → 40001
2. 房间是否为活跃 → 40001
3. 是否在黑名单 → 40004
4. 是否满员 → 40002
5. 是否为密码房且未验证 → 40003（返回 needPassword=true）
6. 用户是否被封禁 → 40102
7. 用户是否已在该房间 → 直接返回快照（幂等）
```

**业务规则**：

- `BR-14-014`：**游客**可加入公开房（只读），`t_room_member` **不记录**游客，仅存于 Redis 在线集合（key 用 `guest:{deviceId}`）。
- `BR-14-015`：**私密房/密码房**：游客不可进入，必须登录。
- `BR-14-016`：密码验证结果缓存 30 分钟（`ml:room:pwd:{roomId}:{userId}`），期间重复进入不重复验证。
- `BR-14-017`：满员判定：`online_count >= max_members` 时拒绝（`online_count` 以 Redis 为准）。
- `BR-14-018`：加入房间**幂等**：已在房内再次 join 直接返回快照，不重复广播。
- `BR-14-019`：被踢出的用户 5 分钟内不可再加入该房间（`ml:room:kick:{roomId}:{userId}` TTL 5min），除非房主解除。
- `BR-14-020`：加入后**自动订阅**房间频道，并把房间加入用户的"最近访问房间"列表（`ml:room:recent:{userId}` ZSet，保留 10 个）。

**异常情况**：

| 编号 | 场景 | 处理 |
|---|---|---|
| `EX-14-002-1` | 房间已解散 | `40001` + 前端跳房间列表 |
| `EX-14-002-2` | 房间满员 | `40002` + 提供"加入等待"选项（P2） |
| `EX-14-002-3` | 密码错误 | `40003`，允许重试 3 次，超过则 5 分钟锁定 |
| `EX-14-002-4` | 在黑名单 | `40004` |
| `EX-14-002-5` | 被踢出后 5 分钟内 | 拒绝并提示剩余时间 |
| `EX-14-002-6` | WS 未连接就 join | 返回错误，前端先连 WS |
| `EX-14-002-7` | 网络中断 | 客户端重连后自动重新 join |

**验收标准**：

- `AC-14-002-1`：游客可进公开房收听
- `AC-14-002-2`：游客进密码房被拒
- `AC-14-002-3`：满员房间拒绝加入
- `AC-14-002-4`：被踢用户 5 分钟内无法加入
- `AC-14-002-5`：密码验证缓存生效，30 分钟内免重复验证
- `AC-14-002-6`：加入后 500ms 内收到房间快照
- `AC-14-002-7`：重复 join 幂等，不产生重复广播

### FR-14-003 退出房间 【P0】

| 项 | 内容 |
|---|---|
| **功能目标** | 离开房间，释放麦位与在线状态 |
| **使用角色** | 房间成员 |

**操作流程**：

1. 用户点击"退出"或关闭页面 → 发送 `room.leave`。
2. 服务端：下麦（释放麦位）→ 移出排麦队列 → 移出在线集合 → 取消本地订阅 → 更新 `t_room_member.total_duration`。
3. 广播 `room.member.leave` 给其他成员。
4. 若退出者是房主 → 触发**房主交接逻辑**（见 FR-14-009）。

**业务规则**：

- `BR-14-021`：退出时**必须释放麦位**，队列中下一位如有则自动递补（可配置）。
- `BR-14-022`：退出时累计停留时长（`now - join_time`）写入 `t_room_member.total_duration`。
- `BR-14-023`：异常断开（未发 leave）时，由心跳超时（90s）触发相同的清理逻辑。
- `BR-14-024`：房主退出时，按 `房间角色优先级 + 贡献值 + 加入时间` 顺序，自动转让给房管或最早的活跃成员。
- `BR-14-025`：房间内最后一人退出 → 房间进入"空房"状态，30 分钟后若无人进入则自动关闭（`status=2`），24 小时后转解散。

**异常情况**：

| 编号 | 场景 | 处理 |
|---|---|---|
| `EX-14-003-1` | 退出时 Redis 不可用 | 记录待清理，后台任务补偿 |
| `EX-14-003-2` | 房主异常断开 | 60s 内未重连则自动转让房主 |
| `EX-14-003-3` | 最后一人为房主且退出 | 触发转让；无其他成员则房间转空房状态 |

**验收标准**：

- `AC-14-003-1`：退出后在线列表移除该用户
- `AC-14-003-2`：退出后麦位被释放并可被他人占用
- `AC-14-003-3`：房主退出后房主自动转让给房管
- `AC-14-003-4`：停留时长被正确累计

### FR-14-005 麦位管理 【P0】

| 项 | 内容 |
|---|---|
| **功能目标** | 管理房间麦位（排麦出歌的展示位） |
| **使用角色** | 全员（申请）、房主/房管（管理） |

**麦位规则**：

| 麦位 | 归属 | 说明 |
|---|---|---|
| 1 号麦 | 房主专属 | 房主固定占用，不可被抢占 |
| 2 号麦 | 房管优先 | 空置时任何人可上 |
| 3~N 号麦 | 自由 | 先到先得或按排麦顺序 |

**上麦方式**：

| 方式 | 说明 | 配置项 |
|---|---|---|
| 自由上麦 | 点击空麦位直接上麦 | `room.allow_apply=1` 且无审核 |
| 排麦上麦 | 加入队列，按序上麦（由房主/房管批准或自动） | 默认 |
| 房主指派 | 房主直接把用户拉上麦 | 房主特权 |

**操作流程（排麦上麦）**：

1. 用户点击"申请上麦" → 加入 `ml:room:mic:queue:{roomId}` ZSet（score = 递增序号）。
2. 落库 `t_room_queue`（`queue_type=1`）。
3. 广播 `room.queue.update` 给全员。
4. 房主/房管审批：
   - **批准** → 分配空麦位 → 更新 `t_room_mic` → 移出队列 → 广播 `room.mic.update` + `room.queue.update`。
   - **拒绝** → 状态置 `2` → 通知申请人。
5. 自动模式（`need_approve=0`）：有空位时自动上麦。

**业务规则**：

- `BR-14-031`：同一用户**同时只能占一个麦位**。
- `BR-14-032`：麦位满时，申请者进入等待队列，有人下麦则自动递补（可配置是否自动）。
- `BR-14-033`：麦位队列上限 50 人，超出拒绝。
- `BR-14-034`：重复申请同一房间返回 `40009`（已在队列中）。
- `BR-14-035`：用户**离开房间**时自动下麦并移出队列。
- `BR-14-036`：房主可"锁定"麦位（`status=2`），锁定期间不可被占用。
- `BR-14-037`：麦位分配使用**分布式锁** `ml:lock:room:mic:{roomId}`，防止并发抢占同一麦位。
- `BR-14-038`：用户上麦时校验：未被禁言、非黑名单、在房内。
- `BR-14-039`：单个用户排队等待超 30 分钟自动取消（防止僵尸队列）。

**异常情况**：

| 编号 | 场景 | 处理 |
|---|---|---|
| `EX-14-005-1` | 麦位已满 | `40008`，提示加入排队 |
| `EX-14-005-2` | 并发抢同一麦位 | 分布式锁保证只有一个成功，另一个返回 `40008` |
| `EX-14-005-3` | 队列已满（50 人） | 拒绝加入队列 |
| `EX-14-005-4` | 用户已被禁言 | 拒绝上麦 |
| `EX-14-005-5` | 上麦后被禁言 | 自动下麦 |
| `EX-14-005-6` | 房主下麦 | 房主位（1 号麦）保留，房主可随时回位 |

**验收标准**：

- `AC-14-005-1`：50 人同时申请上麦，麦位分配无冲突
- `AC-14-005-2`：重复申请返回 `40009`
- `AC-14-005-3`：下麦后队列首位自动递补
- `AC-14-005-4`：离开房间自动下麦
- `AC-14-005-5`：房主位不被他人占用

### FR-14-006 禁言 / 踢人 / 黑名单 【P0】

| 项 | 内容 |
|---|---|
| **功能目标** | 维护房间秩序 |
| **使用角色** | 房主 / 房管（禁言、踢人）、房主（黑名单） |

**禁言**：

| 项 | 规则 |
|---|---|
| 时长选项 | 5 分钟 / 30 分钟 / 1 小时 / 24 小时 / 永久（永久仅房主） |
| 效果 | 不可发言、不可发弹幕、不可申请上麦；**仍可收听** |
| 存储 | `ml:room:mute:{roomId}` Hash（userId → 到期时间戳）+ `t_room_member.mute_status/mute_until` |
| 解除 | 自动到期（定时清理）/ 房主手动解除 |
| 通知 | 被禁言者收到 `room.member.update` + 站内通知 |

**踢人**：

| 项 | 规则 |
|---|---|
| 效果 | 强制断开房间连接、移出在线集合、释放麦位、移出队列 |
| 冷却 | 被踢后 5 分钟内不可再加入（`ml:room:kick:{roomId}:{userId}`） |
| 通知 | 被踢者收到 `room.kicked`（含原因）+ 站内通知 |
| 广播 | 全员收到 `room.member.leave` |

**黑名单**：

| 项 | 规则 |
|---|---|
| 效果 | 永久禁止加入该房间（除非移除） |
| 上限 | 200 人/房 |
| 存储 | `ml:room:blacklist:{roomId}` Set + `t_room_member.room_role=9` |
| 权限 | 仅房主可操作 |

**业务规则**：

- `BR-14-040`：房主**不可**被禁言/踢出（`BR-14-027`）。
- `BR-14-041`：房管**不可**禁言/踢出其他房管。
- `BR-14-042`：禁言/踢人操作记录到房间操作日志（`t_room_message` type=3 系统消息）。
- `BR-14-043`：被禁言用户尝试发言，返回 `room.chat.rejected` reason=`muted`。
- `BR-14-044`：禁言到期自动解除（XXL-Job 每分钟扫描 + 请求时惰性校验双重保障）。
- `BR-14-045`：踢人需二次确认（前端），且必填原因。
- `BR-14-046`：黑名单用户尝试进入返回 `40004`。
- `BR-14-047`：房主可将黑名单用户移出黑名单。

**异常情况**：

| 编号 | 场景 | 处理 |
|---|---|---|
| `EX-14-006-1` | 房管禁言房主 | `40007` 拒绝 |
| `EX-14-006-2` | 房管禁言其他房管 | 拒绝（`40006`） |
| `EX-14-006-3` | 黑名单已满 200 | 拒绝，提示清理 |
| `EX-14-006-4` | 重复拉黑 | 幂等成功 |
| `EX-14-006-5` | 被禁言用户重连 | 禁言状态从 Redis 恢复并继续生效 |
| `EX-14-006-6` | 踢人时用户已离线 | 仍记录踢出与冷却 |

**验收标准**：

- `AC-14-006-1`：被禁言用户无法发言，提示剩余时间
- `AC-14-006-2`：房管无法禁言房主（`40007`）
- `AC-14-006-3`：被踢用户 5 分钟内无法加入
- `AC-14-006-4`：禁言到期自动解除
- `AC-14-006-5`：黑名单用户无法进入
- `AC-14-006-6`：禁言状态在断线重连后保持

### FR-14-007 播放队列与控播 【P0】

| 项 | 内容 |
|---|---|
| **功能目标** | 房主控制房间内播放，成员可点歌 |
| **使用角色** | 房主/房管（控播）、成员（点歌申请） |

**播放模式**：

| 模式 | 值 | 说明 |
|---|---|---|
| 房主控播 | 1 | 只有房主/房管可操作播放，成员只能收听（默认） |
| 自由播放 | 2 | 每个成员本地独立播放，不强制同步（房间变成"歌单广场"） |
| 投票切歌 | 3 | 成员可发起投票切歌，达到阈值自动切歌 |

**播放队列**：

```
ml:room:queue:{roomId}   List [{songId, addBy, addTime, source}]
```

| 来源 | 说明 |
|---|---|
| 房主添加 | 直接入队 |
| 成员点歌 | 需审核（`need_approve=1`）或直接入队 |
| 排麦用户出歌 | 上麦用户自动播放其点歌 |
| 系统推荐 | 队列空时自动补位（可配置） |

**操作流程（成员点歌）**：

1. 成员在房间内搜索或从歌单选择歌曲 → 点击"点歌"。
2. 提交 `POST /room/{roomId}/queue`，body `{songId}`。
3. 若 `need_approve=1` → 进入待审队列，广播 `room.queue.update`（待审区）。
4. 房主/房管审核 → 通过则加入正式队列并广播；拒绝则通知点歌者。
5. 队列更新广播给全员。

**业务规则**：

- `BR-14-048`：队列长度上限 100 首。
- `BR-14-049`：同一用户排队点歌上限 3 首。
- `BR-14-050`：队列为空且播放结束时，自动切换到"推荐补位"（从房间主题标签推荐）或停止播放。
- `BR-14-051`：房主可删除队列中任意歌曲、调整顺序、清空队列。
- `BR-14-052`：控播操作需通过分布式锁 `ml:lock:room:play:{roomId}` 串行化。
- `BR-14-053`：投票切歌：发起者创建投票（`ml:room:vote:{roomId}`），有效期 60s；**同意率 ≥ 60% 且同意数 ≥ 3** 则切歌；投票期间不可重复发起。
- `BR-14-054`：切歌时保留"当前歌曲已播放时长"记录，用于计算完播/跳过埋点。
- `BR-14-055`：队列中歌曲被下架/无版权时，自动跳过并提示。

**异常情况**：

| 编号 | 场景 | 处理 |
|---|---|---|
| `EX-14-007-1` | 队列已满 | 拒绝，提示队列已满 |
| `EX-14-007-2` | 普通成员尝试控播 | 忽略 + 错误提示 |
| `EX-14-007-3` | 点歌歌曲无版权 | 拒绝并提示 |
| `EX-14-007-4` | 队列中歌曲被下架 | 自动移除并跳过 |
| `EX-14-007-5` | 房主长时间不切歌（单曲循环） | 无强制干预；成员可发起投票切歌（模式 3） |
| `EX-14-007-6` | 并发控播指令 | 分布式锁 + version 保证顺序 |

**验收标准**：

- `AC-14-007-1`：成员点歌经审核后进入队列
- `AC-14-007-2`：队列满（100 首）时拒绝
- `AC-14-007-3`：房主可删除队列歌曲并即时广播
- `AC-14-007-4`：投票切歌达成阈值后自动切歌
- `AC-14-007-5`：队列播完后自动推荐补位或停止

### FR-14-009 房主转让与交接 【P1】

| 项 | 内容 |
|---|---|
| **功能目标** | 房主角色可转移，房主意外离线时可自动交接 |
| **使用角色** | 房主 |

**手动转让**：

1. 房主在成员列表选择目标用户 → 点击"转让房主"。
2. 二次确认（提示不可撤销）。
3. 服务端：目标用户 `room_role=2`，原房主 `room_role=0`（或保留房管身份，可配置）。
4. 广播 `room.member.update` × 2。
5. 记录操作日志 + 站内通知双方。

**自动交接（房主长时间离线）**：

```
房主断开连接
  → 60s 内未重连
  → 按优先级选择新房主：
     1) 贡献值最高的房管
     2) 最早加入的房管
     3) 贡献值最高的成员
     4) 最早加入的成员
  → 若无其他成员：房间进入空房状态，等待房主重连
  → 广播房主变更 + 站内通知
```

**业务规则**：

- `BR-14-061`：转让目标必须在房间内且非黑名单。
- `BR-14-062`：转让后原房主默认降为房管（可选保留），可在转让时选择。
- `BR-14-063`：自动交接仅在房主离线 **超过 60s** 时触发，避免短暂抖动导致误交接。
- `BR-14-064`：自动交接每天每房间最多 3 次，防止频繁交接。
- `BR-14-065`：房主在离线期间重连，若已交接则不自动夺回（避免混乱），但可请求新房主转回。
- `BR-14-066`：转让/交接均记录到 `t_room_message` 系统消息 + 操作日志。

**异常情况**：

| 编号 | 场景 | 处理 |
|---|---|---|
| `EX-14-009-1` | 目标用户已离开房间 | 拒绝，提示刷新成员列表 |
| `EX-14-009-2` | 房间内无其他成员 | 保持房主不变，等待重连 |
| `EX-14-009-3` | 转让瞬间目标用户离线 | 仍可转让（下次上线生效） |
| `EX-14-009-4` | 频繁自动交接 | 超过 3 次/天则停止并告警 |

**验收标准**：

- `AC-14-009-1`：手动转让后新房主拥有全部房主权限
- `AC-14-009-2`：房主离线 60s 后自动交接给房管
- `AC-14-009-3`：短暂抖动（< 60s）不触发交接
- `AC-14-009-4`：交接后原房主不自动夺回

### FR-14-010 房间关闭 / 解散 【P0】

| 项 | 内容 |
|---|---|
| **功能目标** | 房主管理房间的存续 |
| **使用角色** | 房主（关闭/解散）、超管（强制解散） |

**关闭 vs 解散**：

| 操作 | 状态 | 可恢复 | 成员处理 | 数据 |
|---|---|---|---|---|
| 关闭 | `status=2` | 24h 内可重开 | 断开连接、清在线 | 保留全部 |
| 解散 | `status=3` | ❌ | 断开 + 通知 | 30 天后归档 |

**操作流程（解散）**：

1. 房主点击"解散房间" → 二次确认（输入房间名确认，防误操作）。
2. 服务端校验房主身份。
3. 广播 `room.closed` 给全员（含解散原因）。
4. 等待 3 秒（让前端展示提示）。
5. 清理：删除全部 `ml:room:*:{roomId}` Key、断开所有 WS 订阅、`t_room_member` 标记删除、`t_room.status=3`。
6. 通知所有成员（站内通知）。

**业务规则**：

- `BR-14-067`：解散**不可恢复**，需二次确认（输入房间名）。
- `BR-14-068`：解散时**先广播后清理**（顺序不可颠倒，否则用户无感知）。
- `BR-14-069`：解散后房间号不可复用。
- `BR-14-070`：超管强制解散需走审批流程（`t_approval`），需填写理由，记录敏感操作日志。
- `BR-14-071`：房间被平台关闭（违规）时，向房主发送违规原因与申诉入口。

**异常情况**：

| 编号 | 场景 | 处理 |
|---|---|---|
| `EX-14-010-1` | 清理过程中 Redis 异常 | 重试 + 后台补偿任务 |
| `EX-14-010-2` | 部分用户清理失败 | 后台任务扫描并清理孤儿订阅 |
| `EX-14-010-3` | 超管无审批强制解散 | `40303` 拒绝 |
| `EX-14-010-4` | 房主解散时有无成员在线 | 正常解散，无需广播 |

**验收标准**：

- `AC-14-010-1`：解散后所有成员收到通知并被移出
- `AC-14-010-2`：解散后房间相关的 Redis Key 全部清除
- `AC-14-010-3`：关闭的房间 24h 内可重开，之后自动解散
- `AC-14-010-4`：超管强制解散需审批

## 8. 高并发与性能设计

| 场景 | 设计 |
|---|---|
| 500 人房间广播 | RocketMQ 广播模式 + 本机订阅表过滤（见 [13 章 FR-13-007](./13-模块04-WebSocket.md)） |
| 在线数高频读 | Redis String 缓存（Set 变更同步） |
| 麦位并发抢 | 分布式锁 `ml:lock:room:mic:{roomId}` |
| 控播并发 | 分布式锁 `ml:lock:room:play:{roomId}` + version 单调递增 |
| 热房间（> 1000 人） | 分级：热门房间独立 Topic，避免大范围广播 |
| 心跳风暴 | 心跳间隔 30s + 随机抖动 ±5s |
| 消息存储 | 房间消息**按月分表**，且**只落库不保证完整**（过载可丢弹幕） |

**容量预估**：

```
假设 1000 个活跃房间，平均 50 人在线：
- WS 连接数 = 50000 → 5 个 WS 实例（每实例 1 万连接）
- 房间状态 Redis 内存 = 1000 × 10KB = 10MB
- 消息广播 QPS 峰值 = 1000 房间 × 5 条/秒 = 5000 条/秒 → RocketMQ 单 Topic 可承载
- 房间消息落库 = 5000 条/秒 → 需分表 + 异步批量写
```

## 9. 弱网与异常处理

| 场景 | 处理 |
|---|---|
| 客户端网络差 | 优先保证音频流畅：降低弹幕频率、合并消息、关闭非关键广播 |
| 客户端重连 | 重连后重新 join 并拉取增量消息（`sinceId`） |
| 服务端推送积压 | 慢连接断开（弹幕可丢） |
| 音频加载慢 | 允许最多 5s 追赶，超过则直接 seek 到权威位置 |
| 断线超过 5 分钟 | 视为离开房间，释放麦位 |
