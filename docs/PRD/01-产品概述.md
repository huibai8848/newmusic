## 1. 项目背景

### 1.1 行业背景

在线音乐市场已进入**存量竞争**阶段，主流平台（QQ音乐、网易云音乐、Spotify）已解决"听歌"这一基础需求。差异化的机会在于：

1. **社交化听歌** — 从"一个人戴耳机"转向"一群人同时听、同时聊"，音乐房（类似一起听/语音房）显著提升停留时长。
2. **AI 原生交互** — 用户不再满足于点选分类，而是用自然语言表达场景与情绪（"适合跑步的周杰伦快歌"），需要 AI 理解意图并直接给出结果。
3. **可解释推荐** — 用户对"算法的黑箱"信任度低，需要"因为你收藏了周杰伦"这类理由，并保留负反馈入口。

### 1.2 项目定位

**MusicLive** 是一个 Web 端在线音乐社交平台，同时提供三条主线能力：

| 主线 | 能力 | 用户价值 |
|---|---|---|
| **听（Listen）** | 曲库播放、歌词、音质、离线、跨端同步 | 稳定、高质量的音乐消费体验 |
| **聊（Social）** | 音乐房实时互动、私信、动态、关注、评论 | 从孤立消费到群体共鸣 |
| **懂（AI）** | AI 搜索、AI 推荐、AI 歌单、歌词翻译/摘要、情绪识别、哼唱识曲 | 降低发现成本，提升匹配精度 |

### 1.3 与竞品的差异点

| 维度 | 主流平台 | MusicLive 差异化 |
|---|---|---|
| 音乐房 | 少数有，功能封闭 | **开放麦位+投票点歌+房榜单**，房主可自定义规则 |
| 搜索 | 关键词为主 | **自然语言 AI 搜索 + 意图解释**，支持场景/情绪/年代复合条件 |
| 推荐 | 黑箱 | **推荐理由可解释 + 一键反馈**（喜欢/不感兴趣/屏蔽歌手） |
| 歌词 | 静态滚动 | **逐字歌词 + 多语言翻译 + AI 摘要 + 情绪标注** |
| 数据 | 仅运营可见 | **用户可见个性化听歌年报/画像**（P2） |

### 2.2 用户目标

| 编号 | 目标 | 说明 |
|---|---|---|
| U-01 | 3 秒内开始听歌 | 首页 → 播放 ≤ 3 次交互、≤ 3s 加载 |

| U-03 | 房间内无感同步 | 播放进度偏差 ≤ 1.5s |
| U-04 | 推荐可理解可控 | 100% 推荐结果带理由或可反馈 |

### 2.3 北极星指标

> **北极星指标：日有效播放用户数（DAU-Play）**
> 定义：当日播放时长 ≥ 30 秒 且 播放曲目数 ≥ 3 的独立用户数。

**指标分解树**：

```
DAU-Play
├── 新用户转化
│   ├── 注册转化率（访客→注册）
│   └── 首日播放转化率（注册→首播）
├── 留存
│   ├── 次日留存 D1
│   ├── 7 日留存 D7
│   └── 30 日留存 D30
├── 频次
│   ├── 人均日播放曲目数
│   └── 人均日播放时长（分钟）
└── 社交放大
    ├── 音乐房参与率
    └── 社交行为渗透率（评论/收藏/分享）
```

## 3. 目标用户画像

### 3.1 核心用户群

| 画像 | 占比预估 | 特征 | 核心诉求 | 对应功能 |
|---|---|---|---|---|
| **学生党（Z 世代）** | 40% | 16-24 岁，时间碎片化，社交活跃，价格敏感 | 一起听、找同好、个性歌单 | 音乐房、动态、关注、免费音质 |
| **通勤白领** | 30% | 25-35 岁，早晚通勤听歌，注重场景 | 场景歌单、离线缓存、跨端续播 | 场景推荐、离线、跨设备同步 |
| **音乐发烧友** | 15% | 25-40 岁，追求音质与曲库深度 | 无损音质、均衡器、逐字歌词 | 音质切换、音效、歌词增强 |

```
                          ↓                   ↓
                    个人听歌路径          社交路径

                    ├ 离线下载            ├ 发布动态

                                                    ↓
                                            内容审核 / 举报

                                            留存 / 分享裂变
```

## 4. 产品范围

### 4.1 范围内（In Scope）

| 端 | 范围 |
|---|---|
| **PC Web** | 全部 C 端页面 + 后台管理（React 18 + TS + Vite） |
| **移动 Web / PWA** | 响应式适配 + 可安装 PWA（模块 21） |
| **后端服务** | Spring Boot 单体（模块化分层），预留微服务拆分 |
| **管理后台** | 平台管理、审核、运营配置、数据看板 |
| **基础设施** | Redis / MySQL / ES / MQ / Milvus / 监控体系 |

### 4.2 范围外（Out of Scope，本期明确不做）

| 不做项 | 原因 | 后续规划 |
|---|---|---|
| 原生移动 App（iOS/Android） | 资源投入大，先验证 Web | V3.0 评估 |
| 用户自助上传音频 | 版权风险极高 | 仅管理员上传，长期评估 |
| 实时语音/视频连麦 | 需 RTC 基础设施（TRTC/Agora），成本高 | V2.0 评估（假设 A-09） |
| 直播打赏/礼物提现 | 涉及支付牌照与结算 | 一期仅做虚拟礼物展示（模块 22） |
| 完整支付/会员体系 | 需资质与合规 | 预留字段，不上线（假设 A-05） |
| 社交关系链导入（微信/QQ） | 需第三方授权与审核 | V2.0 |
| 多语言国际化（i18n） | 一期仅中文 | V2.0 |

### 4.3 明确的产品红线

1. **版权合规优先** — 无授权音频不进入 `public` 状态（`copyright_status` 强校验）。
2. **未成年人保护** — 注册需勾选年龄承诺；音乐房禁止涉黄涉政内容；敏感词库强制生效。
3. **数据合规** — 手机号、身份证等敏感字段加密存储；用户可申请注销与数据导出。
4. **内容可追溯** — 所有 UGC 内容留存操作日志与审核记录，满足监管回溯要求。

## 5. 核心业务流程（端到端）

### 5.1 流程一：游客 → 首播

```
1. 游客访问首页 (/)
2. 系统返回：轮播推荐 + 热门歌曲 + 热门歌单（游客可读，走 Redis 缓存）
3. 游客点击某歌曲 → 前端调用 /api/v1/player/url?songId=x 获取播放地址
4. 后端校验：歌曲状态=上架 且 版权状态=已授权 且 音质可用
5. 后端返回 30 秒试听地址（游客降级策略）+ 播放 token
6. 前端播放，埋点上报 play_start
7. 播放至 30s → 弹出注册引导（"登录畅听全曲"）
8. 游客注册 → 自动登录 → 恢复播放全曲 + 播放进度续接
```

### 5.2 流程二：用户进入音乐房并排麦

```
1. 用户从房间列表点击进入 → 建 WebSocket 连接 + 加入房间频道
2. 服务端下发：房间信息、公告、当前播放（含权威进度+时间戳）、在线成员、麦位队列
3. 客户端播放器对齐服务端进度（见 14 章进度校准算法）
4. 用户点击"上麦申请" → 进入排麦队列（Redis ZSet 按序号）
5. 房主/房管审批 → 用户上麦 → 全员广播麦位变更
6. 用户可在麦上点歌 → 进入房间播放队列（可配置为房主审核/自动通过）
7. 用户可聊天/发弹幕 → WebSocket 广播（走敏感词过滤，见 27 章）
8. 直播/收听过程中，按房间热度上报心跳
9. 退出房间 → 释放麦位 → 清理在线集合 → 广播离开
```

### 5.3 流程三：AI 搜索

```
1. 用户输入自然语言："适合跑步的周杰伦快歌"
2. 后端 AI 搜索管道：
   a. 意图识别（LLM）→ 意图=找歌，情绪=活力，场景=运动
   b. 关键词抽取 → 实体：歌手=周杰伦；属性：快节奏（BPM 高）；场景=跑步
   c. 条件补全 → 补全 BPM>120、风格=流行/说唱、时长<5min
   d. 检索：ES 结构化过滤 + 标签召回；不足则向量召回补齐
   e. 排序：BM25 + 热度 + 与意图匹配度 + 大模型精排
   f. 结果解释生成 → "为你筛选了周杰伦节奏较快的歌曲，适合跑步时听"
3. 返回：歌曲列表 + 解释 + 可调整的筛选标签（用户可点掉"快歌"条件）
4. 埋点：ai_search_query / ai_search_result_click
```

### 5.4 流程四：内容违规处置

```
1. 用户发布评论/动态/私信/房间发言
2. 同步过滤：DFA 敏感词（本地词库，含变体/拼音识别）→ 命中则拦截/替换
3. 异步审核：投递 MQ → AI 审核（文本/图片/音频分类）→ 返回风险分
4. 风险分 ≥ 阈值 → 进入人工复审队列（admin 待办）
5. 人工判定：通过 / 拒绝 / 封禁 / 警告
6. 用户收到处理结果通知；若为封禁则触发权限失效（Redis 会话清除）
7. 全过程记录审核日志（审核人、时间、依据、原文快照）
8. 用户可申诉 → 申诉进入复审队列（升级给超级管理员）
```

## 7. 关键产品决策（ADR 摘要）

| 编号 | 决策 | 理由 | 替代方案 |
|---|---|---|---|
| PD-01 | 一期采用**模块化单体**而非微服务 | 团队规模小、迭代快、运维成本低；模块边界清晰，为拆分预留 | 直接微服务（否决：过早优化） |
| PD-02 | 音乐房一期为"**排麦出歌**"而非实时语音 | 实时语音需 RTC，成本与合规门槛高 | 接入第三方 RTC（V2.0 评估） |
| PD-03 | 大模型采用 **SPI 可插拔 + OpenAI 兼容协议** | 避免厂商锁定，便于切换/降级 | 硬编码单一厂商（否决） |
| PD-04 | 搜索以 **ES + IK** 为主，向量库为辅 | ES 生态成熟，IK 中文分词效果好；向量用于 AI 搜索补充 | 纯向量检索（召回精度不足） |
| PD-05 | 播放器采用 **HTML5 Audio + 全局 Store** | 实现简单、跨页面持续播放可控 | Web Audio API（复杂，仅音效用） |
| PD-06 | 敏感词采用 **本地 DFA + 远程词库热更新** | 低延迟、可离线、可动态更新 | 纯远程服务（否决：延迟高） |
| PD-07 | 埋点一期走 **MQ → ClickHouse**，MySQL 存汇总 | 写入量大，OLAP 更适合分析 | 直接写 MySQL（否决：写放大） |
