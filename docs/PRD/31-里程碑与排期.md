**排期假设**：

- 团队齐备（见 3.1），无重大人员变动。
- 需求在 V0.2 开始前基本冻结（V1.0 之后允许小范围变更）。
- 版权与音频源在 V0.2 结束前解决（**最大风险**，见 6）。
- 无跨团队强依赖阻塞。

## 2. 里程碑详细规划

### 2.1 V0.1 工程骨架（2 周）

**目标**：搭建可开发、可测试、可部署的骨架，让团队"第一天就能写业务代码"。

| 里程碑 | 内容 | 交付物 | 完成标准 |
|---|---|---|---|
| **M0.1 工程分层**（第 1 周） | Maven 多模块或单模块分包、统一响应、全局异常、错误码、Swagger | 工程骨架代码 | 启动无报错，Swagger 可访问 |
| **M0.2 数据层**（第 1 周） | MySQL 建表脚本、MyBatis-Plus 配置、逻辑删除、乐观锁、雪花 ID、Long→String 序列化 | DDL 脚本 + 配置 | 单表 CRUD 跑通 |
| **M0.3 鉴权**（第 2 周） | Spring Security + JWT（RS256）、RBAC 框架、UserContext | 鉴权模块 | 登录 → 带 token 访问受保护接口 |
| **M0.4 中间件接入**（第 2 周） | Redis、RocketMQ、ES 接入与健康检查 | 中间件配置 | 各中间件连通性验证通过 |
| **M0.5 前端骨架**（第 2 周） | Vite + React + TS + AntD + 路由 + Axios 封装 + Zustand + 全局布局 | 前端骨架 | 页面可跳转、接口可调通 |
| **M0.6 DevOps**（第 2 周） | Docker Compose（本地一键起）、CI 流水线、镜像构建 | Dockerfile + CI 配置 | 提交代码自动构建通过 |
| **M0.7 规范落地**（第 2 周） | 代码规范、提交规范、分支策略、评审流程 | 规范文档 | 团队确认 |

**V0.1 验收（`AC-M0-001`）**：

- 新同学克隆代码后 **1 小时内**能跑起完整本地环境。
- 前端能成功调用后端接口并展示数据。
- CI 通过（编译 + 单测 + 扫描）。
- 部署到 DEV 环境成功。

**风险**：依赖版本冲突（尤其 JDK 8 下 ES/IK/Milvus），**必须在 V0.1 解决**，否则后期代价极高。

### 2.2 V0.2 MVP（8 周）— 能听、能搜、能进房

**目标**：核心闭环可用（听歌 + 搜索 + 音乐房 + 基础社交 + 后台），可对内演示、可小范围试用。

**对应模块**：10（CRUD）、11（前端）、12（Redis）、13（WebSocket）、14（音乐房）、15（搜索，基础）、16（播放歌词）、18（后台，基础）、19（社交基础）、20（IK 分词）

| 里程碑 | 周次 | 内容 | 关键交付 |
|---|---|---|---|
| **M1.1 曲库与用户** | 第 1-2 周 | 歌曲/歌手/专辑/歌单 CRUD、用户体系、管理后台（用户/歌曲管理）、音频上传（管理员） | 可从后台录入歌曲并上传音频 |
| **M1.2 播放内核** | 第 2-3 周 | 播放器（前端）、播放接口、URL 签名、播放记录、基础歌词（LRC） | **可完整播放一首歌**（首个可用闭环） |
| **M1.3 搜索** | 第 3-4 周 | ES 索引、IK 分词、关键词搜索、联想、筛选、排序 | 搜索可用且中文分词正确 |
| **M1.4 基础社交** | 第 4-5 周 | 评论、点赞、收藏、分享、举报 | 歌曲详情页可互动 |
| **M1.5 WebSocket 与房间** | 第 5-7 周 | WebSocket 通道、心跳重连、集群广播、音乐房（创建/加入/麦位/排麦/控播/权限/聊天） | **可多人同房间同步听歌**（核心亮点） |
| **M1.6 后台与运营** | 第 6-7 周 | 管理后台（内容管理、审核基础、推荐位配置、基础看板） | 运营可配置与查看 |
| **M1.7 联调、优化、测试** | 第 7-8 周 | 全链路联调、性能优化、缺陷修复、UAT、部署 | MVP 版本发布 |

**V0.2 验收（`AC-M0-002`）**：

| 类别 | 标准 |
|---|---|
| 功能 | 10/11/12/13/14/15(基础)/16/18(基础)/19/20 模块的 P0 需求全部验收通过 |
| 性能 | 核心接口 P99 达标（播放 ≤ 200ms、搜索 ≤ 500ms） |
| 稳定性 | 混合场景 1000 QPS 通过 |
| 房间 | 单房间 500 人、同步延迟 ≤ 500ms |
| 安全 | 无高危漏洞，越权测试通过 |
| 质量 | 无 S1/S2 缺陷 |

**V0.2 里程碑演示（Demo Day）**：

> 演示脚本：登录 → 搜索一首歌 → 播放 → 查看歌词 → 创建歌单 → 进入音乐房 → 房主播放 → 其他人同步收听 → 弹幕互动 → 上麦说话 → 评论 → 后台查看数据。

**关键风险**：

- **音频源与版权**（阻断性）：MVP 可先用**内部授权素材/自有内容**演示，**但对外发布前必须解决**。
- WebSocket 集群一致性：需在 M1.5 完成，**这是最容易出大坑的地方**。

### 2.3 V1.0 正式版（8 周）— 推荐与社交

|---|---|---|---|

| **M2.2 AI 搜索与 AI 推荐** | 第 2-4 周 | 自然语言搜索（LLM 解析意图）、AI 场景歌单、推荐理由 | AI 搜索可用 |
| **M2.3 内容安全** | 第 3-5 周 | 敏感词 DFA（12 种绕过）、机审（文本/图片）、人工审核工作台、举报处理、用户处罚、信用分、版权管理 | **内容安全体系可运营** |
| **M2.4 完整社交** | 第 4-6 周 | 私信完整、关注、动态、主页、消息中心、@提醒 | 社交闭环 |
| **M2.5 数据平台基础** | 第 5-7 周 | 埋点体系、核心指标（DAU-Play 等）、实时看板、用户画像基础、留存/漏斗 | 数据可决策 |

| **M2.7 全链路测试与发布** | 第 7-8 周 | 性能压测、安全测试、兼容性、UAT、灰度、正式发布 | **V1.0 上线** |

**V1.0 验收（`AC-M0-003`）**：

| 类别 | 标准 |
|---|---|
| 功能 | 全部 P0 需求验收通过，关键 P1 通过 |
| 性能 | 混合场景 5000 QPS，P99 达标 |
| 可用性 | 核心链路 99.95%（观察一周） |
| 安全 | 渗透测试通过，无高危 |
| 内容安全 | 审核覆盖率 100%，SLA 达标 |
| 合规 | 隐私政策、注销、青少年模式、AI 标识可用 |
| 运维 | 监控告警、降级、灰度、回滚可用并演练 |
| 质量 | 无 S1/S2，缺陷逃逸率 ≤ 5% |

**发布策略**：

```
内测（内部员工 + 白名单）→ 1 周
   ↓
灰度（5% → 25% → 50% → 100%）→ 1 周
   ↓
正式发布
   ↓
发布后 2 周重点观察（指标、反馈、成本）
```

## 5. 关键路径与依赖

### 5.1 关键路径

```
V0.1 工程骨架
   ↓（必须完成，否则无法并行开发）
V0.2 M1.1 曲库与用户
   ↓
V0.2 M1.2 播放内核  ←── 关键路径起点（首个可用闭环）
   ↓
V0.2 M1.3 搜索（可与 M1.4 并行）
   ↓
V0.2 M1.5 WebSocket 与房间  ←── 技术风险最高
   ↓
V1.0 M2.3 内容安全  ←── 合规阻断项（无此项不得上线）
   ↓
V1.0 M2.6 高可用与运维
   ↓
V1.0 发布  ←── 关键里程碑
```

**关键路径上的任务不可延期**，否则整个版本顺延。

### 5.2 外部依赖

| 依赖 | 影响 | 需要时间 | 责任方 | 风险 |
|---|---|---|---|---|

**风险管理办法**：

- **每周风险回顾**：更新风险状态、等级、缓解进展。
- **红色风险每日跟踪**（R-01、R-07）。
- **风险升级机制**：缓解措施无效时升级到项目负责人/管理层。
- **新风险随时登记**（不限于初始清单）。

### 7.3 变更管理

| 变更类型 | 流程 |
|---|---|
| 需求变更 | 提交变更申请 → 影响评估（工期/成本/风险）→ 产品 + 技术评审 → 批准 → 更新 PRD 与排期 |
| 技术方案变更 | 提交 ADR → 架构评审 → 批准 → 更新文档 |
| 发布变更 | 走发布流程（灰度 + 回滚预案） |
| 紧急变更 | 快速审批 + 事后补文档 |

> **需求变更原则**：**变更必须有代价意识**。每次变更需明确"砍掉什么"或"延期多久"，避免无成本变更导致无限蔓延。
