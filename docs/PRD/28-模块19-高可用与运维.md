## 4. 限流、熔断、降级

### FR-28-001 限流 【P0】

| 项 | 内容 |
|---|---|
| **功能目标** | 保护系统不被突发流量击穿 |
| **使用角色** | 系统内部 |

**限流层次**：

| 层 | 维度 | 说明 |
|---|---|---|
| **接入层** | IP / 全局 | Nginx / 网关限流（防 DDoS、爬虫） |
| **应用层** | 接口 / 用户 / 设备 | 单接口 QPS、单用户频率 |
| **服务层** | 下游依赖 | 保护下游（如数据库、LLM） |
| **资源层** | 线程池 / 连接池 | 隔离不同业务 |

**限流算法选型**：

| 算法 | 特点 | 适用 |
|---|---|---|
| **令牌桶（Token Bucket）** | 允许突发 | **推荐**（用户体验好） |
| **漏桶（Leaky Bucket）** | 恒定速率 | 需要严格匀速 |
| **滑动窗口（Sliding Window）** | 精确 | 需要严格限制 |
| **固定窗口** | 简单但有临界问题 | 不推荐 |
| **Sentinel 流控** | 框架化、支持多种 | **推荐**（本项目用 Sentinel） |

**Sentinel 配置示例**：

```java
@Configuration
public class SentinelConfig {

    @PostConstruct
    public void initFlowRules() {
        List<FlowRule> rules = new ArrayList<>();

        // 【1】全局接口 QPS 限流
        FlowRule global = new FlowRule();
        global.setResource("global");
        global.setGrade(RuleConstant.FLOW_GRADE_QPS);
        global.setCount(5000);           // 5000 QPS
        global.setControlBehavior(RuleConstant.CONTROL_BEHAVIOR_DEFAULT); // 快速失败
        rules.add(global);

        // 【2】播放接口限流（核心，配额较高）
        FlowRule play = new FlowRule("play:start");
        play.setGrade(RuleConstant.FLOW_GRADE_QPS);
        play.setCount(2000);
        play.setControlBehavior(RuleConstant.CONTROL_BEHAVIOR_DEFAULT);
        rules.add(play);

        // 【3】搜索接口（中等）
        FlowRule search = new FlowRule("search:query");
        search.setGrade(RuleConstant.FLOW_GRADE_QPS);
        search.setCount(500);
        search.setControlBehavior(RuleConstant.CONTROL_BEHAVIOR_WARM_UP); // 预热
        search.setWarmUpPeriodSec(10);
        rules.add(search);

        // 【4】AI 接口（低，成本保护）
        FlowRule ai = new FlowRule("ai:*");
        ai.setGrade(RuleConstant.FLOW_GRADE_QPS);
        ai.setCount(50);
        ai.setControlBehavior(RuleConstant.CONTROL_BEHAVIOR_RATE_LIMITER); // 匀速排队
        ai.setMaxQueueingTimeMs(3000);
        rules.add(ai);

        // 【5】评论/发动态（防刷）
        FlowRule comment = new FlowRule("comment:create");
        comment.setGrade(RuleConstant.FLOW_GRADE_QPS);
        comment.setCount(200);
        rules.add(comment);

        FlowRule.post = new FlowRule("post:create");
        post.setGrade(RuleConstant.FLOW_GRADE_QPS);
        post.setCount(50);
        rules.add(post);

        // 【6】登录（防暴力破解）
        FlowRule login = new FlowRule("user:login");
        login.setGrade(RuleConstant.FLOW_GRADE_QPS);
        login.setCount(100);
        rules.add(login);

        FlowRuleManager.loadRules(rules);
    }

    /** 热点参数限流：按 userId 限制单用户 */
    @PostConstruct
    public void initParamFlowRules() {
        ParamFlowRule rule = new ParamFlowRule("song:play")
            .setParamIdx(0)                  // 第 0 个参数（userId）
            .setCount(60)                    // 单用户 60 QPS
            .setDurationInSec(1);
        ParamFlowRuleManager.loadRules(Collections.singletonList(rule));
    }
}
```

**用户级限流（Redis + Lua 滑动窗口）**：

```lua
-- KEYS[1]: 限流 key
-- ARGV[1]: 窗口大小（秒）
-- ARGV[2]: 限制次数
-- ARGV[3]: 当前时间戳（毫秒）
-- ARGV[4]: 请求 ID（唯一）

local key = KEYS[1]
local window = tonumber(ARGV[1])
local limit = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local reqId = ARGV[4]

local windowStart = now - window * 1000

-- 移除窗口外的记录
redis.call('ZREMRANGEBYSCORE', key, 0, windowStart)

-- 统计窗口内请求数
local count = redis.call('ZCARD', key)

if count < limit then
    redis.call('ZADD', key, now, reqId)
    redis.call('EXPIRE', key, window + 1)
    return 1   -- 允许
else
    return 0   -- 拒绝
end
```

**业务规则**：

- `BR-28-001`：**所有对外接口必须有全局限流**（防止整体被打挂）。
- `BR-28-002`：**核心接口有独立限流**（不被非核心接口挤占）。
- `BR-28-003`：**限流必须有友好响应**（返回 `429` + `Retry-After` + 明确提示，而非 500）。
- `BR-28-004`：**限流阈值必须可配置**（不硬编码，支持热更新）。
- `BR-28-005`：**限流必须区分正常与异常流量**（正常用户不该被整体限流误伤）。
- `BR-28-006`：**恶意的、明确超限的**：直接拒绝；**偶发的、接近阈值的**：可排队（`WARM_UP`/`RATE_LIMITER`）。
- `BR-28-007`：**白名单**（内部 IP、监控）不受限流。
- `BR-28-008`：**限流触发必须告警**（持续触发说明容量不足或攻击）。
- `BR-28-009`：**限流必须记录**（谁被限流、哪个接口、次数）。
- `BR-28-010`：**分布式限流必须用 Redis**（多实例共享计数），单机限流用 Sentinel（快但全局不准）。
  - **分工**：Sentinel 做**单机 + 集群流控**（支持集群模式），Redis 做**用户维度精细限流**。
- `BR-28-011`：**限流不得影响已建立的连接**（如 WebSocket 已连接用户）。
- `BR-28-012`：**登录接口限流必须按账号 + IP 双维度**（防撞库）。

**异常情况**：

| 编号 | 场景 | 处理 |
|---|---|---|
| `EX-28-001-1` | 超限 | 429 + `Retry-After` |
| `EX-28-001-2` | Redis 不可用 | 降级为单机限流（Sentinel）+ 降阈值（保守） |
| `EX-28-001-3` | 限流规则加载失败 | 使用默认值 |
| `EX-28-001-4` | 误伤正常用户 | 支持临时白名单 |
| `EX-28-001-5` | 限流热点参数超限 | 429，提示"操作过于频繁" |

**验收标准**：

- `AC-28-001-1`：全局限流生效
- `AC-28-001-2`：核心接口独立限流
- `AC-28-001-3`：超限返回 429 且有提示
- `AC-28-001-4`：限流阈值可热更新
- `AC-28-001-5`：用户级限流（Redis 滑动窗口）生效
- `AC-28-001-6`：白名单不受限
- `AC-28-001-7`：限流告警生效
- `AC-28-001-8`：Redis 故障降级单机限流

### FR-28-002 熔断 【P0】

| 项 | 内容 |
|---|---|
| **功能目标** | 下游故障时快速失败，避免级联崩溃 |
| **使用角色** | 系统内部 |

**熔断状态机**：

```
     ┌──────────────┐
     │   CLOSED     │  ← 正常，统计失败率
     │  （关闭）    │
     └──────┬───────┘
            │ 失败率 > 阈值（如 50%）且请求数 > 最小样本（如 20）
            ↓
     ┌──────────────┐
     │    OPEN      │  ← 熔断，直接失败（不调用下游）
     │  （打开）    │
     └──────┬───────┘
            │ 等待时间窗（如 30s）
            ↓
     ┌──────────────┐
     │  HALF_OPEN   │  ← 放行少量请求探测
     │ （半开）     │
     └──────┬───────┘
            │
     成功 → CLOSED（恢复）
     失败 → OPEN（继续熔断，等待时间翻倍）
```

**Sentinel 熔断配置**：

```java
@PostConstruct
public void initDegradeRules() {
    List<DegradeRule> rules = new ArrayList<>();

    // 【1】按异常比例熔断（推荐用于外部依赖）
    DegradeRule llm = new DegradeRule("llm:call");
    llm.setGrade(RuleConstant.DEGRADE_GRADE_EXCEPTION_RATIO);
    llm.setCount(0.5);                  // 异常比例 > 50%
    llm.setTimeWindow(30);               // 熔断 30 秒
    llm.setMinRequestAmount(20);         // 最小请求数 20
    llm.setStatIntervalMs(10000);        // 统计窗口 10 秒
    rules.add(llm);

    // 【2】按慢调用比例熔断
    DegradeRule es = new DegradeRule("es:search");
    es.setGrade(RuleConstant.DEGRADE_GRADE_RT);
    es.setCount(500);                    // RT > 500ms 视为慢调用
    es.setSlowRatioThreshold(0.5);       // 慢调用比例 > 50%
    es.setTimeWindow(20);
    es.setMinRequestAmount(20);
    rules.add(es);

    // 【3】按异常数熔断
    DegradeRule thirdParty = new DegradeRule("audit:third_party");
    thirdParty.setGrade(RuleConstant.DEGRADE_GRADE_EXCEPTION_COUNT);
    thirdParty.setCount(20);             // 10 秒内异常数 > 20
    thirdParty.setTimeWindow(60);
    rules.add(thirdParty);

    DegradeRuleManager.loadRules(rules);
}
```

**熔断对象清单**：

| 下游 | 熔断条件 | 熔断后行为 |
|---|---|---|
| LLM 服务 | 异常率 > 50% | 走 AI 降级（见 [23 章](./23-模块14-AI增强.md)） |
| Elasticsearch | 慢调用比例 > 50% | 降级到 MySQL LIKE 查询（见 [15 章](./15-模块06-AI搜索与AI搜索.md)） |
| 第三方审核 API | 异常数 > 20/10s | 仅用 DFA + 规则 |
| 向量库（Milvus） | 异常率 > 50% | 跳过向量召回 |
| 推荐服务 | 异常率 > 30% | 降级热门榜 |
| 数据平台（埋点） | 异常率 > 50% | 本地缓冲 |
| 对象存储 | 异常率 > 50% | 禁止上传 |
| 短信/邮件 | 异常数 > 10/10s | 停止发送，记录待发 |

**业务规则**：

- `BR-28-013`：**所有跨进程调用必须熔断**（HTTP、RPC、DB、Redis、MQ）。
- `BR-28-014`：**熔断阈值必须基于实测**（不拍脑袋），且可配置。
- `BR-28-015`：**必须有最小请求数**（避免低流量下误熔断）。
- `BR-28-016`：**熔断必须有降级路径**（熔断后不能直接报错给用户）。
- `BR-28-017`：**熔断必须告警**（状态变化时）。
- `BR-28-018`：**半开探测必须限制流量**（避免恢复瞬间再次打挂下游）。
- `BR-28-019`：**熔断状态必须可观测**（Grafana 展示熔断器状态）。
- `BR-28-020`：**禁止熔断核心内部调用**（如业务代码自身，应通过限流而非熔断）。
- `BR-28-021`：**熔断时间窗要合理**（太短会反复熔断-恢复-熔断，太长影响恢复）。

**验收标准**：

- `AC-28-002-1`：下游异常时熔断生效
- `AC-28-002-2`：熔断后走降级路径
- `AC-28-002-3`：半开探测恢复
- `AC-28-002-4`：熔断阈值可配置
- `AC-28-002-5`：最小请求数保护
- `AC-28-002-6`：熔断状态可观测
- `AC-28-002-7`：熔断告警
- `AC-28-002-8`：熔断不影响其他下游

### FR-28-003 降级开关 【P0】

| 项 | 内容 |
|---|---|
| **功能目标** | 通过配置快速关闭非核心功能，保护核心链路 |
| **使用角色** | 运维（操作）、管理员（授权） |

**降级开关设计**：

```java
@Component
public class DegradeSwitch {

    /** 开关配置（从配置中心/Redis 读取，支持热更新） */
    private final Map<String, Boolean> switches = new ConcurrentHashMap<>();

    public boolean isEnabled(String key) {
        return switches.getOrDefault(key, true);
    }

    /** 动态刷新（监听配置变更） */
    @EventListener
    public void onConfigChange(ConfigChangeEvent event) {
        switches.putAll(configService.getDegradeSwitches());
    }
}

/** 使用（注解方式） */
@DegradeSwitch(name = "recommend.reason", fallback = "noReason")
public AiReason generateReason(Song song) { ... }

public AiReason noReason(Song song) {
    return null;  // 不发推荐理由
}
```

**降级级别（按严重程度）**：

| 级别 | 名称 | 触发条件 | 关闭内容 |
|---|---|---|---|
| **0** | 正常 | — | 无 |
| **1** | 轻度降级 | 流量 +50% 或 P99 恶化 50% | 日志采样、非核心埋点采样、热力图 |
| **2** | 中度降级 | 流量 +100% 或 P99 > 1s | AI 生成类功能（理由、摘要）、探索位、个性化推荐 |
| **3** | 重度降级 | 核心指标恶化 | 各仓推荐 → 热门榜、AI 搜索 → 关键词、动态发现页 |
| **4** | 保命降级 | 依赖大面积故障 | 只保留：登录、播放、搜索（关键词）、基础列表 |
| **5** | 只读 | 灾难 | 仅浏览，禁止写操作 |

**一键降级**：

```
管理员后台 → 系统降级 → [选择级别 2] → 确认
   ↓
立即生效（配置中心推送，秒级）
   ↓
所有实例读取最新开关
   ↓
前端同步感知（接口返回 degradeLevel，前端隐藏相应功能）
```

**业务规则**：

- `BR-28-022`：**所有非核心功能必须有降级开关**。
- `BR-28-023`：**降级开关必须热更新**（秒级生效，不重启）。
- `BR-28-024`：**降级必须有明确的分级**（不能只有"全开/全关"）。
- `BR-28-025`：**降级操作必须有权限控制**（仅运维/管理员）+ **操作日志**。
- `BR-28-026`：**降级后前端必须同步感知**（隐藏入口，避免用户点击报错）。
- `BR-28-027`：**降级必须是可逆的**（恢复后立即恢复功能）。

### FR-28-004 Redis 集群 【P0】

| 项 | 内容 |
|---|---|
| **功能目标** | Redis 高可用、可扩展、故障自动切换 |
| **使用角色** | 系统内部 |

**Redis 部署架构**：

```
方案：Redis Cluster（3 主 3 从，6 节点）
  - 数据分片：16384 个 hash slot 分布在 3 个主节点
  - 每主节点 1 从节点（故障自动切换）
  - 客户端：Lettuce（集群模式）+ Redisson（分布式锁）

客户端配置：
  spring.redis.cluster.nodes=redis-1:6379,redis-2:6379,redis-3:6379,redis-4:6379,redis-5:6379,redis-6:6379
  spring.redis.cluster.max-redirects=3
  spring.redis.lettuce.pool.max-active=32
  spring.redis.lettuce.pool.max-idle=16
  spring.redis.lettuce.pool.min-idle=8
  spring.redis.timeout=2000ms
  spring.redis.lettuce.cluster.refresh.adaptive=true
  spring.redis.lettuce.cluster.refresh.period=30s
```

**为什么用 Cluster 而不是主从 + Sentinel**：

| 方案 | 容量 | 扩展 | 复杂度 | 本项目 |
|---|---|---|---|---|
| 主从 + Sentinel | 单机内存上限 | **不能水平扩展** | 低 | 内存需求小可用 |
| **Cluster** | **可水平扩展** | 支持 | 中 | **采用**（预期数据量：缓存 ~10GB、Feed 收件箱 ~2GB、限流计数等） |

**Redis 使用分类（必须区分，避免混用）**：

| 用途 | Key 前缀 | 特性要求 | 说明 |
|---|---|---|---|
| **缓存** | `ml:cache:*` | 可丢 | 缓存穿透/雪崩需处理 |
| **会话** | `ml:session:*` | **不可丢**（掉线） | JWT 无状态，但存黑名单 |
| **计数/限流** | `ml:rate:*`, `ml:stat:*` | 可丢（近似） | HyperLogLog / 计数 |
| **分布式锁** | `ml:lock:*` | **不可丢** | Redisson |
| **队列/收件箱** | `ml:feed:*` | 可丢（可重建） | 见 [25 章](./25-模块16-社交升级.md) |
| **实时状态** | `ml:room:*` | 可丢（崩溃时从 DB 重建） | 见 [22 章](./22-模块13-音乐房升级.md) |
| **去重** | `ml:dedup:*` | 可丢 | 幂等 |

**持久化配置**：

```
# 缓存类数据：可以不持久化（RDB 定时快照即可）
# 关键数据（锁、会话、Feed）：需要 AOF

appendonly yes
appendfsync everysec        # 每秒 fsync（性能与安全平衡）
save 900 1
save 300 10
save 60 10000

# 内存策略（必须区分）
# 缓存实例：allkeys-lru（淘汰最久未用）
# 计数/锁实例：noeviction（不淘汰，写满报错，避免丢锁）—— 实际上 Cluster 共用一个策略
maxmemory-policy allkeys-lru    # 注意：不可与锁混用同一实例
```

> **重要风险**：`allkeys-lru` 下，Redis 内存满时会**淘汰任意 key**，包括**分布式锁**！这会导致**锁失效（被误删）**。
>
> **对策**：
> 1. **锁 key 设置过期时间**（Redisson 看门狗自动续期，且锁有自己的超时）。
> 2. **监控 Redis 内存使用率**（> 80% 告警）。
> 3. **重要场景用 Redisson 的 RedLock（多主）** 或**用 DB 乐观锁兜底**（见 [14 章](./14-模块05-音乐房.md) 麦克风座位）。
> 4. **【假设 A-38】** 生产环境建议**缓存与锁/会话分实例**（不同 Cluster）以避免策略冲突。若资源有限，至少**监控 + 锁超时 + DB 兜底**三重保障。

**关键实践**：

| 实践 | 说明 |
|---|---|
| **禁用 `KEYS`** | 生产禁用，用 `SCAN`（`KEYS` 会阻塞） |
| **禁用 `FLUSHALL`** | 生产禁用（可 rename-command 屏蔽） |
| **大 key 治理** | 单 key ≤ 10KB（Hash/List/ZSet 元素 ≤ 5000），定期扫描（`--bigkeys`） |
| **热 key 治理** | 热 key 用**本地缓存**（Caffeine）+ 多副本（key 加随机后缀分散到不同 slot） |
| **Pipeline 批量** | 批量操作用 Pipeline（减少 RTT） |
| **避免跨 slot 操作** | Cluster 下 `MGET`/`MSET` 跨 slot 会失败，用 `{}` hash tag 强制同 slot（如 `ml:like:{userId}:song`） |
| **连接池合理** | 避免连接数爆炸，Lettuce 默认共享连接（无需大池） |

**业务规则**：

- `BR-28-033`：**必须用 Redis Cluster**（3 主 3 从起）。
- `BR-28-034`：**必须区分缓存与锁/会话**（见上，不同实例或至少不同策略保障）。
- `BR-28-035`：**分布式锁必须有过期时间**（防死锁）。
- `BR-28-036`：**分布式锁必须有 DB/乐观锁兜底**（Redis 不可靠时数据不能错）。
- `BR-28-037`：**生产禁用 `KEYS`、`FLUSHALL`、`FLUSHDB`**（rename-command 屏蔽）。
- `BR-28-038`：**大 key 与热 key 必须治理**（定期扫描 + 告警）。
- `BR-28-039`：**跨 slot 操作必须用 hash tag**。
- `BR-28-040`：**必须监控**：内存使用率、命中率、QPS、慢查询、连接数、主从延迟、slot 分布。
- `BR-28-041`：**缓存必须处理三大问题**（穿透、击穿、雪崩，见 [12 章](./12-模块03-Redis缓存.md)）。
- `BR-28-042`：**Redis 故障必须降级**（不能直接导致业务不可用）：
  - 缓存失效 → 查 DB（性能下降）
  - 限流失效 → 单机限流
  - 锁失效 → DB 乐观锁
  - Feed 失效 → 全拉模式
- `BR-28-043`：**Redis 版本**：≥ 6.2（支持 `LMPOP` 等新命令），因安全原因 **禁用危险命令**。
- `BR-28-044`：**Redis 必须有鉴权**（password）与**网络隔离**（仅内网访问）。
- `BR-28-045`：**Redis 备份**：每日 RDB 备份到对象存储，保留 7 天。

**异常情况**：

| 编号 | 场景 | 处理 |

| `EX-28-004-2` | 整个 Cluster 不可用 | 业务降级（见 BR-28-042） |

### FR-28-005 消息队列高可用 【P0】

| 项 | 内容 |
|---|---|
| **功能目标** | MQ 高可用、不丢消息、可重放 |
| **使用角色** | 系统内部 |

**MQ 分工（重要）**：

| MQ | 用途 | Topic 示例 |
|---|---|---|
| **RocketMQ** | **业务消息**（需顺序、事务、延迟消息） | 房间广播、通知、搜索同步、Feed 分发、审核 |
| **Kafka** | **数据管道**（高吞吐、可回溯） | 埋点、日志、数仓 |

**RocketMQ 高可用部署**：

```
NameServer: 2 节点（无状态，互相同步）
Broker: 2 主 2 从（同步双写 or 异步复制）
  - 主从同步方式：SYNC_MASTER（强一致，性能略低）/ ASYNC_MASTER
  - 本项目：核心业务（通知、审核）用 SYNC；非核心（Feed、埋点）可 ASYNC

Topic 配置：
  - 读写队列数：4（默认）
  - 消息保留：3 天（业务消息）
  - 刷盘：SYNC_FLUSH（核心）/ ASYNC_FLUSH
```

**消息可靠性保障（三段）**：

| 阶段 | 保障 |
|---|---|
| **生产端不丢** | 同步发送（等待 ack）+ 失败重试（3 次）+ 本地消息表（事务消息） |
| **Broker 不丢** | 同步刷盘 + 主从同步复制 |
| **消费端不丢** | **消费成功后才 ACK**（业务处理成功才确认），失败则重试 |

**消费幂等（关键）**：

```java
@Component
@RocketMQMessageListener(topic = "ml_notify_event", consumerGroup = "notify_consumer")
public class NotifyConsumer implements RocketMQListener<NotifyMessage> {

    @Override
    public void onMessage(NotifyMessage msg) {
        // 【幂等】消息可能重复消费，必须幂等
        String idempotentKey = "ml:mq:idem:notify:" + msg.getMsgId();
        Boolean first = redis.opsForValue()
            .setIfAbsent(idempotentKey, "1", Duration.ofHours(24));
        if (Boolean.FALSE.equals(first)) {
            log.info("Duplicate message, skip: {}", msg.getMsgId());
            return;   // 已处理，直接 ACK
        }

        try {
            notifyService.send(msg);
        } catch (Exception e) {
            redis.delete(idempotentKey);   // 【重要】失败要删除幂等键，允许重试
            throw e;                        // 抛出异常 → MQ 重试
        }
    }
}
```

> **关键陷阱**：如果先写幂等键再处理业务，**业务失败后幂等键残留**会导致重试被跳过（消息丢失）。所以**失败必须删除幂等键**，或用"处理后写幂等键 + 业务与幂等键在同一事务"。

**重试与死信**：

```
消费失败 → RocketMQ 自动重试（默认 16 次，指数退避）
   ↓ 超过重试次数
死信队列（%DLQ%{consumerGroup}）
   ↓
告警 + 人工介入（查看死信消息，修复后手动重投）
```

**延迟消息**（RocketMQ 原生支持）：

| 场景 | 延迟 |
|---|---|
| 订单超时（本无） | — |
| 消息撤回（2 分钟窗口） | 2min |
| 审核超时升级（24 小时） | 24h |
| 缓存延迟双删（见 [12 章](./12-模块03-Redis缓存.md)） | 500ms |
| 任务重试 | 1min/5min/30min |

**RocketMQ 广播模式（房间同步用）**：

```java
@Component
@RocketMQMessageListener(
    topic = "ml_room_broadcast",
    consumerGroup = "room_broadcast_consumer",
    messageModel = MessageModel.BROADCASTING   // 【关键】广播模式
)
public class RoomBroadcastConsumer implements RocketMQListener<RoomBroadcastMessage> {
    // 每个实例都收到消息，推送给本实例持有的 WebSocket 连接
    // 见 [13 章](./13-模块04-WebSocket.md)
}
```

> **为什么用广播模式**：房间消息需要发到**所有实例**（因为房间成员可能连在不同的实例上）。广播模式下**每个实例都消费全量消息**，各自推送给自己持有的连接。

**业务规则**：

- `BR-28-046`：**核心业务消息必须同步发送 + 重试**（不丢）。
- `BR-28-047`：**消费必须幂等**（`msgId` 去重）。
- `BR-28-048`：**失败必须删除幂等键**（允许重试）。

- `BR-28-054`：**顺序消息**：需要顺序的场景（如房间播放状态变更）用**顺序消息**（同一 MessageQueue），但**必须接受性能损失**。
  - **本项目**：房间播放状态用**版本号（playStateVersion）**保证顺序（见 [22 章](./22-模块13-音乐房升级.md)），不用顺序消息（性能更好）。

- `BR-28-056`：**MQ 必须有监控**：发送成功率、消费成功率、积压量、延迟、死信量。

### FR-28-006 数据库高可用 【P0】

| 项 | 内容 |
|---|---|
| **功能目标** | MySQL 高可用、读写分离、故障切换 |
| **使用角色** | 系统内部 |

**部署架构**：

```
方案：MySQL 主从（1 主 2 从）+ 读写分离 + MHA/Orchestrator 故障切换
  - 主库：写
  - 从库 1：读（用于报表、后台查询）
  - 从库 2：读 + 备份 + 从库灾备

读策略：
  - 写后立即读 → 主库（避免主从延迟读到旧数据）
  - 列表/统计类读 → 从库
  - 事务内读 → 主库
```

**读写分离实现（动态数据源）**：

```java
/** 通过 AOP + ThreadLocal 切换数据源 */
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Slave {
}

@Aspect
@Component
public class DataSourceAspect {

    @Around("@annotation(slave)")
    public Object around(ProceedingJoinPoint pjp, Slave slave) throws Throwable {
        try {
            DataSourceContext.set(DataSourceType.SLAVE);
            return pjp.proceed();
        } finally {
            DataSourceContext.clear();
        }
    }
}

/** 强制主库（写后读） */
public void updateAndRead() {
    userMapper.update(...);
    DataSourceContext.set(DataSourceType.MASTER);   // 强制主库
    try {
        userMapper.selectById(...);
    } finally {
        DataSourceContext.clear();
    }
}
```

**业务规则**：

- `BR-28-059`：**必须主从部署**（1 主 ≥ 1 从）。
- `BR-28-060`：**读写分离必须有"写后读主"机制**（避免主从延迟导致业务错误）。
  - **典型场景**：用户修改资料后立即刷新 → 必须读主库。
  - **实现**：写操作后，当前请求线程后续读走主库（ThreadLocal 标记）。
- `BR-28-061`：**主从延迟必须监控**（> 1s 告警，> 5s 时对延迟敏感的读切到主库）。
- `BR-28-062`：**必须用连接池（Druid）**并有监控（连接数、慢 SQL、SQL 统计）。
- `BR-28-063`：**慢 SQL 必须治理**（> 1s 记录并告警，> 5s 阻断并告警）。
- `BR-28-064`：**大事务禁止**（单事务 < 1000 行 / < 1 秒），大事务拆批。
- `BR-28-065`：**必须分表的大表**：
  - `t_play_history`（按月分表，见 [16 章](./16-模块07-播放与歌词.md)）
  - `t_feed_inbox`（按 user_id 分 16 表，见 [25 章](./25-模块16-社交升级.md)）
  - `t_ai_call_log`、`t_operation_log`（按月分表）
- `BR-28-066`：**备份策略**：全量备份（每日）+ binlog（实时），保留 7 天；**每季度恢复演练**。
- `BR-28-067`：**主库故障切换**：Orchestrator 自动切换（< 30s），或 MHA。
- `BR-28-068`：**禁止在业务代码中手工开启事务过长**（用 `@Transactional` 并注意传播行为）。
- `BR-28-069`：**MySQL 参数**：`innodb_buffer_pool_size`（物理内存 60-70%）、`innodb_flush_log_at_trx_commit=1`（安全）、`sync_binlog=1`。
- `BR-28-070`：**隔离级别**：默认 `READ-COMMITTED`（避免间隙锁，提升并发；配合 binlog `ROW` 格式）。

**异常情况**：

| 编号 | 场景 | 处理 |

| `EX-28-006-1` | 主库宕机 | Orchestrator 自动切换（< 30s），应用重连 |

| `EX-28-006-6` | 数据文件损坏 | 从备份恢复 |

### FR-28-008 日志与链路追踪 【P0】

| **功能目标** | 全链路可观测，问题可快速定位 |

**日志体系**：

| 类型 | 内容 | 存储 | 保留 |
|---|---|---|---|

| **审计日志** | 管理操作（见 [18 章](./18-模块09-管理后台.md)） | MySQL + ELK | 2 年 |

**日志格式（结构化 JSON）**：

```json
{
  "timestamp": "2026-10-12T14:23:45.123+08:00",

  "service": "newmusic",
  "instance": "10.0.1.5:8080",
```

**链路追踪（SkyWalking）**：

```
用户请求
   ↓ [TraceId 生成，注入 MDC 与 HTTP Header]
Nginx
   ↓
Spring Boot 应用（SkyWalking Agent 自动埋点）
   ├─→ MySQL（自动埋点，慢查询标记）
   ├─→ Redis（自动埋点）
   ├─→ RocketMQ（生产/消费，自动埋点）
   ├─→ Elasticsearch（自动埋点）
   ├─→ LLM API（手动埋点）
   └─→ 内部方法（可手动埋点关键方法）
   ↓
前端（可选：上报 traceId，与后端关联）
```

**SkyWalking Agent 配置**：


**手动埋点（关键业务方法）**：

```java
/** 使用 SkyWalking 的 @Trace 注解 */

    // 自动创建 span
}
```

**traceId 贯穿**：

```
前端生成 traceId（或服务端生成）
   ↓ 通过 HTTP Header 传递
后端接收 → 放入 MDC（日志自动带上）
   ↓ 通过 MQ 消息属性传递
下游消费者 → 取出放入 MDC
   ↓ 通过 WebSocket 消息传递（可选）
前端可据此查询完整链路
```

**关键排查场景（SOP）**：

| 场景 | 排查路径 |
|---|---|
| 某用户反馈播放失败 | 用 userId 查日志 → 找 traceId → SkyWalking 看链路 → 定位到具体环节 |
| 接口 P99 突增 | Grafana 看接口 → SkyWalking 看慢链路 → 找出慢的 span（DB？ES？外部 API？） |
| 错误率上升 | 日志搜索 ERROR → 聚合异常类型 → 定位范围 |
| 数据不一致 | 用 traceId 追踪完整链路 → 看每一步的输入输出 |
| 用户投诉内容未显示 | 用 contentId 查审核记录 → 看决策与原因 |

**业务规则**：

- `BR-28-083`：**日志必须结构化（JSON）**（便于检索与聚合）。
- `BR-28-084`：**日志必须包含 traceId**（全链路关联）。

- `BR-28-092`：**追踪必须覆盖跨进程调用**（HTTP、RPC、MQ、DB、Redis）。
- `BR-28-093`：**关键业务方法必须手动埋点**（如推荐、搜索、播放、AI 调用）。
- `BR-28-094`：**链路追踪必须与日志关联**（同一 traceId）。
- `BR-28-095`：**必须支持按 userId/contentId/traceId 检索**。
- `BR-28-096`：**日志与追踪必须有权限控制**（敏感数据日志仅特定角色可见）。
- `BR-28-097`：**日志写入必须异步**（不阻塞业务，用 Logback AsyncAppender），但**ERROR 级别需保证不丢**（同步或独立队列）。

## 7. 发布与容灾

### FR-28-009 灰度发布与回滚 【P1】

| 项 | 内容 |
|---|---|
| **功能目标** | 降低发布风险，快速回滚 |
| **使用角色** | 运维、开发 |

**发布策略**：

| 策略 | 说明 | 适用 |
|---|---|---|
| **滚动发布** | 逐批替换实例 | 常规发布 |
| **蓝绿发布** | 双环境切换 | 重大版本 |
| **金丝雀（灰度）** | 先给小部分流量 | **推荐**（本项目） |
| **A/B 发布** | 按用户分流 | 需要对比时 |

**灰度维度**：

```
1. 按实例灰度：先发 1 个实例（5% 流量），观察 → 再 25% → 50% → 100%
2. 按用户灰度：内部用户 → 白名单用户 → 1% 用户 → 10% → 100%
3. 按地域灰度：先单地域 → 多地域
```

**灰度观察指标**：

| 指标 | 通过标准 |
|---|---|
| 错误率 | 不高于基线 |
| P99 延迟 | 不高于基线 20% |
| GC | 无明显恶化 |
| 业务指标（播放成功率等） | 不下降 |
| 日志 ERROR | 无新增异常类型 |
| 观察时长 | ≥ 15 分钟/阶段 |

**回滚**：

```
回滚触发条件：
  - 错误率 > 基线 2 倍
  - P99 > 基线 3 倍
  - 出现数据错误
  - 人工判断

回滚动作：
  - K8s: kubectl rollout undo（< 1 分钟）
  - 数据库变更：需**向后兼容**（见下），不做自动回滚
  - 配置变更：配置中心回滚（秒级）
```

**数据库变更规范（关键）**：

```
【必须向后兼容】任何 DB 变更必须保证"新代码 + 旧 schema"和"旧代码 + 新 schema"都能运行

安全的变更（可随时回滚）：
  ✓ 新增表
  ✓ 新增字段（可空，或有默认值）
  ✓ 新增索引（注意：大表加索引会锁表，用 pt-online-schema-change / gh-ost）
  ✓ 新增枚举值（代码兼容旧值）

危险的变更（不可回滚，必须分多次发布）：
  ✗ 删除字段（先停用，下次发布再删）
  ✗ 修改字段类型（新增字段 + 双写 + 迁移 + 切换 + 删除）
  ✗ 重命名字段（新增 + 双写 + 迁移 + 删除）
  ✗ 加非空约束（先填默认值）

变更流程（expand-contract）：
  Step 1（expand）: 新增字段，双写新旧字段，读旧字段
  Step 2（migrate）: 数据迁移，读新字段（双写继续）
  Step 3（contract）: 停止双写，删除旧字段
  每个 Step 独立发布，可回滚
```

**业务规则**：

- `BR-28-098`：**所有发布必须灰度**（不允许直接全量）。
- `BR-28-099`：**灰度必须设定明确的观察指标与时长**。
- `BR-28-100`：**灰度必须可随时中止与回滚**。

- `BR-28-104`：**发布必须有回滚预案**（含 DB 变更的处理方式）。

```
  - 方案 A（推荐）：自建 `t_sys_config` + Redis + 定时/事件刷新（简单，无需额外组件）

```

**配置热更新机制**：

```java
@Component
public class ConfigRefreshService {

    /** 本地缓存 */
    private final Map<String, String> localCache = new ConcurrentHashMap<>();

    /** 定时全量拉取（兜底，30 秒） */
    @Scheduled(fixedDelay = 30000)
    public void refreshAll() {
        Map<String, String> latest = configRepository.loadAll();
        localCache.putAll(latest);
    }

    /** 事件驱动增量更新（主，秒级） */
    @EventListener
    public void onConfigChange(ConfigChangeEvent event) {
        localCache.put(event.getKey(), event.getValue());
        log.info("Config refreshed: {}", event.getKey());
        // 触发相关组件的重新加载（如限流规则、推荐配置）
        configChangeHandlers.forEach(h -> h.onChange(event));
    }

    public String get(String key, String defaultValue) {
        return localCache.getOrDefault(key, defaultValue);
    }
}
```

### FR-28-015 健康检查与自愈 【P0】

| 项 | 内容 |
|---|---|
| **功能目标** | 快速发现不健康实例，自动恢复 |
| **使用角色** | 系统 |

**健康检查**：

```java
@Component
public class CustomHealthIndicator implements HealthIndicator {

    @Override
    public Health health() {
        Health.Builder builder = Health.up()
            .withDetail("version", buildVersion);

        // 检查关键依赖（轻量检查，不耗资源）
        try {
            // 【1】数据库
            jdbcTemplate.queryForObject("SELECT 1", Integer.class);
            builder.withDetail("database", "ok");
        } catch (Exception e) {
            builder.down().withDetail("database", e.getMessage());
        }

        // 【2】Redis
        try {
            redisTemplate.opsForValue().get("health:check");
            builder.withDetail("redis", "ok");
        } catch (Exception e) {
            builder.down().withDetail("redis", e.getMessage());
            // 【注意】Redis 不可用时不应让实例下线（有降级路径），只标记为 degraded
        }

        // 【3】线程池
        ThreadPoolExecutor pool = (ThreadPoolExecutor) recallExecutor;
        double usage = (double) pool.getActiveCount() / pool.getMaximumPoolSize();
        builder.withDetail("recallPoolUsage", usage);
        if (usage > 0.9) {
            builder.withDetail("status", "degraded");
            // 高使用率不直接 down，但告警
        }

        return builder.build();
    }
}
```

**健康检查端点**：

| 端点 | 用途 | 检查内容 |
|---|---|---|
| `/actuator/health/liveness` | 存活（K8s livenessProbe） | 进程是否活着（不检查依赖） |
| `/actuator/health/readiness` | 就绪（K8s readinessProbe） | 关键依赖是否可用 |
| `/actuator/health` | 详细健康 | 全部依赖 |

> **重要**：**liveness 不能检查依赖**！如果 liveness 检查了 DB，DB 挂了会导致所有实例被 K8s 重启，反而更糟。liveness 只检查进程本身。

**K8s 探针配置**：

```yaml
livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  initialDelaySeconds: 60
  periodSeconds: 10
  failureThreshold: 3

readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
  initialDelaySeconds: 30
  periodSeconds: 5
  failureThreshold: 3

startupProbe:              # 启动探针（慢启动应用，如加载模型/词库）
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  initialDelaySeconds: 30
  periodSeconds: 10
  failureThreshold: 18     # 最长 3 分钟
```

**自愈能力**：

| 故障 | 自愈 |
|---|---|
| 实例不健康 | K8s 重启（liveness） / 摘除流量（readiness） |
| 实例崩溃 | K8s 重启（Pod restart policy） |
| 内存溢出 | JVM 崩溃 → K8s 重启 + 告警 + OOM 分析 |
| 线程池打满 | 降级 + 告警（不重启） |
| 死锁 | 检测 → 告警 → 重启（谨慎） |
| 连接泄漏 | 连接池自愈（超时回收） + 告警 |
| 高 CPU | HPA 扩容 |
| 依赖故障 | 熔断降级（不重启） |
| 磁盘满 | 日志滚动 + 告警（不重启） |

**业务规则**：

- `BR-28-165`：**所有服务必须提供健康检查**（liveness + readiness）。
- `BR-28-166`：**liveness 不得检查依赖**（避免依赖故障导致重启风暴）。
- `BR-28-167`：**readiness 检查关键依赖**（不健康则摘除流量）。
- `BR-28-168`：**健康检查必须轻量**（≤ 10ms，不产生副作用）。
- `BR-28-169`：**必须有启动探针**（慢启动应用，如加载词库/模型）。
- `BR-28-170`：**优雅停机**：收到 SIGTERM 后先摘流量，等待进行中请求完成（最长 30s），再退出。
  - **WebSocket 特殊处理**：向客户端发送"服务重启"消息，客户端自动重连其他实例（见 [13 章](./13-模块04-WebSocket.md)）。
- `BR-28-171`：**启动必须做自检**（依赖可用性、配置完整性、词库加载），失败则拒绝启动（快速失败而非带病运行）。
- `BR-28-172`：**重启必须有退避**（`CrashLoopBackOff`），避免无限重启。
- `BR-28-173`：**重启必须告警**（频繁重启是严重信号）。

**异常情况**：

| 编号 | 场景 | 处理 |
|---|---|---|
| `EX-28-015-1` | 依赖不可用但进程正常 | readiness 失败，摘除流量（不重启） |
| `EX-28-015-2` | 进程假死 | liveness 失败，K8s 重启 |
| `EX-28-015-3` | 启动自检失败 | 拒绝启动，告警 |
| `EX-28-015-4` | 频繁重启 | 退避 + 告警 + 回滚 |
| `EX-28-015-5` | 优雅停机超时 | 强制退出（设置 `terminationGracePeriodSeconds`） |

**验收标准**：

- `AC-28-015-1`：liveness 与 readiness 分离
- `AC-28-015-2`：liveness 不检查依赖
- `AC-28-015-3`：readiness 检查关键依赖
- `AC-28-015-4`：启动探针配置
- `AC-28-015-5`：优雅停机生效（含 WebSocket 通知）
- `AC-28-015-6`：启动自检
- `AC-28-015-7`：重启退避与告警
- `AC-28-015-8`：健康检查轻量（≤ 10ms）

## 11. 应急预案（Runbook）

### 11.1 应用实例全部不可用

```
现象：健康检查失败，所有实例 5xx
排查：
  1. 检查 K8s Pod 状态（kubectl get pods）
  2. 检查启动日志（是否有启动异常）
  3. 检查最近发布（是否刚发布导致）
  4. 检查依赖（DB/Redis 是否可用）
处置：
  1. 若是新发布导致 → 立即回滚（kubectl rollout undo）
  2. 若是依赖故障 → 修复依赖（见对应预案）
  3. 若是资源不足 → 扩容
  4. 若无法快速修复 → 启用静态兜底页（Nginx）
通知：立即通知 P0 群
```

### 11.2 Redis 全量不可用

```
现象：缓存大量 miss，DB 压力暴增，接口超时
排查：
  1. Cluster 状态（redis-cli cluster info）
  2. 内存是否满（info memory）
  3. 是否有大 key / 热 key
  4. 网络连通性
处置：
  1. 缓存失效 → 业务降级（读 DB），但需限流保护 DB
  2. 限流降级为单机限流（Sentinel）
  3. 分布式锁降级为 DB 乐观锁
  4. Feed 降级为全拉模式
  5. 逐步恢复 Redis，预热热点数据
关键：绝不能让 DB 被击穿 → 必须同步开启 DB 保护限流
```

### 11.3 MySQL 主库不可用

```
现象：写操作失败
排查：
  1. 主库进程状态
  2. 复制状态（Orchestrator）
  3. 磁盘、连接数、锁
处置：
  1. Orchestrator 自动切换（< 30s）
  2. 应用重连（连接池自动重连）
  3. 若无法切换 → 提升从库为主库（手动）
  4. 切换后验证数据一致性
关键：切换期间写操作会短暂失败，前端需友好提示"稍后重试"
```

### 11.4 播放量骤降

```
现象：Grafana 播放指标骤降 > 30%
排查顺序：
  1. 埋点链路是否正常（是否只是埋点问题）
  2. CDN 是否故障（音频 404/超时率）
  3. 播放接口是否报错
  4. 签名 URL 是否失效（密钥问题）
  5. 前端是否有 JS 错误（检查前端监控）
  6. 是否全站故障（其他指标也降）
处置：
  1. 埋点问题 → 修复埋点
  2. CDN 问题 → 切备用 CDN
  3. 接口问题 → 修复 + 回滚
  4. 前端问题 → 回滚前端版本
```

### 11.5 高危内容漏出

```
现象：发现违规内容已公开
处置（最高优先级，立即执行）：
  1. 立即下架内容（手动）
  2. 定位原因（词库缺失？机审故障？人工误判？）
  3. 补充词库/修复机审（立即热更新）
  4. 全量扫描同类内容（回溯清理）
  5. 评估影响范围（多少人看过）
  6. 30 分钟内出初步报告，2 小时内出复盘
  7. 若涉及监管红线 → 按合规流程上报
关键：安全事件不看"是否影响业务"，看"是否影响合规"
```

### 11.6 AI 成本突增

```
现象：AI 成本告警（超预算 80%）
排查：
  1. 哪个场景成本高（t_ai_call_log 按场景聚合）
  2. 是否缓存失效（命中率骤降）
  3. 是否被刷（某用户/设备高频调用）
  4. 是否有循环调用 bug
处置：
  1. 立即降低该场景限流阈值
  2. 强制启用缓存
  3. 封禁刷量用户
  4. 修复 bug
  5. 若必要 → 熔断该场景 AI
```

### 11.7 WebSocket 连接数异常

```
现象：连接数远超预期（或骤降）
排查：
  1. 是否有客户端异常重连风暴
  2. 某实例是否连接数不均
  3. 网络是否抖动
处置：
  1. 重连风暴 → 客户端退避重连（服务端下发重连间隔）
  2. 分布不均 → 负载均衡调整（一致性 hash）
  3. 扩容 WS 实例
```
