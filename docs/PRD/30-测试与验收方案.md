## 1. 测试目标与原则

### 1.1 目标

| 目标 | 说明 |
|---|---|
| **功能正确** | 所有 FR 的业务规则（BR）与异常（EX）被覆盖验证 |
| **非功能达标** | 性能、安全、可用性、一致性、兼容性达标（见 [29 章](./29-非功能需求.md)） |
| **缺陷前移** | 越早发现越便宜，测试左移 |
| **质量可度量** | 覆盖率、缺陷密度、逃逸率可统计 |
| **可验收** | 每个 FR 有可执行的验收标准（AC） |

### 1.2 质量指标

| 指标 | 目标 |
|---|---|
| 单元测试覆盖率（核心模块） | ≥ 60%（行） |
| 单元测试覆盖率（推荐/搜索/AI 等核心逻辑） | ≥ 70% |
| 接口测试覆盖率（核心接口） | 100% |
| 严重缺陷（S1/S2）上线前修复率 | 100% |
| 缺陷逃逸率（上线后发现的 S1/S2 / 总 S1/S2） | ≤ 5% |
| 冒烟测试通过率 | 100% |
| 性能达标率 | 100% |
| 安全高危漏洞 | 0 |

### 1.3 缺陷分级

| 级别 | 定义 | 处理时限 |
|---|---|---|
| **S1 致命** | 服务不可用、数据丢失/错误、安全漏洞、资金损失 | **立即修复**，阻断发布 |
| **S2 严重** | 核心功能不可用、无法绕过、用户体验严重受损 | 24 小时内，阻断发布 |
| **S3 一般** | 非核心功能异常、可绕过、体验问题 | 本迭代内 |
| **S4 轻微** | 文案、样式、优化建议 | 排期处理 |

**发布红线**：**S1/S2 必须全部修复方可发布**。

## 2. 测试策略

### 2.1 测试分层（测试金字塔）

```
           ┌─────────────┐
           │   手动/探索  │  少量（关键场景、体验）
           ├─────────────┤
           │  端到端 E2E  │  少量（核心用户旅程）
           ├─────────────┤
           │   集成测试   │  适量（模块间、中间件）
           ├─────────────┤
           │   接口测试   │  **最多（主要投入）**
           ├─────────────┤
           │   单元测试   │  **大量（基础）**
           └─────────────┘
```

**说明**：

| 层 | 占比 | 说明 |
|---|---|---|
| 单元测试 | 60% | 快、便宜、覆盖逻辑分支 |
| 接口测试 | 25% | 覆盖业务规则与异常 |
| 集成测试 | 10% | 覆盖中间件交互（DB/Redis/MQ/ES） |
| E2E | 4% | 覆盖核心用户旅程 |
| 手动探索 | 1% | 体验、边界、新功能探索 |

### 2.2 测试类型清单

| 类型 | 目的 | 工具 | 频率 |
|---|---|---|---|
| **单元测试** | 逻辑正确 | JUnit 5 + Mockito | 每次提交（CI） |
| **接口测试** | 业务规则、异常、权限 | JUnit + MockMvc / REST Assured | 每次构建（CI） |
| **集成测试** | 中间件交互 | Testcontainers / 内嵌容器 | 每日 / 合并前 |
| **E2E 测试** | 用户旅程 | Playwright | 每日 / 发布前 |
| **性能测试** | 容量与延迟 | JMeter / k6 | 每版本 |
| **安全测试** | 漏洞 | OWASP ZAP / 扫描工具 / 渗透 | 每版本 + 每半年渗透 |
| **兼容性测试** | 浏览器/设备 | BrowserStack / 真机 | 每版本 |
| **数据测试** | 一致性、对账、迁移 | 自研脚本 | 每次数据变更 |
| **故障测试** | 韧性 | ChaosBlade | 每季度 |
| **回归测试** | 防退化 | 自动化套件 | 每次发布 |
| **UAT** | 业务验收 | 手动 + 真实场景 | 上线前 |
| **灰度验证** | 线上验证 | 监控 + 人工 | 每次发布 |

### 2.3 测试环境

| 环境 | 用途 | 数据 | 部署 |
|---|---|---|---|
| **本地** | 开发自测 | 造数据 | Docker Compose |
| **开发（DEV）** | 联调 | 造数据 | 自动部署 |
| **测试（TEST）** | 功能测试 | 造数据 | 自动部署 |
| **预发（STAGING）** | 集成/性能/UAT | **接近生产**（脱敏数据） | 生产同构 |
| **生产（PROD）** | 灰度/全量 | 真实 | — |

> **原则**：**预发环境必须与生产同构**（同配置、同中间件版本、数据量接近），否则性能测试无意义。

### 2.4 测试数据策略

| 项 | 策略 |
|---|---|
| 造数 | 提供 seed 脚本（用户、歌曲、歌单、房间、评论各 N 条） |
| 脱敏 | 生产数据导入预发必须脱敏（手机号、密码、token） |
| 隔离 | 测试数据与生产隔离，测试环境不写生产 |
| 埋点 | 测试环境埋点标记 `env=test`，不混入生产分析 |
| 清理 | 自动化测试用例自清理（或独立租户/命名空间） |
| 边界数据 | 特意构造：空、超长、特殊字符、emoji、极值 |

**示例 1：业务规则测试（点赞）**

```java
@DisplayName("点赞业务规则")
class LikeServiceTest {

    @Test
    @DisplayName("BR-14-001: 同一用户对同一歌曲只能点赞一次")
    void should_RejectDuplicateLike() {
        // given
        Long userId = 1001L, songId = 2001L;
        when(likeMapper.selectCount(any())).thenReturn(1L);

        // when
        BusinessException ex = assertThrows(BusinessException.class,
            () -> likeService.like(userId, songId));

        // then
        assertEquals(ErrorCode.ALREADY_LIKED, ex.getErrorCode());
    }

    @Test
    @DisplayName("取消点赞后可以重新点赞")
    void should_AllowReLikeAfterUnlike() {
        // ... 覆盖状态流转：未赞 → 赞 → 取消 → 赞
    }

    @Test
    @DisplayName("并发点赞不产生重复数据（唯一索引兜底）")
    void should_HandleConcurrentLike() throws Exception {
        int threads = 20;
        ExecutorService pool = Executors.newFixedThreadPool(threads);
        CountDownLatch latch = new CountDownLatch(threads);
        AtomicInteger success = new AtomicInteger();

        for (int i = 0; i < threads; i++) {
            pool.submit(() -> {
                try {
                    likeService.like(1001L, 2001L);
                    success.incrementAndGet();
                } catch (Exception ignored) {
                } finally {
                    latch.countDown();
                }
            });
        }
        latch.await(10, TimeUnit.SECONDS);

        // 无论并发多少，最终只有 1 条
        assertEquals(1, success.get());
        assertEquals(1L, likeMapper.selectCount(any()));
    }
}
```

### 3.3 单元测试规范

| 编号 | 要求 |
|---|---|
| `TR-30-001` | 测试方法命名：`should_预期行为_When_条件` 或中文 `@DisplayName` |
| `TR-30-002` | 遵循 AAA 模式（Arrange-Act-Assert） |
| `TR-30-003` | 一个测试只验证一个行为 |
| `TR-30-004` | 测试必须独立、可重复、无顺序依赖 |
| `TR-30-005` | 外部依赖必须 Mock（DB/Redis/HTTP/LLM） |
| `TR-30-006` | **必须覆盖业务规则（BR）与异常（EX）** |
| `TR-30-007` | **必须覆盖边界**（空、极值、超长、特殊字符、emoji） |
| `TR-30-008` | **必须覆盖并发场景**（关键写操作） |
| `TR-30-009` | 禁止在测试中使用 `Thread.sleep` 等待（用 Awaitility） |
| `TR-30-010` | 测试必须能被 CI 自动执行（不依赖人工环境） |
| `TR-30-011` | **AI/LLM 调用必须 Mock**（不消耗成本），并用固定响应断言处理逻辑 |
| `TR-30-012` | 时间相关逻辑必须可注入时钟（`Clock`）以便测试 |

## 4. 接口测试

### 4.1 覆盖要求

**每个对外接口必须测试**：

| 维度 | 用例 |
|---|---|
| **正常** | 至少 1 个正常用例 |
| **参数校验** | 必填缺失、类型错误、长度超限、格式错误、越界 |
| **权限** | 未登录（401）、无权限（403）、水平越权（访问他人资源） |
| **业务规则** | 每条 BR 至少 1 个用例 |
| **异常** | 每条 EX 至少 1 个用例 |
| **幂等** | 重复提交（如适用） |
| **限流** | 超限返回 429（如适用） |
| **边界** | 空列表、仅 1 条、超过分页上限 |

## 6. E2E 与端到端用户旅程

### 6.1 核心用户旅程清单

| 编号 | 旅程 | 步骤 |
|---|---|---|
| `E2E-01` | **新用户注册到播放** | 注册 → 登录 → 完善资料 → 首页推荐 → 点击播放 → 收藏 |
| `E2E-02` | **搜索并播放** | 搜索关键词 → 筛选 → 播放 → 查看歌词（含翻译） |
| `E2E-03` | **AI 搜索** | 输入自然语言 → AI 解析 → 结果播放 |
| `E2E-04` | **创建歌单** | 创建 → 添加歌曲 → 编辑 → 设为公开 |
| `E2E-05` | **AI 生成歌单** | 输入描述 → 生成 → 试听 → 保存 |
| `E2E-06` | **房间创建与互动** | 创建房间 → 他人加入 → 房主播放 → 成员同步 → 弹幕 → 退出 |
| `E2E-07` | **麦克风上麦** | 申请上麦 → 房主通过 → 上麦 → 说话 → 下麦 |
| `E2E-08` | **社交互动** | 关注用户 → 查看动态 → 点赞 → 评论 → 收到通知 |
| `E2E-09` | **发布动态** | 发布（含图片）→ 审核 → 展示 → 他人互动 |

**对账脚本示例**：

```sql
-- 点赞数对账（缓存 Redis 计数 vs DB 实际）
-- 允许偏差 0.1%
SELECT s.song_id,
       s.like_count AS cache_count,
       (SELECT COUNT(*) FROM t_like l WHERE l.song_id = s.song_id AND l.deleted = 0) AS real_count
FROM t_song_stat s
WHERE ABS(s.like_count - (SELECT COUNT(*) FROM t_like l
        WHERE l.song_id = s.song_id AND l.deleted = 0)) /
      GREATEST(s.like_count, 1) > 0.001;
-- 结果应为空；非空则告警并自动重算
```

```
  ↓
[10] 部署到 TEST
  ↓
[11] 集成测试
  ↓
[12] E2E 测试
  ↓

  ↓

  ↓

  ↓

  ↓
[17] 线上验证
  ↓
[18] 全量发布
```

### 14.2 质量门（Quality Gate）

| 检查 | 阈值 | 不通过 |
|---|---|---|
| 单元测试通过率 | 100% | 阻断 |
| 覆盖率（核心） | ≥ 60% | 阻断 |
| 代码扫描（SonarQube） | 无 blocker/critical | 阻断 |
| 依赖漏洞 | 无 CVSS ≥ 7 | 阻断 |
| 镜像漏洞 | 无 HIGH/CRITICAL | 阻断 |
| 接口测试通过率 | 100% | 阻断 |
| 冒烟测试 | 100% | 阻断回滚 |

### 14.3 自动化测试报告

- 每次 CI 运行产出报告（通过率、覆盖率、趋势）。
- 失败用例必须第一时间通知（企业微信/邮件）。
- 覆盖率趋势下降必须告警。
- 用例稳定性监控（flaky test 必须修复，不能重试掩盖）。
