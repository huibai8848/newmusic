## 2. 系分决策（ADR）

| 编号 | 决策 | 理由 | 影响面 |
|---|---|---|---|
| **D-01** | 播放地址接口放在**后端新增 `module/play`**，路径 `GET /api/v1/player/url`；**不**复用 `/music/songs/{id}` 返回的裸地址 | 裸地址无法做版权校验、过期与审计；接口有清晰边界，模块 12 的 `/play/record` 可平移到同一模块 | `module/play`、`src/api/player.ts` |
| **D-02** | 签名算法与 PRD `BR-16-010` 一致：`sign = HMAC_SHA256(secret, path + "|" + expires + "|" + userId)`，`expires` 为**秒级**时间戳，有效期 2h | 与 PRD 逐字对齐，避免前端联调时语义分叉；`userId` 参与签名使链接不可跨账号复用 | `PlayUrlSigner` |
| **D-03** | **签名在 MVP 不做强制校验**：演示音频由 Spring 静态资源处理器直接吐出，不带校验过滤器 | 真实防盗链的对象是 CDN 边缘节点，本地静态目录没有校验点；写一个校验 Filter 挡 `file:` 资源是**看起来安全**的假实现。前端仍按"地址会过期"的真实契约实现（到期前 5 分钟重取） | `WebMvcConfig` §4.3、§9 风险 R-02 |
| **D-04** | `<audio>` 元素**保持在 `main.tsx` 根节点**，不按 PRD `BR-16-007` 移回 `MainLayout` | PRD 写 `MainLayout` 是为了"路由切换不销毁"；挂在根节点严格更强（进后台、跳登录页也不销毁）。此偏差在模块 02 已登记，本模块不改回 | `main.tsx` |
| **D-05** | 歌词**解析在前端**（`utils/lrc.ts` 纯函数），后端只存 LRC 原文 | PRD `BR-16-051` 明确要求；纯函数易测，且歌词可随 `localStorage` 缓存离线可用 | `src/utils/lrc.ts` |
| **D-06** | 歌词当前行定位用**二分查找**，且只在**行号变化时**才触发滚动（`currentLine` 进 store 之前先比对） | `BR-16-054` 禁止线性扫描；按行号而不是按时间做依赖，避免 4Hz 的 `timeupdate` 每帧重排 | `src/utils/lrc.ts`、`LyricPanel` |
| **D-07** | 歌词滚动用 `transform: translateY(calc(50% - N * 行高))`，**不用 `scrollTop`**；行高固定 36px 以便纯计算定位 | `BR-16-055`；固定行高让滚动位置是常量表达式，不依赖 `offsetTop` 读取（避免强制同步布局） | `LyricPanel.module.less` |
| **D-08** | 全屏播放页是 **overlay + `history` 历史记录**，不是路由：展开时 `history.pushState`，监听 `popstate` 关闭 | `BR-16-044` 要求"不改变路由 + 浏览器后退可关闭"；用独立路由会导致刷新后落到空白页 | `src/components/player/PlayingPage.tsx` |
| **D-09** | 队列继续沿用模块 02 的 `localStorage` 持久化（`ml.player`：`queue`/`currentIndex`/`volume`/`muted`/`playMode`/`quality`），**但播放进度单独存 `ml.lastPlay`**（D-14），不混进这条记录 | 队列可能 500 首，把进度一起塞进去会让"只改进度"也重写整个队列的 JSON；两者写入频率差两个数量级（队列偶发 vs 进度每 5 秒）。`BR-16-021` | `playerStore` |
| **D-10** | 随机播放用 `shuffleOrder: number[]`（索引洗牌序列）+ `shufflePos` 游标，一轮播完**重新洗牌**并把已播过的首曲排除在首位之外 | `BR-16-014` 禁止"每次随机取索引"（会重复）；排除首位可避免"洗牌后第一首还是刚听完的那首" | `playerStore` |
| **D-11** | 失败重试状态**放在 `AudioEngine` 的 ref 里**，不进 store | 重试计数、退避定时器与 `HTMLMediaElement` 生命周期强绑定，进 store 会引入无意义的全局可变状态，且组件卸载时的清理更难写 | `AudioEngine` |
| **D-12** | 演示音频用**纯 Node 合成 WAV**（正弦波 + 简单包络），**未压缩**，单个文件 9~14 MB（合计 66.6 MB，走 `.gitignore`） | 本机无 ffmpeg；WAV 无需编码器即可手写 RIFF 头。用 MP3 必须引第三方编码器，为一个演示素材不值得。代价是文件大，但它是本地静态文件、不进 Git，换来的是**时长与 `t_song.duration` 逐首精确相等**——进度条不会说谎 | `scripts/make-demo-audio.mjs` |
| **D-13** | 播放地址**按 `(songId, quality, userId)` 缓存到 `sessionStorage`**，同时记录 `expiresAt`；`currentSong` 变化才重新请求，播放中不重取 | 拖进度条、切页面都不该重新签发；`sessionStorage` 关闭标签页即失效，比 `localStorage` 更贴合"两小时会话地址"的语义。**缓存键带 `userId` 是因为签名里含 `userId`**——换账号后旧地址验签必然失败，不带 `userId` 会拿到一个 403 的 URL | `src/api/player.ts` |
| **D-14** | 断点续播独立成 `ml.lastPlay` 单条记录（`{songId, position, updatedAt, userId}`），由 `services/lastPlay.ts` 负责节流写入与恢复 | 见 D-09：写入频率与队列差两个数量级，必须分开 | `src/services/lastPlay.ts` |
| **D-15** | `single` 模式的**自动重播**由 `AudioEngine` 的 `ended` 回调**直接 `currentTime = 0; play()`**（读 `repeatOne`），不走 `store.next()`；**手动点「下一首」在 `single` 模式下照样切歌**，与 `loop` 完全一样——两者只在「本曲播完要不要重播」上不同 | `ended` 时如果只把 `currentIndex` 设回同一值，React 观察不到变化、`<audio>` 不会被重新播放——**这是模块 02 遗留的缺陷**（单曲循环实际会停住）。存 `repeatOne` 单独一份就是为了在 `ended` 里少读一个字段。**v1.6 更正**：本条原写「手动点『下一首』落在 `single` 模式时则走 `replayToken` 重播」，与 `BR-16-016` / `AC-16-002-4` 及本模块 §1.1 第 9 项都相反，是那条 `ended` 机制被错推广到手动切歌上，代码曾照此实现（§9 R-11） | `AudioEngine` / `playerStore` / `playOrder` |

## 4. 接口契约

### 4.1 `GET /api/v1/player/url`

**请求**（公开接口，游客可调；带 Token 时 `userId` 参与签名）

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `songId` | string（雪花 ID） | 是 | 歌曲 ID |
| `quality` | `standard` / `high` / `lossless` | 否 | 默认 `standard`；无该档音源时自动降级 |

**响应** `R<PlayUrlVO>`：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "songId": "1000000000000005001",
    "quality": "standard",
    "requestedQuality": "lossless",
    "downgraded": true,
    "url": "/media/demo/demo-01.wav?expires=1760000000&sign=3f9a...",
    "duration": 84,
    "format": "wav",
    "expiresAt": 1760000000000,
    "previewDuration": null
  },
  "traceId": "…"
}
```

**字段说明**

- `downgraded`：请求无损但只有标准档时为 `true`，前端据此在播放条上提示实际音质
- `url`：**相对路径**（本机演示）。真实部署时把 `newmusic.play.cdn-base` 配成域名，`url` 直接带域名；前端一律原样使用，不做拼接
- `expiresAt`：毫秒时间戳，前端按它判断是否需要在切歌前重取
- `previewDuration`：游客试听的片段时长，MVP 恒为 `null`（试听属模块 03/12）

**错误码**

模块 07 **不新增错误码**：校验全部落在 `SongService.requirePlayable(songId)` 上（模块 01 已交付），
所以错误码就是它原有的那几个，前端按 `code` 分支即可。

| code | 抛出点 | 场景 | 前端表现 |
|---|---|---|---|
| `10001` | `PlayUrlService` | `songId` 缺失 | 参数错误提示 |
| `30001` | `requirePlayable` | 歌曲不存在 / 已逻辑删除 / 已下架 / 审核被拒 | 「歌曲不存在或已下架」并跳过该曲（BR-16-004） |
| `30008` | `requirePlayable` | 歌曲审核中（`audit_status=0`） | 「歌曲正在审核中」并跳过 |
| `30002` | `requirePlayable` | 无版权 / 版权过期 / 受限 | 「当前歌曲无版权」并跳过（BR-16-003） |
| `30003` | `requirePlayable`、`PlayUrlService` | 标准音质为空（无任何可用音源） | 「该歌曲暂无可用音质」并跳过 |

> ①`30001` 的文案本身就是「歌曲不存在或已下架」，后端刻意把「不存在」与「已下架」合并为同一码——
> 下架的歌曲不应向前端泄露它曾经存在过（PRD 05 §2.2 的信息最小化约定）。前端因此不做区分。
>
> ②`30003` 兜底分支在 `requirePlayable` 之后**不可达**（它已保证 `audioStandard` 非空），
> 保留仅为防御；即"请求无损但只有标准档"不会报错，而是走 `downgraded=true` 降级。

### 4.2 歌词接口（模块 01 已交付，本模块只消费）

`GET /api/v1/music/lyrics/{songId}` → `R<Lyric | null>`

| 字段 | 类型 | 本模块用法 |
|---|---|---|
| `content` | string | LRC 原文，交给 `parseLrc()` |
| `contentType` | number | `1` 标准 LRC / `2` 逐字 LRC / `3` 纯文本；`2` 本次按标准 LRC 解析（丢弃 `<mm:ss.xx>` 逐字标签），`3` 整段按无时间轴文本展示 |
| `translation` / `romaji` | string | 本次**不展示**（模块 14） |
| `offsetMs` | number | 服务端校准值。**与正文 `[offset:]` 是同一个槽位，取其一而非相加**：非 0 时覆盖正文标签（`override`），为 0 时用正文标签。再叠加用户校准（`BR-16-069`）。见 §10 v1.3 |

无歌词时 `data` 为 `null` → 展示「暂无歌词」+ 歌曲信息（`BR-16-056`）。

### 4.3 静态媒体

`GET /media/**` → `file:${newmusic.media.dir:./media}/**`

```yaml
newmusic:
  media:
    dir: ./media            # 相对**后端进程工作目录**（即仓库根）
  play:
    sign-secret: ${PLAY_SIGN_SECRET:newmusic-demo-secret-change-me}
    url-ttl-seconds: 7200   # 2h，与 PRD BR-16-010 一致
    cdn-base: ""            # 留空 → 返回相对路径；配成 https://cdn.xxx → 返回绝对 URL
```

## 5. 状态与交互设计

### 5.1 `playerStore` 增量字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `shuffleOrder` | `number[]` | 当前队列的洗牌索引序列；`playList` / 队列增删 / 切进随机模式时重建。**一轮播完时由 `advance` 一并换新**（D-10） |
| `shufflePos` | `number` | 当前曲在 `shuffleOrder` 中的位置。**只有 `playOrder.advance` 有权算出它**：一轮播完时序列会被重建，用旧序列现算必然错位（§9 R-10）。直接点某首歌（不经过 `advance`）时才用 `shufflePosOf` 现算 |
| `repeatOne` | `boolean` | 由 `playMode === 'single'` 派生，单独存是为了 `ended` 事件里少读一个字段（D-15） |
| `lastPlayedId` | `string \| null` | 熔断用：连续失败的歌曲 ID 不重复计入连败 |
| `failStreak` | `number` | 连续失败计数，≥3 时停止自动切歌并提示检查网络（`BR-16-089`） |
| `playSource` | `'search' \| 'playlist' \| 'album' \| 'artist' \| 'home' \| 'queue' \| 'unknown'` | 供模块 12 上报埋点，本次只写入不消费 |
| `currentLine` | `number` | 当前歌词行号，`-1` 为前奏。**由 `AudioEngine` 单向写入、面板只读**，这样歌词面板挂几份都不重复计算 |
| `replayToken` | `number` | 递增计数；变化即代表"从头重播当前曲"（D-15），`AudioEngine` 监听它做 `currentTime = 0; play()`。触发点有三：`single` 下本曲播完、播放超 3 秒时点「上一首」、以及**切歌目标恰好是本曲**（队列只剩一首）——后者必须走它而不走 `goTo`，否则 `currentTime` 归零而 `index` 未变，引擎不会重新播放（§9 R-11） |
| `overlayOpen` / `queueDrawerOpen` / `hotkeyHelpOpen` | `boolean` | 三个浮层开关。**不持久化**：刷新页面后全屏播放页不该自己弹出来 |

**断点续播**（`BR-16-039`）另存一份轻量记录，避免把整个队列写进存储：

```jsonc
// ml.lastPlay
{ "songId": "1000000000000005001", "position": 62.5, "updatedAt": 1760000000000, "userId": "…" }
```

- 每次 `timeupdate` **节流 5 秒**写入（`BR-16-036`），进度四舍五入到 0.1 秒（`BR-16-037`）
- 距结尾 < 3 秒时记 `0`（`BR-16-038`）
- 应用启动时若 `updatedAt` 在 **7 天内**且歌曲 ID 与 `queue` 里能对上，则恢复为**暂停态**并把进度写进 `seekRequest`，播放条提示「上次播放到 01:02」（`BR-16-039`）
- 已下架/无版权的歌曲**不恢复**并清掉记录（`EX-16-005-4`）

### 5.2 播放地址获取时序

```
currentSong 变化 / quality 变化 / 播放失败需要重取
   ↓
查 sessionStorage 缓存 ml.playurl.{songId}.{quality}
   ├─ 命中且 expiresAt - now > 5min  → 直接用
   └─ 未命中 / 临近过期 / 上次请求失败 → GET /api/v1/player/url
        ↓
     写缓存 → audio.src = url → audio.play()
        ↓
     失败分支按 §5.3 处理
```

> **为什么不预加载整条队列**：`BR-11-045`（模块 02）已定"地址按需获取"。队列 500 首全量签发既浪费服务端签名算力，也会让一批地址在用户还没听到时就开始倒计时。

### 5.3 播放失败处理（FR-16-012）

| `audio.error.code` | 处理 | 是否保留进度 |
|---|---|---|
| 1 `ABORTED` | 忽略（用户主动中止 / 切歌导致） | — |
| 2 `NETWORK` | 退避重试 1s、3s（最多 2 次），重试前重新签发地址（可能是签名过期）；仍失败 → 跳下一首 | 是（`reload()` 后回写 `currentTime`） |
| 3 `DECODE` | **不重试**，跳下一首并在控制台记录 `songId` 与格式 | 否 |
| 4 `SRC_NOT_SUPPORTED` | 降一档音质重试一次（`lossless → high → standard`）；仍失败 → 跳下一首 | 是 |

- 连续失败计数按**不同歌曲**累计：同一首歌重试不计入（避免一首坏歌直接触发熔断）
- `failStreak >= 3` → 停止自动切歌，`error` 置为「网络异常，请检查网络后重试」，播放按钮保持可用让用户手动重试（`BR-16-089`）
- 任一成功播放事件（`playing`）都会把 `failStreak` 清零

### 5.4 歌词面板

```tsx
// 关键：只在行号变化时更新，避免 4Hz 的 timeupdate 触发重排
const currentLine = usePlayerStore((s) => s.currentLine);
```

- 容器高度 = 7 行（`36px * 7`），当前行居中：`translateY(calc(50% - 3.5 * 36px - line * 36px + 3.5 * 36px))` 化简为 `translateY(calc(50% - line * 36px - 18px))`
- 前奏（`currentLine === -1`）时高亮位置停在第一行上方，显示歌曲信息
- 用户手动滚动（`wheel` / `touchmove`）→ 暂停自动滚动 **5 秒**并显示「恢复自动滚动」浮层（`BR-16-059`）
- 点击某行 → `seek(line.time)`，跟随自动滚动立即恢复（`BR-16-058`）
- 无时间轴（`contentType === 3` 或解析出 0 行）→ 纯文本滚动区，禁用点击跳转并给出说明

### 5.5 全屏播放页（overlay）

- 打开：`PlayingPage` 挂载 + `history.pushState({ mlPlaying: true }, '')`
- 关闭：`popstate` 且 `event.state?.mlPlaying !== true` → 卸载；点「收起」按钮则 `history.back()`

- **不**独占 `<audio>`：overlay 只是视图，音频仍由根节点的 `AudioEngine` 驱动（`BR-16-045`）
- 移动端（`< 768px`）全屏页占满视口；桌面端为居中卡片（`max-width: 1100px`）

## 6. 关键时序

### 6.1 点击列表播放 → 出声 → 歌词滚动

```
用户点击 SongTable 某行
  → playList(list, index)                    [store：更新 queue / currentIndex / isPlaying，乐观渲染]
  → AudioEngine 观察到 currentSong 变化
      → fetchPlayUrl(songId, quality)        [sessionStorage 命中则 0 请求]
      → audio.src = url; audio.play()
      → pushHistory(song)                    [模块 02 的本地历史]
      ← 'playing' 事件 → isPlaying=true, isBuffering=false, failStreak=0
  → useLyric(songId) 触发
      → songApi.lyric(songId) → parseLrc(content, offsetMs) → currentLine 初始 -1
  → 'timeupdate'（≈4Hz）
      → setProgress(t, d)                    [进度条]
      → 计算 currentLine，**变化才** setCurrentLine()   [歌词滚动]
```

### 6.2 签名过期（播到一半换歌）

```
① 用户在 01:59 切歌 → 缓存命中但 expiresAt - now < 5min
② fetchPlayUrl 强制走网络 → 新地址与新 sign
③ audio.src 换新 → 从 0 开始播放新曲
```

播放**进行中**地址过期不打断当前曲（`EX-16-001-8`）：浏览器已建立连接的媒体流不会因 URL 查询串过期而中断，只有下次换 `src` 时才需要新地址。

### 6.3 音频 404 → 重试 → 跳曲

```
'error' 事件(code=2 NETWORK)
  → retryCount=1，setTimeout(1000) → 重新 fetchPlayUrl（换新签名）→ reload() 并回写 currentTime
  → 仍失败 → retryCount=2，setTimeout(3000) → 同上
  → 仍失败 → failStreak++；若 <3 → next(true)；若 >=3 → 停播 + 「网络异常，请检查网络」
```

| R-10 | **随机模式重新洗牌等于没洗**（已修） | 原 `nextIndexIn` 只返回目标索引，`playerStore.goTo` 便拿**旧** `shuffleOrder` 去算落位游标。而 `shuffleOrder` 是 `0..n-1` 的排列，**任何合法索引都在里面**，`indexOf` 必然命中——于是新首曲被落位到它在旧序列里的位置，之后的「下一首」又沿旧序列走。净效果：重新洗牌只决定了周期交界处的一首，且紧接着重播本周期刚放过的歌（违反 `BR-16-014`），同时与 D-10 的既定决策不符。**实测样例**：旧序列 `[1,2,4,5,3,0]`，播完 `0` 后新首曲是 `4`，但旧实现下第二周期会是 `[5,3,0,1,2,4]`——`5,3,0` 是刚放过的三首原样重播 | 已修（2026-10-16，经确认后按 D-10 处理）：把「哪份序列算数」的决策移进 `advance`，它在周期交界处返回**重建后的序列 + 游标 0**，store 只负责原样落位。因此这条契约本身有单测（`test-playorder.mjs` §8 断言第二周期**不是**旧序列的旋转——谁把 bug 重新引入，该条立刻变红）。**注意 `shufflePosOf` 里 `Math.max(0, …)` 的 `-1` 分支在此路径上已成死代码**（序列恒为排列），它只为「目标曲不在当前序列」这一入口保留 |
| R-12 | **进度条是「边拖边 seek」，不是「释放才 seek」**（**未修**） | `PlayerBar.tsx:150` 与 `PlayingPage.tsx:162` 都是 `onChange={(v) => seek(v)}`——`onChange` 在拖动过程中每 `step`（1 秒）触发一次，于是一次拖动会连续发出上百次 `seek`，每次都会改写 `<audio>.currentTime` 并带一个 `seekRequest` nonce。而 §1.1 第 10 项与 `AC-16-005-1`（拖动进度条有预览气泡）、`AC-16-005-2`（**释放后立即跳转**）写的是「拖动预览（**释放才 seek**）」「拖动有气泡且**释放才跳**」。**未直接改成 `onChange` 预览 / `onChangeComplete` 提交，是因为那样会引入一个更糟的回归**：`rc-slider` 的方向键走 `onHandleOffsetChange`（`rc-slider/es/Slider.js:328`），它只调 `triggerChange`、**不调 `finishChange`**，所以键盘微调滑杆会永远提交不了——滑杆移动、音频不动，且预览值被冻结 | 待浏览器走查给出实测（拖动时是否真的听得出一顿一顿）。修法要一并处理键盘路径：拖动期用本地预览状态，`onChangeComplete`、方向键 `onKeyUp`、`blur` 三个出口都提交；同时要避开与全局 `←/→` ±5s 快捷键的重叠（滑杆获得焦点时两者都会响应）。**当前仅记录，不在走查前盲改** | `playerStore.next()` 里有一段 `if (playMode === 'single') { replayFromStart(); return; }`，`prev()` 同样。这与 `BR-16-016`（"单曲循环时点击『下一首』仍**切换**到下一首，不重播当前"）、`AC-16-002-4`、以及**本模块 §1.1 第 9 项**三处相反。起因是 D-15 那条 `ended` 机制被错推广：`ended` 确实不能靠"把 `currentIndex` 设回同一值"来重播（React 观察不到变化），但**手动切歌根本不该重播**——两件事被写成了一条规则。附带影响：`single` 模式下坏歌的自动跳过也走 `next(true)`，重播导致同一首反复失败、`failStreak` 因"同一首歌只算一次"永不达 3，`AC-16-117` 的熔断**在该模式下不可达** | 已修（2026-10-16）：`single` 在 `advance` 里与 `loop` 合并为同一分支（`(currentIndex + 1) % length`），并在 `playOrder.ts` 注明"两者只在 `ended` 要不要重播上不同"；`next`/`prev` 删掉 `single` 提前返回；D-15 那句错的话已改写。**顺带补上一处护栏**：「目标就是本曲」时走 `replayFromStart`（否则 `goTo` 改了 `currentTime` 但 `index` 没变，引擎不重新播放，界面与声音错位——正是 D-15 记的那个坑），以及 `goTo` 跳过不可播歌曲的**递归深度上限**（整队列无版权时原先会撑爆调用栈）。回归断言 `test-playorder.mjs`「R-11 回归」一节逐点比对 `single` 与 `loop`，谁改回去立刻变红 |

### 11.4 四种播放模式（`AC-16-103`，本轮重点）

模式按钮的 `aria-label` 与 Tooltip 会显示当前模式，Tooltip 形如 `顺序播放（点击切换到列表循环）`。**点击顺序固定为：顺序播放 → 列表循环 → 单曲循环 → 随机播放 → 顺序播放**（也可用 `R` 键轮换）。

| 模式 | 怎么验 | 预期现象 |
|---|---|---|
| 顺序播放 | 切到该模式，跳到**最后一首**，拖到末尾 | 播完**停止**，不回到第一首；进度归零、按钮变回 `播放`（`BR-16-017`） |
| 列表循环 | 最后一首拖到末尾 | 自动回到**第一首**继续 |
| 单曲循环 | ① 任意一首拖到末尾 ② 然后**手动点「下一首」** | ① 本曲**从头重播**（`ended` 路径）<br>② **必须切到下一首**，歌名要变（`BR-16-016` / `AC-16-002-4`）——**这正是本轮刚修的 R-11**，修前这里会变成重播本曲 |
| 单曲循环（续） | 再点「上一首」 | 切到**上一首**（`BR-16-016` 只写了 next，prev 按对称处理） |
| 随机播放 | 记下**第一轮 6 首的播放顺序**（队列抽屉里当前行会高亮，或用歌名逐个记）；逐首拖到末尾走完一轮；再记第二轮的顺序 | ① 一轮之内 6 首**互不重复**（`BR-16-014`）<br>② 第二轮开始时**不是**刚播完的那首（`BR-16-014` 的排除首位）<br>③ 第二轮顺序**明显不同于**第一轮（即"重新洗牌真的生效"）——**这是本轮修的 R-10**，修前第二轮会是第一轮顺序的**轮转**，且紧接着重播刚放过的几首。如果第二轮看起来只是第一轮换了个起点，请立刻告诉我 |

> 模式持久化（`BR-16-013`）：切到随机后刷新页面，模式应保持为随机。
