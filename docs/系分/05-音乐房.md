## 2. 系分决策（ADR）

| 编号 | 决策 | 理由 | 影响面 |
|---|---|---|---|
| **D-01** | 房间的**权威数据在 MySQL**（`t_room*`），实时态在 Redis（在线集合、播放态、排麦顺序、禁言/黑名单快速判定）。`RoomService` 只回答「该不该进来 + 进来后改哪些数据」，协议与会话仍由模块 04 的 `MusicWebSocketHandler` 负责 | 房间 CRUD、成员关系、麦位、队列必须可重启恢复；把 Handler 继续限制在「协议翻译」层，模块 04 的可靠消息 / 幂等 / 广播逻辑不需要复制一份 | `module/room/**`、`MusicWebSocketHandler` |
| **D-02** | 房主权威改为 `t_room.owner_id`。`ml:room:owner:{roomId}` **只保留给模块 04 的演示房**，真实房间不再读取；`findManagedRoom(roomId) == null` 时才走旧的 SETNX 演示路径 | 模块 04 的 `verify-04.mjs` 与 `/live/:roomId` 依赖演示房；真实房主必须可事务性转让、可在 DB 查询，Redis 键不适合作为唯一真相。两条路径用「DB 里有没有这个 roomId」硬隔离，避免一个房间被两套规则同时管理 | `RoomService.findManagedRoom`、`WsPresenceService.claimOwner` |
| **D-03** | 麦位、禁言、黑名单采用「**先 DB 后 Redis**」的双写；Redis 故障只让实时镜像变旧，不回滚 DB。读取时以 DB 兜底（如 `isBlacklisted` 同时查 Set 与成员表） | 房间功能必须在 Redis 抖动时仍能「进去、说话、管理」；实时镜像丢失最多导致短暂误判，下一次写或定时任务会修复 | `RoomStateService`、`RoomMicService`、`RoomModerationService` |
| **D-04** | 密码校验放在 **HTTP `POST /join`**，WS `room.join` 复用 `ml:room:pwd:{roomId}:{userId}` 的 30 分钟验证结果 | 密码表单需要明确的错误码与重试计数，WS 帧不适合承载表单交互；验证一次后 WS 重连不必再带密码，符合 `BR-14-016` | `RoomService.prepareJoin`、`RoomPage` 密码弹窗 |
| **D-05** | 「加入」场景把关闭 / 解散统一映射为 **40001 房间不存在**；「房内操作」场景才区分 40020（已关闭）/ 40011（状态异常）；详情对已解散返回 40001 | 加入接口是未授权用户也能触达的边界，返回「已关闭」会泄露房间曾经存在（`EX-14-002-1`）；已经在房内的人需要明确提示，因此操作路径保留 40020 | `RoomPermissionService.requireActiveForJoin / requireActiveForOperation` |
| **D-06** | 真实房间的控播用 `ml:lock:room:play:{roomId}` 串行化「读旧状态 → 写 Redis → 同步 DB」；acks 先下发，DB 的 `current_song_id` 与队列消费随后完成 | 切歌是低频写、高频广播；锁只包住状态迁移，不包网络下发，避免一个慢客户端拖住整个房间。代价是 HTTP 查询可能短暂看到旧队列状态，前端与验收脚本需按最终一致性轮询 | `applyManagedPlayControl`、`RoomService.onPlayStateChanged` |
| **D-07** | 控播权限拆成 `canControl`（房主/房管）与 `canControlPlayback`（房主/房管，且 `playMode=2` 时允许普通成员）。点歌审核、禁言、拉黑仍只走管理权限 | 「自由播放房」的产品含义就是成员可以切歌；但若把成员提升为房管，会顺带获得审核/禁言权限，违反最小权限 | `RoomPermissionService.canControlPlayback`、`RoomService.requireWsControl` |
| **D-08** | 麦位分配用 `ml:lock:room:mic:{roomId}` 分布式锁 + 数据库唯一约束（`room_id + mic_pos`）双重保护；1 号麦固定给房主，锁位不参与分配 | `AC-14-005-1` 要求并发抢占无冲突；只靠「先查空位再更新」会出现两人同时读到同一空位。锁解决顺序，唯一索引解决锁失效时的兜底 | `RoomMicService.assignFirstFree`、`t_room_mic` |
| **D-09** | 排麦队列用 Redis ZSet（userId → seq）做顺序与快速判重，点歌用 `t_room_queue` 落库；`ml:room:queue:{roomId}` 只存**已通过**项的快照 | 排麦是高频变更、低价值历史，放 Redis 合适；点歌要审计、要跨重启恢复，必须落库。查询接口返回「待审 + 已通过」，快照只给播放路径，避免待审歌曲被误播 | `RoomStateService`、`RoomQueueService.refresh` |
| **D-10** | 踢人 / 拉黑顺序：先落冷却或黑名单 → 广播 → 发站内通知 → 最后断开连接（4003 / 4004）。关闭房间先落 `status=2` 再断开（4005） | 反过来会出现「连接已断、重连却还能进来」的窗口；先落状态让关闭回调里的 `onWsLeave` 看到正确状态，避免把正在关闭的房间误交接给其他成员 | `RoomModerationService`、`RoomService.close/dissolve` |
| **D-11** | 生命周期任务（`RoomLifecycleJob`）每分钟跑一次，多实例可并发；所有迁移都是条件更新 + 幂等状态变化 | 没有 XXL-Job，Spring `@Scheduled` 足够；条件更新让重复执行不会产生第二次副作用 | `RoomLifecycleJob` |
| **D-12** | 热度 = 在线人数 × 0.5 + 互动数 × 0.3 + **当前在线者人均停留分钟** × 0.2；Redis 热度缓存 2 分钟，DB 每分钟刷新 | PRD 写的是「停留时长」，若用房间累计总时长，老房会单调增长、永远压住新房；用当前在线者的人均时长更接近「现在这个房热不热」 | `RoomLifecycleJob.recomputeHot` |
| **D-13** | 前端权限码（`room.control`、`room.moderate`…）只用于渲染按钮；每个写接口在服务端独立校验 | 前端权限码是 UX，不是安全边界；`AC-14-102` 要求权限严格区分，服务端必须能单独通过接口测试 | `RoomPermissionService.permissions`、`RoomPage` |
| **D-14** | 私密房不进推荐 / 热门 / 最新，但**保留在「我的」**，方便房主从列表回到自己的房间 | PRD `BR-14-073` 写「不出现在任何列表」；完全隐藏会让房主只能靠分享链接管理私密房。公开 tab 的约束已满足，差异登记为 R-05-04 | `RoomService.page`、`RoomListPage` |
| **D-15** | 演示房兼容：`findManagedRoom` 有记录 → 走 DB 权威；无记录且 `demoRoomEnabled=true` → 走模块 04 的 SETNX 房主；无记录且关闭演示 → 40001 fail-closed | 保证模块 04 的 `verify-04.mjs` 和 `/live/:roomId` 继续可用，同时生产配置可以一键关掉任意数字房间 | `MusicWebSocketHandler.onJoin/onPlayControl` |
| **D-16** | 房间系统消息复用模块 04 的 `t_room_message(type=3)` 与 `t_notification`，由 `RoomNotifier` 统一写；不新建房间操作日志表 | 消息历史、未读数、通知铃铛已经存在；另建表会产生两套清理与两套查询 | `RoomNotifier`、`RoomMessageService` |
| **D-17** | 前端只有 `detail.status === 1` 才建立 WS 入房；密码房先 HTTP 校验成功再入房；退房 / 被踢 / 关房后清空房间态但保留退出提示 | 关闭 / 解散的房间建立 WS 只会拿到错误；先校验密码可以复用后端的失败计数与锁定，不必在 WS 里重复实现 | `RoomPage`、`wsStore` |
| **D-18** | 创建接口同时有 `@RateLimit(USER, 3, 1h)` 与业务层「每日 3 个 / 活跃 10 个」配额；两者错误码不同（10004 vs 40012） | 限流是防刷，配额是产品规则。快速连续创建会先撞限流；跨小时后第 4 个才会撞每日配额。验收脚本先删除本用户的 `ml:limit:room:user:*` 再验证 40012，避免把两层保护混为一谈 | `RoomController.create`、`RoomService.checkCreateQuota` |

## 5. 关键时序

### 5.1 创建房间

```
POST /room/rooms
  → 参数校验（名称/类型/密码/麦位数/人数/播放模式）
  → 敏感词检查（名称、公告）
  → 配额检查：今日创建 < 3 且活跃房间 < 10
  → 分配 6 位 roomNo（Redis INCR，DB 唯一性重试）
  → 插入 t_room（房主、status=1、version=0）
  → 插入 t_room_member（role=2）
  → 初始化 t_room_mic（micCount 个，1 号麦 = 房主）
  → 返回 RoomDetailVO（含权限码）
```

密码房：`password` 经 BCrypt 后写 `t_room.password_hash`，任何接口都不回传。

### 5.2 加入房间（HTTP 预校验 + WS 入房）

```
前端 RoomPage
  → GET /room/rooms/{roomNo} 取详情
  → 若 status != 1：不建立 WS，展示“已关闭”
  → 若 passwordRequired 且非房主/房管：
       POST /room/rooms/{id}/join {password}
         → 校验密码；错误累计 3 次 → 40019 锁定 5 分钟
         → 成功写 ml:room:pwd:{roomId}:{userId}（30min）
  → 否则 POST /join（黑名单 / 踢出冷却 / 满员）
  → WS 已连接 → room.join {roomId}（真实房可省略 password）
       → requireActiveForJoin / 黑名单 / 踢出冷却 / 满员 / 密码缓存
       → registry.joinRoom + presence.joinRoom
       → onWsJoin：写成员关系、最近访问、在线人数、房主占 1 号麦
       → room.join.ack（完整快照）
       → 广播 room.member.join（不含自己）
```

重复 join：同一连接且房间相同 → 只重发 ack，不重复广播。

### 5.3 控播与队列消费

```
room.switch {songId, clientMsgId}
  → findManagedRoom：真实房 / 演示房
  → 真实房：requireActiveForOperation + 黑名单 + canControlPlayback
  → 去重（clientMsgId）
  → 读取旧 songId
  → lock ml:lock:room:play:{roomId}
      → 校验歌曲可播
      → 计算 position / isPlaying
      → INCR ml:room:ver → HSET ml:room:play
      → 下发 ack
      → 广播 room.switch（全员，含发送方）
  → 释放锁
  → onPlayStateChanged(previousSongId, currentSongId)
      → UPDATE t_room.current_song_id
      → markPlayed(previousSongId)：把该歌最早的已通过队列项置为 status=3
```

注意：ack 与广播先于 DB 同步，验收脚本对队列状态使用**轮询最终一致性**，不立即断言。

### 5.4 上麦

```
POST /mic/apply
  → 房间活跃 + 是成员 + 未被禁言/拉黑
  → 已在麦上 → 幂等返回
  → 已在排麦队列 / Redis ZSet → 40009
  → needApprove=0 或 allowFreeMic=1：尝试 assignFirstFree（分布式锁）
       成功 → 写 t_room_mic + Redis Hash + 广播 room.mic.update
  → 否则入排麦队列（上限 50）
       → t_room_queue(queue_type=1, status=0) + ZADD
       → 广播 room.queue.update

POST /mic/approve {userId, approve}
  → 房主/房管
  → 找到排麦项
  → 同意：assignFirstFree → 更新 mic + 队列 status=1 → 定向通知 + 广播
  → 拒绝：status=2 → 移出 ZSet → 定向通知 + 广播

下麦 / 离房 / 被踢 / 被禁言
  → release：删除 t_room_mic、Redis Hash、排麦 ZSet，排麦项置为已播
```

### 5.5 禁言 / 踢人 / 拉黑

```
禁言：
  → 房主/房管；房主不可被禁言（40007）；房管不能管房管（40006，房主除外）
  → durationMinutes = -1 仅房主
  → Redis Hash 到期时间 + t_room_member.mute_status/until
  → 被禁言者自动下麦
  → room.member.update + 站内通知 + room.system

踢人：
  → 房主/房管；房主不可被踢；房管不能踢房管
  → 写 ml:room:kick:{roomId}:{userId} TTL 5min
  → 下麦、结算停留、广播离开
  → 定向 room.kicked（含剩余秒数）+ 站内通知
  → 最后断开该用户在本房间的连接（4003）

拉黑：
  → 仅房主；不能拉黑自己
  → 上限 200（40017）
  → Redis Set + t_room_member.room_role=9
  → 强制离开、广播、站内通知
  → 断开该用户在本房间的连接（4004）
```

### 5.6 关闭 / 重开 / 解散

```
关闭：
  → 房主；requireActiveForOperation
  → 广播 room.closed（reason=closed）
  → 先落 status=0、online_count=0
  → 断开房间全部连接（4005）
  → 给成员发站内通知

重开：
  → 房主；仅 status=0 且关闭时间 < 24h
  → status=1、last_active_time=now
  → 广播 room.reopened

解散：
  → 房主；confirmName 必须等于房间名
  → 广播 room.closed（reason=dissolved）→ 站内通知 → 落 status=2
  → 断开全部连接（4005）
  → clearRoom：删除在线集合、播放态、版本号、麦位、队列、禁言、黑名单、踢出冷却等 ml:room:* 键
```

定时任务：

- 空房（online_count=0 且 Redis 在线集合为空）超过 30 分钟 → status=0，通知房主
- status=0 超过 24 小时 → status=2
- status=1 且无活跃超过 7 天 → status=2
- 每分钟清理到期禁言（Redis Hash + DB 字段）

### 5.7 前端房间页

```
/room/:roomNo
  → useQuery(detail)
  → applyRoomDetail：先渲染房间壳
  → 若 status != 1：展示已关闭 / 已解散，不连 WS
  → 若密码房且无权限：弹密码框 → HTTP join → 成功后 joinRoom
  → wsStore.joinRoom(roomId, password?)
      → room.join.ack 覆盖 detail/members/mics/queue/角色/权限
  → 播放器从 room.join.ack / room.sync 的 position + serverTime 推算进度
  → 每秒按 serverTime 重新计算当前进度，避免本地时钟漂移
  → 退房 / 被踢 / 关房：leaveRoom 清空房间态，保留退出提示
```
