## 2. 系分决策（ADR）

前序编号 D-01~D-32 见模块 01 / 03 文档。

| 编号 | 决策 | 理由与备选 |
|---|---|---|
| **D-33** | 搜索引擎**端口化**：`SearchEngine` 接口 + `MysqlSearchEngine` 实现；ES 作为**目标设计**冻结在文档里，本轮**不装 ES** | 三条理由：① 本机没有 ES，装 ES 是机器级动作（需要启 Docker 守护进程 + 拉 1.5GB 镜像，或下 500MB 压缩包），未经确认不做；② **BR-15-009 把「MySQL LIKE 降级」定为永久交付项**，所以这份实现不是临时脚手架，就是 PRD 要求的那条降级路径本身；③ 用户口径是「先完成 MVP」——MySQL 引擎当天可跑通可验收。**代价必须记住**：丢了 IK 分词、BM25 打分、Completion Suggester、`search_after` 深分页、编辑距离容错。落地 `EsSearchEngine` 时不需要动 `SearchService` 以上的任何一层，也不需要动接口契约 |
| **D-34** | MySQL 里**自己算相关性分**：把 PRD 的字段权重**照搬**成一个 SQL 加权表达式 | PRD 给的是 ES 的字段权重（`name^5`/`name.pinyin^3`/`name.pinyin_first^4`/`artist_name^3`/`album_name^2`/`tags^2`/`lyric^1`）。MySQL 没有打分器，但**权重是业务语义、不是引擎细节**，可以直接翻译：`score = Σ 命中权重`。妙处在于权重表一个字没改，换的只是打分器。打分表达式见 §4.2。**备选与否决**：`MATCH…AGAINST` + ngram 全文索引——默认 `ngram_token_size=2`，**单字查询（如「周」）永远匹配不上**，而中文单字搜索是刚需；且 ngram 给不出字段权重，还得再用 CASE 补分，等于两套东西叠着。故不用。同时**热度不并入打分**：PRD 用 `function_score` 把 `hot_score × 0.001` 混进 `_score`，SQL 里改成「相关性降序 → 热度降序」的并列排序键。差异是：极热的歌**不能**压过明显更相关的歌。这更贴近「最相关的排最前」的直觉，登记为有意偏差 |
| **D-35** | 拼音**写时物化**成列：`t_song` 加 `name_pinyin`/`name_pinyin_first`/`artist_name_pinyin`/`artist_name_pinyin_first`，`t_artist`/`t_album` 各加 `name_pinyin`/`name_pinyin_first`；用 `pinyin4j` 生成 | PRD 用 `analysis-pinyin` 插件让 ES 索引期自动生成，无需应用层改造。没有 ES 就必须自己物化。**放哪儿？** 放原表而不是另建「搜索文档表」——因为 schema 里**已有先例**：`t_artist.first_letter CHAR(1) COMMENT '首字母(拼音)'`，拼音派生数据本来就住在曲库表上。另建文档表的好处（给 FR-15-007 一个同步目标）在 LIKE 检索下**是零收益**：`LIKE '%x%'` 反正全表扫，多一份拷贝只多一份不一致。**回填**：`ApplicationReadyEvent` 时只更新 `name_pinyin IS NULL` 的行，且 UPDATE 语句里显式写 `update_time = update_time` 抑制 `ON UPDATE CURRENT_TIMESTAMP` —— 这样回填**不动 `update_time`**，不会扰动模块 03 的缓存语义与将来 ES 的外部版本号 |
| **D-36** | 歌词检索前**剥离 LRC 标记**（`[00:15.00]`、`[ti:...]`）再匹配 | 库里 `t_lyric.content` 是带时间轴的 LRC 原文。不剥离会有两个后果：① 搜「00」命中全部歌词（全是时间戳）；② 高亮片段会高亮到时间戳上。剥离用 `REGEXP_REPLACE(content,'\\[[^]]*\\]','')`。PRD 的 ES 方案里歌词进文档时也是纯文本（`ik_smart` 分析），所以**剥离是 PRD 设计的隐含要求**，这里只是把剥离点从「建文档」挪到「查询期」。代价：`REGEXP_REPLACE` 逐行跑在 LONGTEXT 上，**规模上必须改成预计算列**，登记 §9 |
| **D-37** | 高亮在**应用层**做，且**必须先 HTML 转义再插 `<em>`** | ES 会返回 `highlight` 片段，MySQL 不会。应用层做法：取字段原文 → HTML 转义 → 把关键词替换成 `<em class="hl">词</em>`（BR-15-005 的标签照抄）。**转义不是可选项**：歌曲名/歌词是用户可投稿内容，直接拼 `<em>` 进 HTML 等于把存储型 XSS 送到前端。PRD 没提这一点，但它是「高亮」这个功能的必要条件 |
| **D-38** | BR-15-002 敏感词：**结构就位 + 词典可配、默认空** | BR-15-002 说「必须经过敏感词过滤」，但敏感词库属模块 18（内容安全），`schema.sql` 里没有 `t_sensitive_word`。沿用模块 03 的 D-22 先例（白名单默认空 + 配置注入）：实现 `SensitiveWordSupport`，词典从 `t_sys_config` 键 `search.sensitive.words`（逗号分隔）读，**默认空**。空词典 = 不拦任何词，但**代码路径、错误码、埋点位全部就位**，且写入一个配置行即可实测。登记为对 BR-15-002「必须」的结构性满足而非内容性满足 |
| **D-39** | BR-15-008 的「游客 30/登录 60」用**显式调用 `RateLimitService.enforce`** 实现，**不改模块 03 的 `@RateLimit` 注解** | BR-15-008 是**同一接口按登录态给两档阈值**，而 `@RateLimit` 是「一个注解 = 一个阈值」，表达不了。三条候选：① 给注解加 `limitAuthenticated` 属性 + 新维度 `SUBJECT`——要动模块 03 的公共组件，回归面大；② 叠两个注解（IP 30 + USER 60）——**错的**：登录用户也有 IP，会先被 30 那档拦住；③ **直接用现成的 `RateLimitService.enforce(type, dimension, identifier, limit, window, api, message)`**——它是 public 的（ACCOUNT 维度本来就要业务代码自己调），登录用户查 `USER` 档 60，游客查 `IP` 档 30，键天然分片（`u:123` vs `ip:1.2.3.4`）。选 ③：**零改动模块 03**，语义正确 |
| **D-40** | 深分页：`from ≥ 1000` 时必须带 `cursor`（BR-15-010） | PRD 要求 `from + size ≤ 1000`，超出走 `search_after`。`PageQuery.MAX_PAGE_SIZE=100`，所以 pageSize=100 时第 10 页就是边界。游标做成不透明串（`base64(score.hotScore.id)` 的最后一行），SQL 用**行值比较** `(relevance, hot_score, id) < (?,?,?)` 配 `ORDER BY … DESC`，是 MySQL 8 支持的字典序语义。直接给一个 `pageNum` 超过边界的请求而**不带**游标时返回 `70005`（明确告知，而不是静默返回空列表让人以为「没数据了」） |
| **D-41** | 无结果返回 **`code: 0` + 空列表 + `suggestWords`**，**不把 `70003` 当错误码** | PRD 05 定义了 `70003 无搜索结果`，PRD 15 的 `EX-15-001-4` 又写「返回空列表 + 推荐搜索词（70003）」。但「查询成功、就是没命中」不是错误：返回非 0 code 会让前端拦截器按错误弹 Toast，与同一行的「展示推荐词」自相矛盾。取「返回空列表 + 推荐词」这半边，`70003` 仍然在 `ResultCode` 里声明（PRD 05 的全局码表完整性），但不作为错误返回 |
| **D-42** | 无版权歌曲**默认过滤掉**（照 §4 的 `filter`），但做成开关 `newmusic.search.include-unplayable` | **PRD 15 自相矛盾**：BR-15-003 与 §4 的 ES 查询都写「只返回 `copyright_status=1`」，同一句括注却写「无版权歌曲在搜索中标记『无版权』但可展示，点击不可播放」。既然括注专门描述了标记行为，说明产品意图里**有**这个展示位；但可机器执行的契约（两处 `filter`）是过滤。处置：**默认服从可执行契约（过滤）**，把「要不要展示无版权」做成配置开关，翻开关即得另一种行为，并在 §9 登记为需产品确认。开关打开时返回项带 `playable:false` + `copyrightStatus`，前端据此置灰 |
| **D-43** | 搜索历史与热搜的异步记录用**自建显式线程池 + `CompletableFuture.runAsync`**，不引 `@EnableAsync` | BR-15-006/007 要求「异步、不阻塞响应」。项目当前没有 `@EnableAsync`。显式线程池的好处：队列有界、拒绝策略明确、`@PreDestroy` 能关、在测试里可等待收敛；`@Async` 是全局开关，一旦有人标在别处就会共用同一个池。线程池与拒绝策略见 §3 |
| **D-44** | 搜索模块**自建只读 Mapper** 跨表投影（`t_song`/`t_lyric`/`t_artist`/`t_album`/`t_playlist`/`t_song_tag`/`t_tag`），**不注入曲库模块的任何 Bean** | 模块 01 定的硬约束是「**禁止跨模块 Mapper 访问**」，防的是「A 模块注入 B 模块的 Mapper/Service，把 B 的领域逻辑绕过去」。搜索是一次**只读跨域投影**，天然不属任何单一领域。两条路：把搜索 SQL 塞进 `SongMapper`（污染曲库模块，且反向依赖）或自建只读 Mapper（依赖方向干净）。选后者。它**只读、不写、不引用曲库的实体以外的任何 Bean**，判为合规并在此备案 |
| **D-45** | 给 `RedisOps` **补 ZSet 能力**（`zincrby`/`zrevrangeWithScores`/`zrem`），add-only | 热搜（BR-15-028 `ZINCRBY`）需要 ZSet，而模块 03 的 `RedisOps` 只有 String / 计数 / Set / 按前缀删。补在 `RedisOps` 而不是在搜索模块里直接用 `StringRedisTemplate`：`RedisOps` 是「唯一简单结构出口」，且它统一经 `RedisGuard` 熔断、统一守 `ml:` 前缀——绕开它等于绕开这两条。**add-only，不改任何已有方法签名**，模块 03 无回归风险 |
| **D-46** | BR-15-012 的「首字母完整词边界匹配」实现为**前缀匹配 + 最短 2 字符** | PRD 的意图是「避免 `q`/`t` 匹配过多」。单字符前缀在中文曲库里召回面极大（`z` 命中所有 zh/z 开头的歌），故要求首字母输入长度 ≥ 2 且用 `LIKE 'kw%'`（前缀）而非 `LIKE '%kw%'`。全拼则用 `LIKE '%kw%'`——PRD 的 ES 侧开了 `fuzziness: AUTO`，比 `%kw%` 更宽松，所以这里仍然是**收紧**而非放宽 |
| **D-47** | `t_search_history`/`t_search_hot` 两表按 PRD 04 的原样录入 `schema.sql` | PRD 04 §10 已给出定义，但 `sql/schema.sql` 里没有（模块 01 只建到曲库+系统域）。照抄 PRD 04 的 DDL，不自行增删字段——这两张表是 PRD 全文档共用的契约 |
| **D-48** | 响应统一带 `degraded` 与 `costMs` 两个字段 | PRD 的 `EX-15-001-1` 要求「响应头标记 `degraded: true`」。放**响应头**对前端不友好（跨域时要 `Access-Control-Expose-Headers`，且类型不安全），放**响应体**里前端直接读。两个都做：体里有 `degraded`，同时写同名响应头给网关/监控用。`costMs` 是本模块自测 P95 的要据，也便于前端做慢查询埋点 |

## 4. 检索设计

### 4.1 为什么不是全文索引

`t_song` 现在没有任何全文索引，本轮也不加。三条理由：

1. **单字查询是刚需**。中文用户搜「周」，ngram（默认 `token_size=2`）匹配不到单字，于是还得补一条 `LIKE` 分支，两套逻辑并行。
2. **ngram 给不出字段权重**。权重（`name^5` 等）是 PRD 的核心业务语义，用 ngram 只能再叠一层 `CASE` 加权，等于用全文索引只买到「候选集」，排序还是自己算。
3. **规模上 MySQL 本来就不是终局**。真到 PRD 说的 100 万首，正确动作是上 ES（D-33），不是继续把 MySQL 榨干。

结论：本轮用**加权 `LIKE` 打分**，把「全表扫」这个代价**明确登记**在 §9，而不是用一个半吊子的全文索引把问题盖住。

### 4.2 打分表达式（D-34 的落地）

```sql
-- 输入全是 ASCII 字母（BR-15-014）时，额外启用拼音三列；含中文时这几项恒为 0
score = 5 * (name             LIKE CONCAT('%', #{kw}, '%'))
      + 4 * (name_pinyin_first LIKE CONCAT(#{pyKw}, '%')   AND CHAR_LENGTH(#{pyKw}) >= 2)  -- BR-15-012/D-46
      + 3 * (name_pinyin       LIKE CONCAT('%', #{pyKw}, '%'))
      + 3 * (artist_name       LIKE CONCAT('%', #{kw}, '%'))
      + 3 * (artist_name_pinyin LIKE CONCAT('%', #{pyKw}, '%'))
      + 2 * (album_name        LIKE CONCAT('%', #{kw}, '%'))
      + 2 * (EXISTS (SELECT 1 FROM t_song_tag st JOIN t_tag t ON t.id = st.tag_id
                     WHERE st.song_id = s.id AND t.status = 1 AND t.deleted = 0
                       AND t.name LIKE CONCAT('%', #{kw}, '%')))
      + 1 * (EXISTS (SELECT 1 FROM t_lyric l
                     WHERE l.song_id = s.id AND l.deleted = 0
                       AND REGEXP_REPLACE(l.content, '\\[[^]]*\\]', '') LIKE CONCAT('%', #{kw}, '%')))
```

- `#{kw}` 是**原样关键词**，`#{pyKw}` 是**小写关键词**（拼音列存的是小写）。含中文时 `pyKw` 传 `NULL`，三处拼音项自动为 0，`LIKE NULL` 不命中——省掉拼接分支，且完全对应 BR-15-014。
- 匹配谓词（`WHERE`）与打分共用同一组条件：`score > 0` 即命中。这样「命中」与「得分」**不可能不一致**（若分开写，迟早出现「有分但没被选上」或反之的诡异结果）。
- 歌词那一项恒参与：`type=lyric` 时只保留歌词项，`type=song` 时歌词项也参与（歌词是 `lyric^1`，PRD 的 `multi_match` 里它本来就在字段列表内）。`type=lyric` 的判定靠 `matchedFields` 里含 `lyric`。

### 4.3 排序

| `sort` | `ORDER BY` | PRD |
|---|---|---|
| `relevance`（默认，综合） | `score DESC, hot_score DESC, id DESC` | 相关性 + 热度 |
| `hot` | `hot_score DESC, id DESC` | `hot_score DESC` |
| `newest` | `publish_time DESC, id DESC` | `publish_time DESC` |
| `duration_asc` / `duration_desc` | `duration ASC/DESC, id DESC` | `duration ASC/DESC` |

三个排序键里 `id DESC` 是**兜底且必需**的：没有它，`hot_score` 相同的行顺序由存储引擎决定，**游标分页会漏行或重行**，而且响应不可复现（验收脚本会随机红）。

### 4.4 过滤（FR-15-006）

维度内 OR、维度间 AND（BR-15-035），且**不参与打分**（BR-15-036 的意图——SQL 里就是 `WHERE` 的独立谓词，不进 `score`）：

| 参数 | 取值 | 谓词 |
|---|---|---|
| `language` | 多值逗号分隔 | `language IN (...)` |
| `genre` | 多值 | `genre IN (...)` |
| `era` | 多值（`80s`/`90s`/`00s`/`10s`/`20s`） | `era IN (...)` |
| `duration` | 多值：`lt3`(<180s) / `3to5`(180~300s) / `gt5`(>300s) | `OR` 组合的区间 |

PRD 把**情绪 / 场景**列为筛选维度但标注 P1，且 `t_song` 里**没有这两列**（`emotion` 在 `t_lyric` 上，`scene` 哪都没有）→ 本轮不支持，登记 §9。

### 4.5 综合 Tab 的配额（BR-15-004）

歌曲 10 + 歌手 3 + 专辑 3 + 歌单 3。实现为**四次独立检索**（各自 `LIMIT`），而不是「查 19 条再分类」——配额是**每类的上限**，不是总上限。

歌手的拼音检索走 `t_artist`（D-35 给它加了拼音列），专辑走 `t_album`，歌单只按 `name` + `tags` LIKE（PRD §6.2 没给歌单拼音，D-35 照此不加）。

### 4.6 联想的数据来源与缓存

```
keyword.length < 1 或 全空白 ──► 只返回热搜词（BR-15-019）
否则：
  ├─ cacheKey = ml:search:suggest:{前 8 字符}（BR-15-020）
  ├─ CacheService.get(cacheKey) ──命中──► 取回「裸数据」→ **按本次 keyword 现算高亮** → 返回
  └─ miss ──► 三类前缀查询（歌手 > 歌曲 > 专辑 > 歌单，BR-15-016）
              ├─ t_artist  name/name_pinyin/name_pinyin_first LIKE 'kw%'
              ├─ t_song    name/name_pinyin/name_pinyin_first LIKE 'kw%'
              ├─ t_album   name/name_pinyin/name_pinyin_first LIKE 'kw%'
              └─ t_playlist name LIKE 'kw%'
              → 过滤（敏感词、纯符号、单字符，BR-15-018）→ 截断到 10（BR-15-015）
              → 写缓存（TTL 1h ±10%，**不含高亮**）
              → 本次现算高亮 → 返回
  └─ 三类都空 ──► 热搜词兜底（BR-15-021）
```

**高亮为什么不能进缓存**：BR-15-020 让「周杰伦的歌」与「周杰伦的曲」共用缓存键（都取前 8 字 `周杰伦的歌`…——实际取前 8 **字符**），而两者的高亮区间不同。缓存里存**数据**（`text`/`type`/`id`/`extra`），高亮**每次按真实 keyword 现算**。这是「按前 8 字符缓存」这条规则的必然推论。

## 6. 关键时序

### 6.1 关键词搜索（含降级路由）

```

  │
  ├─ 1. normalize()：pageNum/pageSize/keyword 归一（PageQuery）
  ├─ 2. 限流：登录 → USER 60/min；游客 → IP 30/min（D-39，显式 enforce）
  │      └─ 超限 → 10004 + Retry-After
  ├─ 3. 敏感词（SensitiveWordSupport，词典默认空 D-38）
  │      └─ 命中 → 70004
  ├─ 4. keyword 为空 → 热搜 + 历史（BR-15-001），结束
  ├─ 5. 深分页校验：from ≥ 1000 且无 cursor → 70005（D-40）
  ├─ 6. SearchEngineRouter.pick()
  │      ├─ 首选引擎 isAvailable() ──是──► 用它
  │      └─ 否 ──► 依次试后续引擎；全不可用 ──► 70001 + 热门歌曲兜底
  │              （实际引擎 != 首选 → degraded = true，写响应体与响应头）
  ├─ 7. MysqlSearchEngine.search()：
  │      打分表达式（§4.2）+ 过滤（§4.4）+ 排序（§4.3）+ LIMIT（或行值游标）
  ├─ 8. 组装：matchedFields（按各项 >0 反推）、highlight（现算、先转义 D-37）、playable
  ├─ 9. **异步**（不阻塞响应，D-43）：
  │      ├─ BR-15-007 热搜 ZINCRBY（同 subject 同词 1 分钟内只计一次）
  │      └─ BR-15-006 登录用户写历史（LREM + LPUSH + LTRIM 20 + t_search_history）
  │      注：敏感词命中的请求在第 3 步就返回了，**天然不会被记录**（BR-15-027）
  └─ 10. 返回（带 degraded / costMs）
```

### 6.2 热搜快照（BR-15-031/032/033）

```
GET /api/v1/search/hot
  │

  │    └─ 命中 ──► 直接返回（5 分钟内所有人看到同一份，BR-15-032）
  └─ miss ──► 重建：
        ├─ ZREVRANGE ml:search:hot:realtime 0 49 WITHSCORES
        ├─ 过滤敏感词 / 纯符号 / 单字符（BR-15-029）→ 取 Top 10
        ├─ 读 ml:search:hot:last（上一份快照的计数）算增速（BR-15-033）：
        │     增速 > 5 且排名上升 → 爆 ；> 3 → 热
        │     ml:search:hot:seen:{word} 不存在 → 新（SETNX, TTL 24h）
        ├─ 置顶词（t_search_hot 当日 is_top=1，最多 3）插到最前（BR-15-030）
        ├─ 写 ml:search:hot:snapshot (TTL 300s) 与 ml:search:hot:last (TTL 1h)
        └─ 榜单为空（ZSet 丢过 / 全新部署）→ 从 t_search_hot 最近一天重建（EX-15-005-2）
             ；仍为空 → 用 t_sys_config 的 search.hot.defaults（EX-15-005-3）

@Scheduled(cron = "0 5 * * * ?")  每小时第 5 分钟（BR-15-031）
  └─ ZREVRANGE 实时榜 → upsert t_search_hot(stat_date=today, keyword)（uk 保证幂等）
```

> **为什么整点过 5 分落库而不是整点**：模块 03 的 T317 已记录本项目尚未引入 XXL-Job，`@Scheduled` 是临时手段；错开整点是为了避开其它定时任务（模块 03 遗留的榜单任务同样会挑整点），减少同一秒的 DB 争用。这里登记为偏差，模块 09 引入调度平台后迁走。

### 6.3 搜索历史

```
写（搜索成功后的异步尾巴）：
  仅登录用户 ── LREM ml:search:his:{userId} 0 <kw>  →  LPUSH <kw>  →  LTRIM 0 19
            └─ 同时 insert t_search_history（用于分析）

GET  /api/v1/search/history  → LRANGE 0 19（不查库：Redis 是这份数据的权威副本）
DELETE /api/v1/search/history?keyword=x → LREM 1 条（只删一条）
DELETE /api/v1/search/history/all → DEL 整个键
```

> **为什么 GET 不查库**：BR-15-022 说 Redis 是「历史」的存储、`t_search_history` 是「落库用于分析」。两者用途不同，所以**读走 Redis、写同时落库**，不做「Redis 丢了从库里恢复」（那样会恢复出跨设备的、更早的、被用户删过的条目，与 BR-15-024「清空后为空」冲突）。

## 9. 风险与已知偏差

| 项 | 说明 | 处置 |
|---|---|---|
| **本轮没有 ES**（D-33，**需评审**） | PRD §3 把 ES 7.17 + IK + pinyin 列为前置条件，实际未部署 | 用 `SearchEngine` 端口隔离；`MysqlSearchEngine` 同时是 BR-15-009 的永久降级路径，非临时品。装 ES 的代价（启 Docker 守护进程 + 拉镜像 / 下 500MB 压缩包）**未经确认不做**；`EsSearchEngine` 与 `FR-15-007` 见 T631 |

| **歌词检索逐行 `REGEXP_REPLACE`**（D-36） | LONGTEXT 上做正则，行数一多就贵 | 本机可接受；规模上必须改成预计算列（T636）。**这是本模块最容易被低估的性能点** |
