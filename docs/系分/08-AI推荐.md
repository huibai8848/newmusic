## 2. 系分决策（ADR）

| 编号 | 决策 | 理由 | 影响面 |
|---|---|---|---|
| **D-01** | 没有向量服务，推荐打分改为**可解释的内容特征 + 行为聚合**：画像来自最近 90 天播放的衰减聚合，候选按热度/风格/语种/歌手/标签/心情/喜欢加权；推荐理由取**贡献最大的那一项** | PRD 的「多路召回 + 精排」依赖向量库与模型服务，本机都没有。硬造一个余弦相似度只会得到不可解释的黑盒。当前公式每一分都能回溯到数据，理由天然真实（BR-17-013），且接口字段（`reason` / `recall` / `score`）与未来接模型时一致 | `ScoringService`、`CandidateService` |
| **D-02** | 反馈采用**追加日志 + 回放**：`t_recommend_feedback` 只追加，Redis Set 只是回放结果的物化；`ml:rec:block:loaded:{uid}` 标记已回放，Redis 不可用时直接回放数据库 | 「撤销」不是删除历史，而是又一条事件；否则无法审计，也无法处理「先屏蔽歌手、再撤销单曲」这类顺序语义。物化让每次推荐只读 3 个 Set，标记避免每次请求扫表 | `FeedbackService` |
| **D-03** | 每日推荐缓存键带日期 `ml:rec:daily:{uid}:{yyyy-MM-dd}`，TTL 48h；当日缓存读取时**按最新屏蔽列表过滤**，但不重新生成 | 日期进键才能保证「0 点后更新」；48h 覆盖跨日与预热。反馈要求「当日每日推荐不变、次日生效」（BR-17-020），因此缓存内容不动，只在读取时剔除屏蔽项 | `DailyRecommendService` |
| **D-04** | 猜你喜欢缓存**候选池**（最多 100 首，30 分钟），翻页时再**按页**应用歌手 ≤2 / 专辑 ≤1；`hasNext` 通过**多选一页**判断 | 若生成池时就套死多样性，第二页会几乎没有内容；若用 `>= need` 判断，候选池恰好装满整数页时会给出「下一页为空」的假 `hasNext`。贪心选择对前缀稳定，多选一页不改变前面几页 | `GuessRecommendService`、`ScoringService.selectDiverseItems` |
| **D-05** | 相似歌曲**离线预计算优先**：每日 03:30 重算 Top 20 写入 `t_song_similar` 与 Redis（7 天）；新歌无数据时在线按同一公式实时计算并落库；结果不足 20 时用热门补足并置 `fallback=true` | 离线矩阵把 O(n²) 从请求路径挪走；新歌必须有 30 秒内可见的相似推荐（AC-17-004-4），只能在线降级；落库后下一次请求即命中 | `SimilarRecommendService`、`RecommendJob` |
| **D-06** | 播放历史 / 进度 / 结束上报**前移到 `module/play`**，接口语义按模块 12 的最终契约设计 | 模块 07 原计划把历史推迟到模块 12，但推荐没有服务端行为数据就无法个性化。现在实现最小闭环，模块 12 只替换聚合方式与存储规模，不改接口 | `module/play`、`services/playReport.ts` |
| **D-07** | 有效播放口径：`playedDuration ≥ 30s` **或** `≥ 60% 歌曲时长` **或** `completed=true`；`play_count` 只在**首次**从无效变有效时 +1 | 与 PRD 一致。只在状态跃迁时累加，避免前端重复 `end` 刷播放量；结束上报的 `position` 与 `playedDuration` 语义分开，拖动进度条不会把续播点拉回 | `PlayHistoryService` |
| **D-08** | 继续播放只返回进度 **10%~90%**、最多 **10 首**；移除写 `ml:rec:continue:hidden:{uid}`，30 天不再出现 | 0%~10% 基本是误点，90%~100% 已接近听完；上限 10 保持首页/推荐页密度。移除是用户显式意图，必须持久于一次刷新 | `ContinuePlayService` |
| **D-09** | 定时任务用 `@Scheduled` 代替 XXL-Job：00:10 预热活跃用户每日推荐，03:30 重算相似矩阵；异常只记日志，不删除旧数据 | 本机没有调度平台。预热与重算逻辑都在 Service 中，接入 XXL-Job 时只需迁走方法 | `RecommendJob` |
| **D-10** | 首页聚合对四个区块**分别 try-catch**，失败区块返回空并写入 `degraded`；前端各区块也各自请求、各自兜底 | 推荐是增强能力，任何一个区块故障都不应该让首页白屏。`degraded` 让前端可以做局部提示 | `RecommendService`、`HomePage` |
| **D-11** | 鉴权边界：`similar` 公开（游客可看，但无个性化屏蔽态）；`record` / `end` 公开（游客按 `deviceId` 归属）；`progress` / `history` / 其余推荐接口要求登录 | 相似歌曲是歌曲详情页的一部分，不应强迫登录；游客播放也要进入历史（PRD 允许），但个性化画像只对登录用户可用 | `RecommendController`、`PlayHistoryController` |
| **D-12** | 雪花 `Long` 仅在超过 JS 安全整数范围时序列化为字符串；前端统一把 ID 当 `string` 处理，混合类型处使用 `String(id)` | 全局约定（模块 01 D-05）。19 位 ID 转字符串防精度丢失，计数与分页保持数字可直接运算 | `JacksonConfig`、`web/src/types/api.ts` |
| **D-13** | 反馈前端按 PRD 补两处交互：不喜欢后 **5 秒通知 + 撤销按钮**；不喜欢歌手前 **Modal 二次确认**；失败自动重试 2 次 | `BR-17-016` / `BR-17-018` 是 P0 验收项，不能只做接口。通知消失后仍可从屏蔽管理恢复，覆盖「撤销超时」的兜底路径 | `FeedbackMenu` |

### 4.2 每日推荐

```json
{
  "code": 0,
  "data": {
    "date": "2026-10-18",
    "fallback": false,
    "generatedAt": 1792300800123,
    "items": [
      {
        "song": { "id": "1000000000000005001", "name": "晴天", "artistName": "周杰伦", "...": "..." },
        "reason": "你喜欢的流行风格",
        "recall": "genre",
        "score": 0.7312,
        "position": 1,
        "listened": false
      }
    ]
  }
}
```

- `items` 目标 30 首；曲库不足或屏蔽过多时允许更少（EX-17-001-4）
- 单曲歌手不超过 2 首；`reason` 不超过 20 个字符
- 生成异常时走 `fallback=true` 的热门兜底，兜底仍会应用歌手上限与屏蔽过滤

### 4.3 猜你喜欢

```json
{
  "page": 1,
  "pageSize": 20,
  "hasNext": true,
  "coldStart": false,
  "items": [ /* 同每日推荐条目 */ ]
}
```

- `hasNext` 表示**本页之后还有内容**，不是「本页已满」
- 每页内歌手 ≤2、专辑 ≤1；同一页不重复
- `coldStart=true` 表示行为不足 5 条，结果以热门 / 问卷偏好为主
- 播放新歌、反馈、提交问卷都会删除 `ml:rec:guess:{uid}`，下一次请求重算

### 4.4 反馈

```json
POST /api/v1/recommend/feedback
{
  "songId": "1000000000000005001",
  "artistId": "1000000000000001001",
  "action": "DISLIKE",
  "scene": "DAILY",
  "position": 3
}
```

| `action` | 必填 | 语义 | Redis 变更 |
|---|---|---|---|
| `LIKE` | `songId` | 正向信号，理由优先展示「你喜欢的歌曲」 | 加入 `rec:like`，移出 `rec:dislike` |
| `DISLIKE` | `songId` | 永久排除该曲 | 加入 `rec:dislike`，移出 `rec:like` |
| `DISLIKE_ARTIST` | `artistId`（可只传 `songId`，服务端派生） | 永久排除该歌手 | 加入 `rec:dislike:artist` |
| `UNDO` | `songId` | 撤销歌曲喜欢 / 不喜欢 | 移出两个歌曲 Set |
| `UNDO_ARTIST` | `artistId` | 撤销歌手屏蔽 | 移出歌手 Set |

```json

POST /api/v1/play/progress
{ "songId": "...", "playId": "...", "position": 50, "duration": 200 }

POST /api/v1/play/end
{ "playId": "...", "playedDuration": 180, "songDuration": 200, "position": 150, "completed": false, "deviceId": "guest-xxx" }
```

- `record` 5 秒内同一主体（登录用户按 `userId`，游客按 `deviceId`）同一首歌重复上报返回 `duplicated=true` 与已有 `playId`

- 游客 `end` 必须携带与 `record` 一致的 `deviceId`，否则静默忽略

## 6. 打分与生成流程

### 6.1 用户画像

`ScoringService.buildProfile(userId)`：

1. `behaviorCount = COUNT(t_play_history WHERE user_id = ?)`；`< 5` 即冷启动
2. 问卷权重 `w = max(0.2, 1 - 0.2 * floor(behaviorCount / 10))`；风格 / 语种直接累加 `w`，歌手累加 `1.2w`，心情单独记录
3. 最近 90 天、最多 500 条播放：
   - 时间衰减 `exp(-0.05 * days)`（约 14 天减半）
   - 有效播放权重 `1.0`，无效播放 `0.35`
   - 歌手累加衰减值；风格 ×0.6；语种 ×0.4；歌曲标签 ×0.4
4. 四张权重表分别归一化
5. 最近播放 ID（50 首）与喜欢歌曲 ID 进入画像

### 6.2 单曲打分

| 特征 | 权重 | 说明 |
|---|---|---|
| 热度 | 0.30 | `hotScore / 1000`，上限 1 |
| 歌手 | 0.20 | 画像歌手权重 |
| 风格 | 0.22 | 画像风格权重 |
| 语种 | 0.10 | 画像语种权重 |
| 标签 | 0.08 | 标签亲和度（与画像标签集合的重合） |
| 心情 | 0.10 | 问卷心情与歌曲标签 / 风格的匹配 |
| 喜欢 | 0.15 | 命中 `like` Set 时加分 |

推荐理由取贡献最大且超过阈值的项：歌手（≥0.08）→ 风格（≥0.08）→ 标签（≥0.045）→ 心情（≥0.05）→ 语种（≥0.05）；喜欢歌曲强制覆盖为「你喜欢的歌曲」；否则「最近很火的歌」。所有文案截断到 20 字。

### 6.3 每日推荐流水线

```
候选过滤（可播放 + 未屏蔽 + 当日未曝光）
  → 打分排序
  → 分档内轻洗牌（同一分数段内按 userId+date 定种，避免每天完全一样）
  → 冷启动：前 50% 热门 + 其余问卷偏好（无问卷则纯热门）
  → 非冷启动：插入 10% 探索位（约第 8/16/24 位，未听过且分数 < 0.45）
  → 多样性选择（歌手 ≤2，已听占比 ≤30%，不足时第二轮放开已听占比）
  → 写 Redis（48h）
```

### 6.4 猜你喜欢

- 候选池：可播放、未屏蔽的全部歌曲；已听歌曲分数 ×0.75（不排除）
- 缓存 100 首，30 分钟
- 每次请求取 `need + size` 首做多样性选择，再切出当前页；`hasNext = selected.size() > need`
- 每页歌手 ≤2、专辑 ≤1、已听占比 ≤20%

### 6.5 相似歌曲

```
score = 0.4 × 标签 Jaccard
      + 0.2 × 同风格
      + 0.1 × 同语种
      + 0.1 × 同年代
      + 0.1 × BPM 接近度
      + 0.1 × 近 90 天共现（按最大值归一）
```

- 离线路径：读 `t_song_similar` Top N（取 3 倍上限后过滤）
- 在线路径：实时计算、物理删除旧行、按 `score × 10000` 四舍五入落库
- 两条路径都做 `sanitize`：排除自身、不可播放、被屏蔽、歌手超限
- 不足 20 用热门补足，标记 `fallback=true`

### 6.6 继续播放与常听

- 继续播放：`last_position / song_duration ∈ [0.1, 0.9]`，按更新时间倒序，去重后最多 10 首
- 最近常听：近 30 天按歌手聚合播放次数，Top 8，缓存 60 分钟
- 最近播放：Redis ZSet 优先，缺失时回源数据库，默认 12 首、最多 50 首

## 9. 风险与已知偏差

| 编号 | 项 | 说明 | 处置 |
|---|---|---|---|
| R-01 | 没有向量召回 / 精排模型 | 打分是内容特征 + 行为聚合，效果上限低于 PRD 目标方案；冷门歌与跨风格发现能力有限 | 接口字段已对齐未来模型；模块 15 接入后只替换 `ScoringService`，不改契约 |
| R-02 | 曲库规模只有 40 首 / 16 歌手 / 22 专辑 | 歌手 ≤2、专辑 ≤1 与 20 首/页的组合容易把候选吃紧；猜你喜欢第 3 页可能为空（`hasNext=false` 是正确语义） | 验收脚本按真实曲库断言；扩大曲库后需复跑分页用例 |
| R-03 | 曝光排除只在**当日重算**时生效 | 正常路径当日缓存不重算，因此「曝光后不再生成」体现为：缓存被删除（手动 / 反馈 / 问卷）后重算时排除当日已曝光歌曲；跨日不排除，否则热门永远无法再次推荐 | 与 PRD「当日已曝光未点击不再生成」的字面语义一致；若要求曝光后立即重排，需要产品确认，当前刻意不做 |
| R-04 | 预热是单机 `@Scheduled` | `prewarmUserLimit=1000`，无分片、无执行记录；不能证明 AC-17-001-10 | 生产迁 XXL-Job（T826）；预热失败只记日志，不影响用户首次请求实时生成 |
| R-05 | 相似矩阵是全量 O(n²) | 当前几十首可接受；上万首会拖慢 03:30 任务 | 模块 15 改为分批 / 离线 Spark；失败保留旧数据（EX-17-004-3） |
| R-06 | `play_count` 的歌曲详情缓存可能滞后 | `incrementCounter` 不失效歌曲详情缓存，接口读到的 `playCount` 可能比数据库晚一拍 | 验收以 `newmusic.t_song.play_count` 为准；模块 12 统一处理缓存失效 |
| R-07 | 每日推荐过滤屏蔽后可能少于 30 | 读取缓存时按最新屏蔽列表过滤，不回填；屏蔽很多时列表变短 | PRD 允许曲库不足时少于 30（EX-17-001-4）；不为凑数突破歌手上限 |
| R-08 | 游客没有个性化推荐 | 游客可看相似歌曲，但 daily/guess 要求登录；首页对游客退回热门 | PRD 角色定义如此；游客播放历史按 `deviceId` 落库，登录后不会自动合并到用户画像 |
| R-09 | 5 秒撤销与二次确认尚未浏览器走查 | 代码已实现（D-13），自动化只覆盖接口；通知按钮、Modal 确认的实际交互未验 | T827 浏览器走查；走查前不把 `AC-17-002-2/4` 整行标绿 |
| R-10 | P1 未交付导致部分 AC 不可达 | 运营置顶、场景歌单、电台、效果统计 | 已在 §8 标 ⛔，排期模块 15 / 17 / 19 |
| R-11 | 共享 Redis / MySQL 的测试隔离依赖脚本 | 验收脚本使用固定探针账号 + 随机 `X-Forwarded-For`，只删自己的 `ml:rec:*{uid}*` / `ml:play:*{uid}*` 与 DB 行，并统计 `ranking:*` 数量 | 任何新增脚本必须沿用同样约束；禁止 `FLUSHDB/FLUSHALL`、禁止无 `newmusic.` 前缀的 SQL |
