### 2026-10-26：音乐房歌曲播放卡顿（seek ↔ canplay 自激）修复

**现象**：进入音乐房后歌曲持续卡顿、声音一顿一顿地重复，进度条几乎不前进；房间控制（暂停/继续/
重头播放）也能听到明显的断点。

**定位**：用 CDP 在 `/room/<roomNo>` 注入 `HTMLMediaElement` 事件监听（monkey-patch `Audio`
构造器 + `currentTime` setter），21 秒内捕获 **251,787** 个媒体事件，按约 1ms 的周期重复：

```
seeked → canplay → set currentTime → playing → seeking → waiting → seeked …
```

期间 `readyState` 长期停在 1（`HAVE_METADATA`），`currentTime` 反复被写回同一位置。

**根因**：`web/src/components/room/RoomAudioSync.tsx` 把 `onLoaded`（内部调用
`applyAuthority(true)`）同时挂在 `loadeddata` 与 `canplay` 上，而 `applyAuthority(true)`
会无条件 `hardSeek(expected)`。写 `currentTime` 触发 `seeking`/`waiting`，重新缓冲到可播后
浏览器**再次触发 `canplay`**，于是又 seek——自我维持的死循环。权威状态版本更新（暂停/继续）
时的无条件 seek 同样会制造一次可听的断点。

**修复**（只改 `RoomAudioSync.tsx`，纯规则 `roomSync.ts` 未动）：

1. 一次性对齐只挂 `loadedmetadata`（每个 `src` 只触发一次），移除 `loadeddata` / `canplay` 监听。
2. `hardSeek` 增加 `SEEK_EPSILON_MS = 100` 护栏：目标与当前位置相差 <100ms 时直接返回，
   不写 `currentTime`（100ms 内的对齐人耳不可辨，却会白白触发一整串媒体事件）。
3. `applyAuthority(true)` 仅在偏差超过 `SOFT_THRESHOLD_MS`（500ms，与 `roomSync.ts` 的软校准
   阈值一致）时才 seek；暂停/继续这类没有实际位移的权威更新只切换 `play()` / `pause()`。

**验证**（CDP，真实房间、歌曲《花海》264.6s）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 12~21 秒内媒体事件数 | 251,787 / 21s | 31 / 12s |
| 循环模式 | `seeked → canplay → seek`，约 1ms 一轮 | 无循环 |
| `readyState` | 长期 1 | 4 |
| seek 次数 | 每毫秒一次 | 1 次（初始对齐到 0.401s） |
| 进度推进 | 反复回到同一点 | 2.45 → 4.47 → 6.47 → 8.47 → 10.49 → 12.51（≈1.00x） |
| `waiting` | 持续出现 | 仅切换/seek 时出现一次 |

房间控件复测：暂停 → `paused=true`、停在 28s；继续 → 30.94s 正常推进；「重头播放」→ 2.43s；
每次操作只产生一次 seek（事件计数 31 → 39 → 40 → 48），无自激。

回归：`npm --prefix web run test` **545 / 0**，`npm --prefix web run build`（含 `tsc --noEmit`）通过。
`test-room-sync.mjs` 的 57 项纯函数断言不变（本次缺陷在事件接线层，纯函数覆盖不到）。

**经验（写进代码注释）**：`canplay` 会在**每次 seek 之后**重新触发，不能当作一次性对齐时机；
一次性对齐用 `loadedmetadata`。凡是可能被媒体事件回调再次触发的 seek，都必须有「偏差小于阈值
不写 `currentTime`」的护栏，否则事件回调与 seek 会互相点火。
